## 一、病因定義

候選 1 的病因不是「程式碼很長」，而是：

> **同一段資料庫存取樣板（組 SQL → 開連線／游標 → 執行 → 提交 → except 復原 → finally 釋放資源）
> 被複製多份，導致錯誤處理與資源管理散落在各呼叫端。**

由此推出兩個可檢驗的判準：

1. **重複性** —— 同一段錯誤處理／資源管理存在 N 份實作
2. **散落性** —— 修一個錯要修 N 次；測一個行為要測 N 次

以此掃描全 codebase，命中兩處：

| 位置 | 重複份數 | 散落的內容 |
| --- | --- | --- |
| `src/task/l_*.py` 8 支 loader | 8 | 約 20 行 upsert 樣板，逐字元相同 |
| `src/task/create_*_tables.py` 2 支建表任務 | 2（+`mysql_utils.create_tables()` 為第 3 份） | 5 行 `except/finally` 樣板，逐字元相同 |

第二處與第一處是**完全相同的結構**：一個通用實作（`upsert_to_table` /
`create_tables`）與 N 個各自手寫錯誤處理的呼叫端。差別只在規模。

### 子決策 4 的修訂理由

原決策的提問把選項限縮為「刪掉」或「保留不碰」，遺漏了第三條路。
盤點後發現 `create_tables()` 其實是 DDL 樣板的正確歸宿，而非誤導性死碼：

- 它有 `inspect_table_exists()` 前置檢查，兩支 `create_*.py` 沒有
- 它把 `SQLAlchemyError` 從一般例外中挑出來分流，兩支 `create_*.py` 沒有

**現行兩支的日誌有業務語意不精確的問題**：`CREATE TABLE IF NOT EXISTS`
在資料表已存在時不會報錯，但程式碼緊接著無條件印出
`Table 'x' created successfully.` —— 對除錯的人是誤導。
`create_tables()` 的存在性檢查能區分「已存在、略過」與「本次建立」。

因此修訂為：`create_tables()` 移除硬編碼 DDL、改收 `tables: dict[str, str]`，
兩支 `create_*.py` 保留 DDL 宣告並呼叫它。這與 loader 的瘦身完全同形。

### upsert 集中化（ADR-0002 原範圍，commit `c3e8103`）

```

        → upsert_to_table(df, table, update_columns, database)
    表名與 update_part 由硬編碼 `dim_accident_day` 改為參數
    新增空 update_columns 的前置檢查（避免組出語法錯誤的 SQL）

src/task/l_*.py  ×8
    56 行 → 20 行（l_fact_night_markets 62 → 33，多了 updated_on 時間戳）
```

### DDL 集中化（範圍擴張，commit `c3e8103`）

```
src/util/mysql_utils.py
    create_tables(engine)
        → create_tables(engine, tables: dict[str, str])
    移除硬編碼的 2 段 DDL（dim_event_day / fact_accident_main，
    且其欄位名 date / weekday 與現行綱要 accident_date / accident_weekday 不符）

src/task/create_traffic_accident_tables.py   173 行 → 137 行
    7 段 DDL 移至模組層 TRAFFIC_ACCIDENT_TABLES，函式體只剩一行呼叫
src/task/create_night_markets_tables.py       54 行 →  45 行
    1 段 DDL 移至模組層 NIGHT_MARKET_TABLES
```

**行為變化**：兩支建表任務現在會先檢查資料表是否存在。
已存在時記錄 `Table 'x' already exists, skipping.` 並跳過 DDL；
不存在時才執行並記錄 `created successfully`。
先前無論如何都記錄後者。

### 交易正確性（commit `18f0105`）

```
dags/d04_analysis_pedestrian_accidents.py
    read_sql() 於迴圈結束後補上 conn.commit()
```

該連線為 `autocommit=False`。mart SQL 目前幾乎全是 DDL，
靠 MySQL 對 DDL 的隱式提交才生效；唯一的 `UPDATE`
（`mart_monthly_pedestrian_death_injury.sql:72`）位於 `CREATE PROCEDURE` 內、
其後第 99 行的 `DROP TABLE` 觸發隱式提交。因此**目前沒有遺失資料**，
但只要日後 mart SQL 結尾出現純 DML 就會被靜默 rollback 且 task 仍為綠燈。

`conn.commit()` 置於 for 迴圈**之後**，維持原本「6 份 SQL 同屬一個事務、
全部成功才算數」的語意（原 `except` 也是整批 rollback）。
