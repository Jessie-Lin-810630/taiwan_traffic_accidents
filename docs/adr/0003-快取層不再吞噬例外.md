## 背景

`src/util/get_or_set_cache_from_redis.py` 的三個函式全部吞掉例外：

```python
def set_cache(key, value, ttl=864000) -> None:
    try:
        r = create_redis_client()
        r.setex(key, ttl, pickle.dumps(value))
        print(f"[Redis Saved] 已快取: {key}")
    except Exception as e:
        print(f"Redis 寫入失敗: {e}")     # 呼叫端完全不知情
```

由此衍生三個問題：

### 1. 呼叫端的例外處理是死碼

`c_data_service.py` 有 4 處這樣的區塊：

```python
try:
    set_cache(cache_key, result, ttl=43200)
except Exception as e:
    # 僅紀錄錯誤，不中斷流程
    print(f"資料已取得但Redis寫入失敗: {e}")
```

由於 `set_cache` 內部已把例外吞掉，**這些 `except` 永遠不會執行**。
註解寫著「僅紀錄錯誤」，但實際上連記錄都發生在 `set_cache` 內部。

### 2. 「快取未中」與「Redis 故障」無法區分

`get_cache` 失敗時回傳 `None`，快取未命中時也回傳 `None`。
`cal_accidents_nearby_nightmarket:284` 因此寫成：

```python
batch = get_cache(batch_key)
if not batch:
    return "讀取後發現無資料，無法計算附近事故"
```

Redis 全掛與批次本來就是空的，走的是同一條路徑。

### 3. `d06` 在資料庫全掛時仍然全綠

`c_data_service` 另有 4 處把 MySQL 故障吞成空 `DataFrame` 或空 list
（`:52`、`:157`、`:213`、`:262`），以及 `cal_accidents_nearby_nightmarket` 中
逐個夜市的 `except: continue`。

`dags/d06_precompute_to_redis` 的三個 task 全部呼叫這一層。
**MySQL 完全無法連線時，六個 task 依然成功，Redis 被寫入一批空結果，
前端安靜地顯示「查無資料」。** 監控完全失去意義。

---

## 決策

**快取層與資料服務層一律向上拋出例外；「要不要降級」由呼叫端各自決定。**

`d06`（預計算 DAG）與 Streamlit 前端是兩個真實的 adapter，需求相反 ——
前者要紅燈，後者要優雅降級。兩個 adapter 撐得起這個 seam。

### 四項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | `c_data_service` 不再回傳空 `DataFrame`／空 list 掩蓋故障，一律 `logger.error(..., exc_info=True)` 後 `raise` | 降級是呼叫端的政策，不是資料服務的職責。`d06` 需要失敗、前端需要提示，兩者無法用同一個回傳值表達 |
| 2 | 快取寫入失敗**依呼叫情境區分**：`d06` 預計算路徑失敗即 `raise`；前端 read-through 路徑僅 `logger.warning` | `d06` 的產出就是快取本身，寫不進去等於任務失敗。前端則是資料已取得，快取只是加速手段 |
| 3 | `cal_accidents_nearby_nightmarket` **保留逐個夜市跳過**，但累計失敗清單，迴圈結束後若有失敗即 `raise` | 兼顧「少數夜市查無資料不該中斷整批」與「大規模故障要紅燈」。單純 fail-fast 會讓一筆髒資料擋掉整批預計算 |
| 4 | 前端 `v_act1_all_accident.py` **納入本輪**，切換至 `redis_utils` 並加上降級處理 | 子決策 1 之後前端不改就會直接噴 traceback 給使用者；且前端是 `get_or_set_cache_from_redis` 最後的呼叫端 |

### 子決策 5：日誌職責 —— `exc_info` 只在邊界層

實作過程中發現子決策 1～4 會造成**同一個錯誤被多層各印一份 traceback**：
`redis_utils.set_cache` 已 `logger.error(..., exc_info=True)`，
`c_data_service` 捕捉後又印一次。

**規則：例外一律 `logger.error(...)` 後 `raise`；`exc_info=True` 只用在例外停止傳播之處。**

一句話判準：**有 `raise` 就不帶 `exc_info`，沒有 `raise` 才帶。**

| 層 | 寫法 | 理由 |
| --- | --- | --- |
| 內層 / 轉手層 | `logger.error("發生什麼")` + `raise` | 留下一行「在哪裡出事」，但不重複輸出 traceback |
| 邊界層（例外停止之處） | `logger.error("...", exc_info=True)`，不 `raise` | 這裡是最後一手，traceback 必須完整 |
| Airflow task | 不需自行記錄 | 例外傳出 task 時 Airflow 會自動輸出完整 traceback |
| Streamlit 前端 | 必須記錄 | `st.error()` 只給使用者看；不記錄的話 traceback 完全消失 |

**保留內層的 `try/except` 而非刪除。** 技術上「只 `log` 一行再 `raise`」的 try/except
確實可以拿掉（例外本來就會傳播），但保留它有維護價值：
它標示出「這裡預期會出錯」，讓後續維護者知道該在哪裡補處理。
曾一度全數刪除，實測後判定可讀性變差而還原。

此子決策**修訂 ADR-0001** 的日誌條文（原文為「一律
`logger.error(..., exc_info=True)` 後原樣 `raise`」）。
例外型別不轉換的核心決策不變，僅調整 `exc_info` 的使用時機。

### 連帶：切換至 `redis_utils`

`c_data_service` 與前端改為從 `src.util.redis_utils` 匯入 `get_cache` / `set_cache` /
`delete_cache`。新版本就是「一律 raise」的設計，另有連線池單例與
socket timeout（`socket_timeout=5`、`socket_connect_timeout=3`）。

## 後果

- `d06` 在 MySQL 或 Redis 故障時**會真的失敗**，Airflow 的 retry 與告警恢復作用。
- 「快取未中」（`get_cache` 回 `None`）與「Redis 故障」（拋 `RedisError`）語意分離。
- 刪除 4 處死碼 `except`。
- 前端故障時顯示明確訊息，而非空白圖表或 traceback。
- **`get_or_set_cache_from_redis.py` 的呼叫端歸零** —— 連同
  `create_db_engine_or_database.py` 與 `inspect_table_schema.py`，
  ADR-0001 決策 5 的凍結三檔終於可以整批刪除。

### 誠實的限制

子決策 3 的門檻設定（有任何失敗就 raise，而非「超過 N% 才 raise」）
是保守選擇。若日後發現部分夜市因資料本身缺漏而長期失敗，
會演變成每次執行都紅燈；屆時應改為比例門檻，而不是退回無條件 `continue`。

子決策 2 讓 `set_cache` 的失敗語意依呼叫點而異，
這個區分寫在呼叫端而非型別系統裡，靠的是註解與測試。
