## 名詞

| 詞 | 意思 | 在程式碼的哪裡 |
| --- | --- | --- |
| **目標表約束** | 事實表 DDL 上寫明的欄位限制，例如 `VARCHAR(30)` 的長度與 `DECIMAL(10,6)` 的精度 | `create_night_markets_tables.py` 的 `NIGHT_MARKET_TABLES` |
| **前置驗證** | 在送進資料庫之前，於 Python 端檢查資料列符不符合目標表約束 | 本文的決策內容 |
| **違規列** | 沒有通過前置驗證的資料列 | 本文的決策內容 |
| **DLQ** | dead letter queue，收容違規列的資料表，供事後人工稽核 | 本文新增的 `dlq_records` |
| **批次識別** | 用來分辨一筆 DLQ 紀錄來自哪一次 DAG 執行的字串 | Airflow 的 `run_id` |
| **違規比例** | DLQ 筆數 ÷（DLQ 筆數 + 正常寫入筆數），以資料列為單位 | 本文的門檻判準 |

## 背景

### 問題 1：目標表約束只存在於 MySQL，Python 端沒有任何一層知道

`fact_night_markets` 的 DDL 上有六個帶長度的字串欄位：

| 欄位 | 型別 |
| --- | --- |
| `nightmarket_name` | `VARCHAR(30)` |
| `region` | `VARCHAR(10)` |
| `zipcode` | `VARCHAR(10)` |
| `city` | `VARCHAR(10)` |
| `district` | `VARCHAR(10)` |
| `area_road` | `VARCHAR(50)` |
| `business_days_weekday` | `VARCHAR(10)` |
| `url_to_googlemap` | `VARCHAR(200)` |

`t_fact_night_markets.py` 的六支清洗函式沒有任何一支知道這些限制。清洗只處理格式，
例如把 Google 名稱裡的括號補述去掉、把地址拆成五個欄位，完全不看長度。
結果是約束的第一次生效時機在 MySQL，也就是資料已經送出去之後。

### 問題 2：一列違規會讓整批回滾

`upsert_to_table()` 用 `executemany()` 一次送出整批、單一 commit，寫入失敗就 rollback
後原樣往外拋。d05 的批次是 10 個夜市，而一個夜市會依營業日展開成大約 7 列，
所以一批進資料庫的是大約 70 列。這次的錯誤訊息 `at row 11` 指的是這一批的第 11 列。

也就是說，**一筆過長的名稱會讓 70 列合格資料一起寫不進去**。批次的原子性是放大器，
不是病因，但它讓單筆異常的影響範圍變得很大。

### 問題 3：ADR-0019 驗的是欄位存不存在，不是值合不合法

ADR-0019 已經在 `read_googlemap_responsed_json()` 加了一層驗證，檢查每個項目有沒有
`result`，以及 `result` 底下有沒有 `name`、`formatted_address`、`geometry`、
`opening_hours` 這四個必要欄位，缺欄比例超過 30% 就拋出。

那一層擋的是「Google API 改了 schema」。但它擋不到「欄位在但對 MySQL 來說欄位值卻不合法」，
這次的過長名稱的案例是屬於後者。

### 問題 4：違規的原始資料隨著回滾一起消失

**（實測）** 這次觸發錯誤的是 Google Maps 回傳的其中一筆夜市，批次內第 11 列。
完整的原始名稱**尚未取得**，因為該批已經回滾，資料沒有留存。
錯誤訊息只說得出「太長」，說不出它到底長什麼樣、長成那樣的原因是什麼。

要判斷這是清理規則有漏網之魚還是這個夜市真的叫這個名字，就需要看到原始值。
現在的做法讓這個判斷不可能做到。

## 決策

### 一、違反目標表約束的資料列剔除，不寫入事實表

違規列不進 `fact_night_markets`，改寫入 DLQ 等待人工判斷。

不採用「截斷後照樣寫入」，也不採用「放寬 DDL 的欄位長度」。
理由是同一個：**（判斷依據：業務判斷，非實測）** 夜市名稱超過 30 字違反華人圈的
命名習慣，所以出現這種值時，比較可能的解釋是清理規則有漏網之魚，
而不是這個夜市真的叫這個名字。而 `nightmarket_name` 會直接呈現在前端頁面上，
不論是截斷到 30 字還是放寬欄位長度，使用者看到的都是一個讀起來奇怪的名稱。
兩種做法都只是讓這個訊號安靜地流到前端，而不是處理它。

代價是那個夜市會從事實表消失。因為名稱是夜市層級的屬性，而一個夜市展開成大約 7 列，
所以一筆名稱違規會讓該夜市的全部營業日資料一起被剔除。前端在下一次成功寫入之前
看不到這個夜市。接受這個代價，因為呈現一個怪異且可能有錯誤的夜市名稱比少一個夜市更會影響前端使用體驗。

### 二、違規列寫入單一通用的 `dlq_records` 表

全專案共用一張 DLQ 表，不替每張事實表各建一張同構表。

| 欄位 | 型別 | 用途 |
| --- | --- | --- |
| `dlq_id` | `INT AUTO_INCREMENT PRIMARY KEY` | 流水號 |
| `source_table` | `VARCHAR(64) NOT NULL` | 這列本來要寫進哪張表 |
| `run_id` | `VARCHAR(255) NOT NULL` | Airflow 的 run 識別，可貼回 Airflow UI 搜尋 |
| `violations` | `JSON NOT NULL` | Pandera 的原始錯誤訊息，一列一筆，多個原因存成陣列 |
| `payload` | `JSON NOT NULL` | 違規那一列的完整內容 |
| `record_hash` | `CHAR(64) NOT NULL` | `payload` 的 sha256，唯一鍵的一部分 |
| `created_on` | `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | 寫入時間 |
| 唯一鍵 | `UNIQUE(source_table, run_id, record_hash)` | 見決策六 |

- 選單一通用表而不是同構表的理由：同構表會製造第三份需要同步的 schema 宣告，
事實表每加一個欄位，DLQ 表也要跟著加。用 `payload JSON` 存整列則完全不隨事實表演化，
而且未來 d01 到 d04、d07 到 d08 接上時不需要改任何 DDL。

- **DLQ 表的欄位不沿用事實表的型別限制。** 要存進 DLQ 的正好是那個 31 字的名稱，
若 DLQ 也宣告 `VARCHAR(30)`，寫 DLQ 會再觸發一次同樣的 `DataError`。
`payload` 用 `JSON` 型別，沒有這個問題。

- `record_hash` 存在的理由是 MySQL 的 JSON 欄位不能直接放進唯一索引，
需要一個固定長度的指紋代表 `payload` 的內容。

- 不加 `dag_id` 欄位。因為 `run_id` 已經能定位到是哪一次執行，`source_table` 已經能定位到
是哪一條管道，`dag_id` 是冗餘的。

- `violations` 存 Pandera 的原始錯誤訊息。

### 三、驗證涵蓋 DDL 讀得出來的約束，另加唯一鍵三欄的 not null 檢查

Pandera schema 的規則分成兩類。**第一類從 DDL 直接讀得出來**：

1. 每個 `VARCHAR(n)` 欄位的字串長度
2. 每個 `DECIMAL(p,s)` 欄位的數值範圍與小數位
3. 每個欄位的值能不能被 DDL 宣告的型別接受，涵蓋 `TIME`、`FLOAT`、`TIMESTAMP`

**第二類是 DDL 讀不出來、但仍要驗的**：

4. `latitude`、`longitude`、`business_days_weekday` 這三欄不得為 null

#### 第一類驗的是值，不是 pandas 的 dtype

第 3 項要特別講清楚，因為 Pandera 的型別檢查有兩種含意，用錯了等於沒驗。

**不是**斷言某一欄的 pandas dtype 是什麼。`business_hours_opening` 在 DataFrame 裡
是 `object` dtype 裝字串，斷言它是 `object` 什麼都攔不到。

**是**檢查值能不能被 MySQL 的目標型別接受：
`TIME` 欄位的值要符合 `HH:MM:SS` 且時分秒各自在合法範圍內，
`FLOAT` 欄位的值要能轉成浮點數，`TIMESTAMP` 欄位的值要符合 `YYYY-MM-DD HH:MM:SS`。
允許為 null 的欄位，null 一律視為通過。

#### 為什麼第一類是這個範圍?

這一輪要關閉的故障類別是「違反 DDL 約束造成整批回滾」，而 `DataError` 的來源
就是 DDL 約束。把 DDL 讀得出來的約束全部驗完，這個類別就完整關閉了。

型別必須納入，否則這個類別關不起來。**（實測程式碼）**
`_clean_business_datetime()` 產生 TIME 欄位的方式是純字串切片：

```python
return f"{t[:2]}:{t[2:]}:00"   # Google 給 "1630" 會變成 "16:30:00"
```

中間沒有任何驗證。Google 若回傳三碼的 `"930"` 會變成 `"93:0:00"`，
回傳 `"1670"` 會變成 `"16:70:00"`。這兩種值送進 `TIME` 欄位，在嚴格模式下會觸發
`error 1292 Incorrect time value`，**跟這次的 1406 是同一個故障類別，同樣整批回滾**。

#### 由 MySQL 自動賦值的欄位不放進 schema

`nightmarket_id` 由 `AUTO_INCREMENT` 產生，`created_on` 由
`DEFAULT CURRENT_TIMESTAMP` 產生。這兩欄的值不經過 ETL，**不可能出錯**，
也根本不在要寫入的 DataFrame 裡，所以不列入 Pandera schema。

判準是「這個值是誰給的」，不是「這個值出錯的機率高不高」。
依這個判準，`updated_on` **要**留在 schema 裡，因為它是
`l_fact_night_markets()` 用 `strftime()` 寫進去的，屬於 ETL 產生的值。

這份排除名單要寫成明文常數放在 `create_night_markets_tables.py`，
供決策四的同步測試使用。它不是第三份約束宣告，只是一份名單，
而且它本身就有文件價值：讀的人一眼就知道哪些欄位不是由 ETL 寫入的。

#### 為什麼要多加第二類?

那三欄正是 `uk_nm_latlonwkd` 這個唯一鍵的組成欄位，而**MySQL 的唯一索引不擋 NULL**。
只要座標是 null，這一列永遠不會跟任何一列衝突，`ON DUPLICATE KEY UPDATE` 對它無效，
**每跑一次 d05 就多插一列，沒有上限**。

所以這三欄的 not null 檢查不是資料完整性的偏好，而是**維持 upsert 冪等性的必要條件**。
它與決策六替 DLQ 表加唯一鍵要防的是同一件事。這條規則不需要新的業務論證，
只需要理解 MySQL 唯一索引對 NULL 的行為。

#### 為什麼不驗更多?

- 不驗值域規則（座標是否落在臺灣範圍、評分是否介於 0 到 5）。 \
  值域規則的每一條都需要新的業務論證，目前沒有長時間觀察所有欄位的值域分布，缺乏充足論證區分合法與不合法的業務資料。

- 不驗 UK欄位以外的 null、不驗跨欄位規則（結束時間是否晚於開始時間）。
  目前測試的是，d05 要寫入的 `fact_night_markets`，該表的地址四欄（`region`、`city`、`district`、`zipcode`）DDL 本身就不含 not null 檢查。何況 `_clean_night_market_address()` 在比對不到時
  填的是「無匹配縣市資訊」，所以加了也攔不到任何東西。

### 四、Pandera schema 與 DDL 放在同一個檔案，並加一支同步測試

Pandera schema 寫在 `create_night_markets_tables.py`，與 `NIGHT_MARKET_TABLES` 的
DDL 字串相鄰。理由是這兩份宣告描述的是同一件事，放在一起才能讓改動時彼此可見。

兩份宣告不同步是這個做法的主要風險，例如有人把 DDL 改成 `VARCHAR(50)`，
Pandera 還在擋 30 字，於是合法資料被丟進 DLQ 而且沒有任何測試會發現。
因此**加一支同步測試**：掃過 DDL 字串裡的每一個欄位宣告，
扣掉由 MySQL 自動賦值的那幾欄之後，斷言 Pandera schema 對每一欄都有對應的規則，
而且長度與精度的數字相等。這支測試擋得住「改錯數字」與「漏掉欄位」兩種情況。

**這支測試的涵蓋範圍就是決策三的第一類，不多也不少。** 具體來說：

| 對象 | 測試會不會檢查 | 原因 |
| --- | --- | --- |
| DDL 的 `VARCHAR(n)` 長度 | 會 | 決策三第一類第 1 項 |
| DDL 的 `DECIMAL(p,s)` 精度 | 會 | 決策三第一類第 2 項 |
| DDL 的 `TIME`、`FLOAT`、`TIMESTAMP` 型別 | 會 | 決策三第一類第 3 項 |
| `nightmarket_id`、`created_on` 這兩欄 | 不會 | 由 MySQL 自動賦值，在排除名單內 |
| DDL 的 `PRIMARY KEY` 與 `UNIQUE` | 不會 | 這兩者是跨列的約束，Pandera 驗不了跨批次的唯一性 |
| Pandera 的三欄非空規則 | 不會 | 決策三第二類，DDL 裡沒有對應宣告 |

所以這支測試**不是**「DDL 與 Pandera schema 完全等價」的保證。
它保證的是：**DDL 上每一個由 ETL 寫入的欄位，Pandera 都有對應的規則，
而且長度與精度的數字一致。**

兩個涵蓋不到的地方要講明。第一，`PRIMARY KEY` 與 `UNIQUE` 是跨列的約束，
Pandera 驗的是單一批次的 DataFrame，本來就表達不了跨批次的唯一性，
這件事由資料庫負責。第二，**三欄非空的規則與資料表之間沒有任何機制維持一致**，
因為 DDL 裡沒有這個宣告，這是選擇不改 DDL 的代價，
處理方式列入未納入本次範圍第 2 項。

CI 的 test job 是部署的前置條件（ADR-0017），所以這支測試會在部署前擋下不同步。

### 五、驗證與分流放在 load 階段

驗證與分流的執行寫在 `l_fact_night_markets.py`。

理由是驗證的內容是「這列符不符合目標表的約束」，那是 load 階段的知識。
`t_` 階段知道「Google 的括號補述要拿掉」，但它沒有理由知道 `nightmarket_name`
是 `VARCHAR(30)`。此外寫入 DLQ 本身也是一種載入，只是寫的不是正確的業務資料。

`l_fact_night_markets()` 因此從單純的寫入函式，變成「驗證、分流、分別寫入兩張表」。
它的回傳值從 `None` 改為（正常寫入筆數, DLQ 筆數）。

`dlq_records` 的建表加進 `NIGHT_MARKET_TABLES` 字典，由既有的第一個 task
`task_crx_nm_table` 一併建立，不新增 task，不改 DAG 相依。

### 六、DLQ 的寫入走既有的 `upsert_to_table()`，以唯一鍵達成冪等

DLQ 的寫入不另外寫 SQL，沿用 ADR-0002 立下的單一寫入入口。
唯一鍵是 `UNIQUE(source_table, run_id, record_hash)`，衝突時更新 `violations`
與 `created_on`。

這樣做是為了處理重試造成的重複。`task_t_and_l_night_markets` 若在第 30 批因為
資料庫連線中斷而失敗，Airflow 會重試整個 task，前 29 批的 DLQ 紀錄會被再寫一次。
打開 DLQ 表看到同一個夜市出現兩次，卻分不清是這個異常真的發生兩次，
還是重試造成的。**重複紀錄正好打在 DLQ 唯一的價值上，也就是判斷發生了什麼事。**

不採用「task 開頭先刪掉同一次執行的舊紀錄」，因為那會引入一個破壞性操作，
而且若 task 在刪除之後、寫入之前被中斷，新舊紀錄會同時消失。
不採用「把 task 的 retries 設成 0」，因為 VM 是 preemptible，暫時性故障是常態，
關掉重試等於讓每一次網路抖動都需要人工介入。

### 七、批次識別使用 Airflow 的 `run_id`，由呼叫端傳入

`run_id` 由 `dags/d05_track_night_markets.py` 從 task context 取出，
經 `t_fact_night_markets()` 傳到 `l_fact_night_markets()`，型別是 `str`。

參數型別定成 `str` 之後，地端測試可以直接傳一個自訂字串，pytest 也一樣。

不使用 `logical_date`。**（實證，Airflow 3.0 RELEASE_NOTES）**
「For runs triggered by assets or the API without a specified date,
the `logical_date` defaults to None」，也就是經 API 或 UI 手動觸發而沒有指定日期時，
`logical_date` 會是 `None`。但是 MySQL 的唯一索引不會擋 NULL，所以批次識別一旦是 NULL，
決策六的冪等性會失效，改用 `run_id` 永遠有值且保證該 DAG run 的唯一性，Airflow 自動重試 DAG run 時 `run_id` 不變。唯有在手動重新觸發同一個月份的 DAG 時會產生新的 `run_id`，造成 DLQ 會多一組紀錄而不是覆蓋。


### 八、整體品質以違規比例把關，由獨立的下游 task 判斷

新增一個下游 task，按以下公式計算違規比例並在超過 30% 時記 `error` 後拋 `ValueError`。

```
違規比例 = DLQ 筆數 ÷（DLQ 筆數 + 正常寫入筆數）
```

**公式說明:**
- 分母 (DLQ 筆數 + 正常寫入筆數) 是整次任務執行的全部資料列，不是任務中 for-loop 的單一批次。
- 兩個數字由 `task_t_and_l_night_markets` 跨批次累加後經 XCom 傳給下游 task 用。
- 門檻定在 30% 是沿用 ADR-0019 的做法，**沒有統計依據**，是拍板出來的數字。

**這個 task 的 `retries` 設為 0。** 上游的失敗（資料庫連線中斷、檔案讀不到）
值得重試，但「這次資料有 35% 不合格」是重試一百次也一樣的結論。此外，依 ADR-0006 第 5 條，
不會被重試的失敗會被記為 `error`；依 ADR-0001，不轉換成 `AirflowException`；
依 ADR-0003 第 3 條，有 `raise` 就不帶 `exc_info=True`。

- 不採用「一有違規就拋出」，那會讓 DLQ 失去意義，因為管道還是跑不完。
- 不採用「一律不拋出」，因為 Google 若改動回應格式導致全部夜市都驗不過，
DLQ 會塞進幾千列而 Airflow 一片綠燈，要等到前端沒資料或是特地去查 DLQ 才會發現。


### 九、本次執行範圍只有 d05

本文的主張適用於全部事實表的載入，但這一輪只改 d05。
d01 到 d04 與 d07 到 d08 的接入列為後續候選。

理由是先在一條管道上驗證這套做法可行，再決定其他管道要不要照抄。
DLQ 表本身是通用的，其他管道接入時不需要改 DDL。

## 後果

### 正面

- 單筆不合格的資料不再讓整批合格資料寫不進去
- 不合格的資料列被留存下來，可以查出它到底長什麼樣，而不是隨著回滾一起消失
- 目標表約束第一次有了 Python 端的明文宣告，而不是靠 MySQL 的 DDL 核對
- 座標為 null 導致唯一鍵失效、每次執行重複插入的問題被擋下來（決策三第二類規則）
- DLQ 表是通用的，其他五條管道接入時不需要新增資料表

### 負面

- 約束變成兩份宣告，DDL 一份、Pandera 一份，靠放在同一個檔案與一支同步測試維持一致
- 三欄 not null 的規則只存在於 Pandera，DDL 沒有對應宣告，同步測試涵蓋不到。
  資料庫層完全沒有防線，繞過 d05 直接寫入的資料不受任何約束
- 門檻 30% 沒有統計依據
- `t_fact_night_markets()` 與 `l_fact_night_markets()` 的簽章都要改，
  各多一個 `run_id` 參數並改成回傳計數
- 引入 `pandera` 這個新依賴

### 中性

- 違規比例的判斷發生在全部批次寫完之後，所以拋出時資料庫已經寫了一部分。
  這在 ADR-0015 選擇逐批 commit 時就是既成事實，upsert 是冪等的，重跑安全
- 手動觸發時 DLQ 會累積而非覆蓋，見決策七

## 未納入本次範圍

1. **值域規則、其他欄位的 null 檢查與跨欄位規則**（決策三的代價）。
   例如座標是否落在臺灣範圍、評分是否介於 0 到 5、
   `business_days_weekday` 是否限於七個值、地址四欄是否為「無匹配縣市資訊」
   這類說明字串、結束時間是否晚於開始時間。
   這些需要各自的業務論證，等 DLQ 累積一段時間的真實資料後再判斷哪些值得加。

2. **把三欄的 `NOT NULL` 補進 DDL 並在既有資料表上執行 `ALTER TABLE`**（決策三與四的代價）。
   做了之後 DDL 會恢復成唯一真實來源，同步測試能涵蓋全部規則，
   而且資料庫層本身也有防線。

   這一輪不做的理由有兩個。第一，`create_tables()` 對已存在的資料表直接跳過，
   所以改 DDL 字串對 VM 上那張表完全沒有作用，必須手動執行 `ALTER TABLE`。
   第二，**VM 上現在有沒有座標為 null 的資料列尚未查證**，若有，
   `ALTER TABLE` 的行為要看 MySQL 的 `sql_mode`，在非嚴格模式下 MySQL 會把既有的
   null 靜默轉成 `0`，結果是幾個座標落在幾內亞灣的夜市，而且不會有錯誤訊息。

   所以這件事的正確順序是：先查既有資料、確認 `sql_mode`、必要時先清資料，
   再執行 `ALTER TABLE`。那是一輪獨立的工作。
   這個專案沒有 migration 工具，`ALTER TABLE` 是一次性的手動操作。

3. **d01 到 d04 與 d07 到 d08 的接入**（決策九）。

4. **d05 失敗時擋下 d06**。`d06_precompute_to_redis` 是純時間排程，
   與 d05 之間沒有跨 DAG 相依。d05 的 gate 失敗時部分資料已經寫進事實表，
   隔天 d06 照常跑，會把不完整的夜市資料算進 Redis。
   **這個風險在本次改動之前就存在**，因為以前 d05 因 `DataError` 失敗時 d06 一樣照跑。
   不在這一輪處理，理由是兩者的排程週期對不上，d05 每月一次而 d06 每五天一次，
   要處理「d06 這次該等哪一次 d05」的時間對齊，那是另一個需要獨立決策的題目。

5. **從 DDL 自動推導 Pandera schema**（決策四）。等到需要驗證的事實表達到一定數量，
   手工維護的重複成本超過解析器的複雜度時再考慮。

6. **DLQ 的處理流程**。本文只決定違規列怎麼被留下來，
   沒有決定人工稽核後怎麼把修正過的資料補回事實表。目前預期是在 DBMS 上手動處理。
