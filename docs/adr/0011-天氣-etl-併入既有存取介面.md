## 名詞

| 詞 | 意思 | 在程式碼的哪裡 |
| --- | --- | --- |
| **存取面** | 一個外部資源（MySQL、GCS、HTTP API）在專案中的唯一進入點 | `src/util/mysql_utils.py` 是 MySQL 的存取面 |
| **第二套存取面** | 同一個外部資源出現第二組互不相通的連線／查詢函式 | 本文要消滅的東西 |
| **天氣 pipeline** | OpenMeteo API → GCS Parquet → MySQL `fact_hourly_weather` 的這條線 | 上列 8 支檔案 |

## 背景

這 8 支檔案是另一條開發線帶進來的天氣觀測 ETL，功能完整、已在 GCP VM 上跑過。
但它成形於 ADR-0001～0010 這一系列重構之外，因此完全沒有走既有的介面：
自建 Engine、自組 UPSERT、自寫例外轉換、自己開 connection 執行 DDL。

最直接的症狀是 `src/util/` 裡出現了**兩個同名函式**：

| | `src/util/get_table_from_mysql_gcp.py` | `src/util/mysql_utils.py` |
| --- | --- | --- |
| 函式名 | `get_table_from_sqlserver` | `get_table_from_sqlserver` |
| 簽章 | `(dql_str, *, database=None)` | `(dql_str, params=None, *, database=None)` |
| 取 Engine | `get_engine_sqlalchemy()` — 每次新建 | `get_engine_to_mysql()` — 以 database 為鍵快取 |
| bind parameter | 不支援 | 支援 |
| 憑證檢查 | 無 | `_require_credentials()` |

讀者必須回頭看 import 行，才知道某個呼叫用的是哪一個。

### 病灶：連線池從未被服務第二個請求

ADR-0004 已經論證過這件事，這裡只記錄它在天氣 pipeline 的重演位置。
`create_engine_conn_tomysql.get_engine_sqlalchemy()` 每次呼叫都 `create_engine(...)`，
而 `l_transform_and_load_to_mysql()` 在**分批迴圈裡**逐批呼叫查詢與建表 ——
一次 DAG run 會生出數十個各帶 5 條連線的池，`pool_size` / `pool_recycle` / `pool_pre_ping`
三個設定全部形同虛設，正是 ADR-0004 定義的病因。

### 一併帶進來的三個規範外事物

- `CHARSET` 環境變數 —— 會成為專案的第 16 個環境變數，`CLAUDE.md` 與 `.env.example` 都沒有它
- `MYSQL_HOST` 預設值 `"mysql8"` —— 既有 `mysql_utils` 是 `"localhost"`，同一個變數兩種預設
- `writer`（`AIRFLOW_ADMIN_EMAIL`）—— 被 import 但全專案零使用

以及一個缺席：沒有 `_require_credentials()`，缺 `MYSQL_USER` 時連線字串會變成
`mysql+pymysql://None:None@...`，MySQL 回覆「認證失敗」，排查方向被帶往帳號權限 ——
ADR-0008 要修的就是這個。

## 決策

**天氣 pipeline 不保留任何自有的資源存取實作，一律改走既有介面。**

分成六個候選，各自獨立可驗證、各自一個 commit：

| 候選 | 決策 | 主要引用 |
| --- | --- | --- |
| 1 | 刪除 `create_engine_conn_tomysql.py` 與 `get_table_from_mysql_gcp.py`，呼叫端改用 `mysql_utils` | ADR-0004、ADR-0008 |
| 2 | 天氣 DDL 改走 `src/task/create_*_tables.py` 的宣告樣板 + `create_tables()` | ADR-0002 |
| 3 | `request_weather_api.py` 內化進 `e_*.py`，套 `@retry_on_transient`，移除 `AirflowException` | ADR-0001、ADR-0006 |
| 4 | 拆開 `l_load_to_mysql_gcp.py` 的 E/T/L 糾纏，寫入改走 `upsert_to_table()` | ADR-0002、0003、0005、0009 |
| 5 | GCS 存取獨立成 `src/util/gcs_utils.py`，改用 `google-cloud-storage` 原生 client | ADR-0001 |
| 6 | `@task` 裝飾器從 `src/task/` 搬回 DAG 層 | ADR-0001 |

### 候選 5 選擇原生 client 而非包裝 GCSHook

三個選項評估過：(A) 包 `GCSHook`、(B) 改用 `google-cloud-storage`、(C) 維持現狀。

**採 B。** 理由是 ADR-0001 的護欄不能為了一個新資源就開例外 ——
`src/util/` 全部工具與 `src/task/` 全部模組可在無 Airflow 環境被匯入，
是由 `test/unit_test/test_util_logger_crtx.py` 實際把關的斷言，不是慣例。
選 A 會讓 `src/util/` 出現第一個依賴 Airflow 的模組，護欄必須開白名單，
而白名單一旦開了，下一個資源沒有理由不比照。

代價明確記錄於此：認證方式從 Airflow Connection（`google_cloud_default`）
改為 VM 的 service account，需新增 `google-cloud-storage` 依賴並確認 VM 權限設定。

### 附帶發現：依賴宣告與實際不符

`apache-airflow-providers-google` **不在 `pyproject.toml` 也不在 `requirements.txt`**，
它只是 `apache/airflow` 官方 image 碰巧內建。因此這 8 支檔案在地端 poetry 環境
完全無法匯入 —— 這也是為什麼 ADR-0001 的兩個護欄測試在納管當下就轉紅。

候選 5 採 B 之後，這個不一致會自然消失（改依賴 `google-cloud-storage`，
而它會被正式寫進 `pyproject.toml`）。

## 後果

### 正面

- MySQL 存取回到單一存取面，ADR-0002／0004／0008 的既有測試自動涵蓋天氣 pipeline
- 天氣 pipeline 免費取得 Engine 快取、憑證驗證、`close_quietly()`、bind parameter
- 候選 5 完成後，ADR-0001 的「零例外」得以維持，`src/util/` 不需要白名單

### 負面

- 候選 5 的認證方式變更需要在 VM 上實際驗證，無法只靠地端測試確認
- 天氣 pipeline 的 DAG 需重新在 Airflow UI parse 過，`weather_api_pool` 的設定要跟著搬

### 中性

- 候選 1 移除了「`database=None` 時回退到 `MYSQL_DATABASE`」的分支。
  該分支在實際呼叫路徑上是死碼（d07／d08 一律傳入明確的資料庫名），
  且專案慣例是由 DAG 以 `os.getenv("MYSQL_DATABASE")` 解析後往下傳（見 `d02`）。
  改動後 `None` 的語意與 `mysql_utils` 一致：不指定資料庫。
