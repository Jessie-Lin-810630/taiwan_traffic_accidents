## 一、病因定義

> **查詢被寫在逐夜市迴圈裡面，所以服務一個批次要跑 30 趟；
> 但這 30 趟問的是同一張表，而且內容大量重疊。**

改動前的結構與六個問題的位置：

```python
def cal_accidents_nearby_nightmarket(batch_key, radius_m_list=[3000], year_targets=["all_sample"]):
#                                                ↑ 問題 5：可變預設值，且 year_targets 標 list[int] 卻裝 str
    batch = get_cache(batch_key)                              # 30 個夜市

    for a_nightmarket in batch:                               # ══ 逐夜市迴圈：30 圈 ══
        query = f"... WHERE latitude BETWEEN {nm_lat - 0.027} ..."
#                    ↑ 問題 3：座標 f-string 內插，params dict 建了卻沒往下傳
        df = get_accident_table_pedestrian_involved_in(query)
#            ↑ 問題 1：粗篩的查詢在迴圈「裡面」→ 一批 30 趟
#            ↑ 問題 2：這張表是「用查詢結果直接建表」生出來的、沒有索引 → 每趟都是全表掃描

        set_cache(契約 key, df)                                # 粗篩寫入

        for r_m, y_target in itertools.product(radius_m_list, year_targets):
#       ══ 細篩迴圈：巢狀在逐夜市迴圈「裡面」，預設參數下只跑 1 圈 ══
            set_cache(f"...{r_km}_{y_target}", df[mask])
#            ↑ 問題 4：預設參數下這把 key 與資料跟粗篩寫入完全相同 → 每個夜市白寫一次

        time.sleep(0.05)                                      # ← 問題 6：對自家 MySQL 節流
```

判準有三個：**迴圈裡有查詢**（來回次數隨圈數線性成長）、**相鄰圈次的結果重疊**
（同一批列被傳回好幾次）、**粒度錯配養出來的附屬程式碼**（逐圈節流、逐圈容錯、
逐圈重複寫入，在粒度修正後全部失去存在理由）。問題 1、2 屬第一項，
問題 3～6 屬第三項。

### 重疊有多嚴重

| | 士林夜市 | 寧夏夜市 |
| --- | --- | --- |
| 中心點 | (25.0878, 121.5240) | (25.0570, 121.5150) |
| 相距 | 約 3.54 公里 | |
| ±3 公里方框 | 6.0 km × 5.46 km | 同左 |
| 兩框重疊面積 | **約 36%** | |

落在重疊區的事故，第 1 趟為士林撈一次、第 2 趟為寧夏又撈一次。
同一都會區的鄰居都是這種關係。

### 問題 4 的證明：細篩那一圈是白做的

唯一的呼叫端（`dags/d06_precompute_to_redis.py:43`）只傳 `batch_key`，
所以 `itertools.product([3000], ["all_sample"])` 只產出一組，細篩迴圈只跑 1 圈。那一圈：

```
key：   粗篩寫的是 ..._3.0_all_sample，細篩那圈組出來的也是 ..._3.0_all_sample
範圍：  (3000 / 1000) / 111  ==  3.0 / 111       # 同一個 float
邊界：  SQL BETWEEN          ==  Series.between  # 都是閉區間
```

數值轉型又在粗篩寫入之前就做完了，所以細篩那圈的 `df[mask]` 就是 `df` 本身。
**同一把 key、同一份資料，寫了兩次。**

## 二、決策摘要

| # | 決策 | 狀態 |
| --- | --- | --- |
| 1 | 病因＝查詢粒度與使用粒度不一致，範圍是整支函式 | 依原案 |
| 2 | 查詢粒度提升到批次（一批一趟），DAG 不動 | 依原案 |
| 3 | `WHERE` 用 30 個框的 OR 聯集，座標全走綁定參數 | 依原案 |
| 4 | 保留 `radius_m_list` / `year_targets`，修可變預設值與型別標註 | **grilling 中翻案** |
| 5 | 粗篩寫入維持無條件執行，細篩迴圈跳過同名 key | 依原案 |
| 6 | 移除 `failed_markets`，查詢失敗即整批失敗 | 依原案 |
| 7 | 刪除 `time.sleep(0.05)` | 依原案 |
| 8 | 等價性這樣證明：把改動前的篩選邏輯抄一份，餵同一份輸入給新舊兩邊，比對輸出是否逐列相同 | 依原案，且資料齊全後補做了真實資料版（第四章） |

### 翻案的一項

子決策 4 原案是「刪掉細篩迴圈與那兩個參數」，deletion test 表面上過關
（沒有呼叫端傳過非預設值）。使用者選擇保留，理由是多半徑／分年度的預計算
是可預見的需求。代價由子決策 5 承擔：保留參數就必須處理問題 4，
多了一行 `if cache_key_per_product == cache_key_rough: continue`。
換來的是那組參數仍然可用，而且現在有測試釘住它真的可用。

## 三、實際改動

改動全部集中在 `src/task/core/c_data_service.py`，一句話說完：
**把粗篩的查詢從逐夜市迴圈裡面搬到外面，並讓那一句 SQL 一次涵蓋整批的 30 個框。**

### 1. 新增一個 seam：`_build_batch_bbox_query()`（`:347`）

```python
def _build_batch_bbox_query(batch, radius_km=ROUGH_RADIUS_KM) -> tuple[str, dict]:
    offset = radius_km / 111
    for i, a_nightmarket in enumerate(batch):
        params[f"min_lat_{i}"] = nm_lat - offset      # 每個夜市貢獻 4 個綁定參數
        ...
        clauses.append(
            f"(latitude BETWEEN :min_lat_{i} AND :max_lat_{i}"
            f" AND longitude BETWEEN :min_lon_{i} AND :max_lon_{i})"
        )
    return "SELECT * FROM analysis_... WHERE " + " OR ".join(clauses), params
```

組出來的 SQL（30 個夜市就 30 個括號）：

```sql
SELECT * FROM analysis_pesdestrian_involving_accident
 WHERE (latitude BETWEEN :min_lat_0 AND :max_lat_0 AND longitude BETWEEN :min_lon_0 AND :max_lon_0)
    OR (latitude BETWEEN :min_lat_1 AND :max_lat_1 AND longitude BETWEEN :min_lon_1 AND :max_lon_1)
    OR ...
```

把「SQL 怎麼組」從「結果怎麼切」分出來，是這輪唯一新增的介面。
它是純函式、沒有 I/O，所以 SQL 的正確性可以被直接測到。

### 2. 查詢從迴圈裡面搬到外面（`:408`）

```python
# ── 改動前：查詢在逐夜市迴圈「裡面」，30 圈 = 30 趟 ──
for a_nightmarket in batch:
    query = f"... WHERE latitude BETWEEN {params['min_lat']} AND ..."
    df_nearby_accidents = get_accident_table_pedestrian_involved_in(query)
    df_nearby_accidents = df_nearby_accidents[valid_cols]
    ...數值轉型...                       # 每圈各做一次

# ── 改動後：查詢在迴圈「外面」，整批 1 趟 ──
query, params = _build_batch_bbox_query(batch)
df_batch = get_accident_table_pedestrian_involved_in(query, params)
df_batch = df_batch[valid_cols].copy()
...數值轉型...                           # 整批只做一次

for a_nightmarket in batch:              # 逐夜市迴圈還在，但裡面不再有查詢
    df_nearby_accidents = df_batch[該夜市的框].reset_index(drop=True)
```

`reset_index(drop=True)` 是等價性的關鍵：改動前每個夜市的快取內容是一趟 SQL
查詢的結果，索引是 `0..n-1`；改動後是批次結果的切片，索引不連續。
不還原索引，快取內容就不是逐列相同。

### 3. 細篩迴圈：位置不變，加一道跳過（`:443`）

```python
for r_m, y_target in itertools.product(radius_m_list, year_targets):
    cache_key_per_product = f"traffic:nearby_v12:{nm_lat:.4f}_{nm_lon:.4f}_{r_km:.1f}_{y_target}"
    if cache_key_per_product == cache_key_rough:   # ← 新增：預設參數下就是這一圈
        continue
```

細篩迴圈仍然巢狀在逐夜市迴圈裡（子決策 4 保留了它）。
差別只在：預設參數下它唯一那圈會被跳過，不再重寫粗篩剛寫過的 key。

### 4. 隨查詢一起移出去的三樣東西

| 移除 | 原因 |
| --- | --- |
| `failed_markets` + 逐夜市 `try/except` | 迴圈裡已經沒有會失敗的 I/O。`set_cache` 失敗依 ADR-0003 子決策 2 本來就在 `try` 之外、直接 `raise` |
| `time.sleep(0.05)` | 節流的對象（迴圈裡的查詢來回）不存在了。`import time` 一併移除 |
| 細篩迴圈的重複寫入 | 見第一章問題 4 |

### 語意變化摘要

| 情境 | 改動前 | 改動後 |
| --- | --- | --- |
| 一個批次的查詢來回 | 30 趟 | 1 趟 |
| 座標進 SQL 的方式 | f-string 內插 | 綁定參數 |
| 查詢失敗 | 記進 `failed_markets`，迴圈跑完才 `RuntimeError` | 立刻原樣傳播 |
| 預設參數下每個夜市的 Redis 寫入 | 2 次（同 key、同資料） | 1 次 |
| 每個夜市的空等 | 0.05 秒 | 0 |
| 契約 key | 由粗篩寫入 | 不變（仍無條件寫入） |

### ADR-0003 子決策 3 的適用範圍

**規則本身不變**：「逐個失敗僅跳過、累計後判定」仍是專案通則。
變的是它在這支函式裡的**前提消失了** —— 那個會失敗的逐夜市查詢已經不在迴圈裡。
保留一個只能捕捉 pandas 框選例外的 `try/except`，是為不可能的情境寫錯誤處理。

## 五、實測：推論 vs 現實

在本機容器上跑完 d01～d06、資料齊全後量測。**環境是 Docker Desktop（10.44 GiB），
不是 GCP VM**，絕對值不能直接外推到生產。

### 規模

| | |
| --- | --- |
| `analysis_pesdestrian_involving_accident`（本輪查的那張） | **106,266 列**，**索引數 0** |
| `fact_accident_main` | 2,135,660 列 |
| `fact_night_markets` | 907 列 → 去重後 **348** 個座標 → **12 個批次** |

### 一個批次的查詢成本（30 個真實夜市，三次取最快）

| | 查詢耗時 | 傳回列數 |
| --- | --- | --- |
| 改動前（30 趟） | **1.554 秒** | 82,513 |
| 改動後（1 趟） | **0.316 秒** | 26,155 |

**加速 4.9 倍，傳輸列數少 68%。** 12 個批次合計省約 14.9 秒。

### 省的是掃描還是傳輸

把 `SELECT *` 換成 `SELECT COUNT(*)`（一樣掃描、只回 1 列），兩者相減即傳輸成本：

| | 只掃描 | 掃描＋傳輸 | 傳輸部分 |
| --- | --- | --- | --- |
| 改動前（30 趟） | 0.629 秒 | 1.554 秒 | 0.925 秒 |
| 改動後（1 趟） | 0.150 秒 | 0.316 秒 | 0.166 秒 |

**掃描省 39%，傳輸省 61%。** 主要收益是「不再重複傳輸重疊區的列」。

### 批次愈大，聯集愈划算

總比對次數其實兩邊相同（`N 句 × 106,266 列 × 1 框` vs `1 句 × 106,266 列 × N 框`）。
聯集省下的是 **N−1 次「開一句查詢」的固定開銷**，所以 N 愈大優勢愈大：

| 批次大小 | 逐夜市 N 趟 | 聯集 1 趟 | 倍數 |
| --- | --- | --- | --- |
| 10 | 0.525 秒 | 0.168 秒 | 3.1× |
| 30（現行） | 1.551 秒 | 0.313 秒 | 4.9× |
| 100 | 4.990 秒 | 0.708 秒 | 7.0× |
| 348（全台） | 16.895 秒 | **1.334 秒** | **12.7×** |

### 記憶體

| | 批次 30（現行） | 全台 348 |
| --- | --- | --- |
| `SELECT *` 全欄位 DataFrame | 33.3 MB | 116.3 MB |
| 裁成 17 欄後 | 19.3 MB | 67.6 MB |
| 單一 process 峰值（`:413` 裁欄位時新舊並存） | 52.6 MB | 184 MB |
| **容器內同時占用**（12 個並行 × 52.6 MB） | **≈ 631 MB** | ≈ 184 MB |

並行是查證過的：`parallelism=32`、`max_active_tasks_per_dag=16`，
12 個 map index 全部在 0.4 秒內啟動。631 MB 是由「單 process 峰值 × 12」推算，
非直接量測。


### 推論 vs 實測

| 改動前的推論 | 實測 |
| --- | --- |
| 「約 300 趟 → 約 10 趟」 | 348 趟 → 12 趟 |
| 收益主要來自「少掃很多次」 | 掃描只占 39%，**傳輸占 61%** |
| `time.sleep(0.05)` 是附屬症狀（子決策 7） | A/B 實測：含 sleep 38.52 秒 vs 不含 18.07 秒，**它一個人就占了舊版總時間的 53%** |
| 否決「全台只查一趟」，理由是失敗影響面擴大 | 該理由成立。但查詢上它快 2.8 倍（1.334 vs 12×0.313）、記憶體省 3.4 倍 —— **失敗隔離是它唯一輸的地方，也是唯一該用來決策的地方** |

### Redis 寫入的成本

payload 用真實的 30 份粗篩切片（中位 3,060 列 / 714 KB，一批合計 18.9 MB）：

| 30 次寫入 | 總耗時 | 單次 |
| --- | --- | --- |
| 現況 `set_cache()` | **0.205 秒** | **6.8 ms** |
| 精簡版（共用 client、不 `ping`、不 logger） | 0.197 秒 | 6.6 ms |
| pipeline（30 次一起送） | 0.162 秒 | 5.4 ms |

成分：`pickle.dumps` 39.4%、`setex` 送出 55.7%、
`create_redis_client()`（含每次都做的 `ping`）3.2%、其餘 1.7%。

兩點值得記下：**每次 `set_cache` 都重跑一次 `create_redis_client()` 的 `ping`
只占 3.2%**（0.23 ms/次），不是問題；**pipeline 只省 21%**，
因為成本由 payload 大小主導而非來回次數 —— 18.9 MB 就是得送過去。

### 一個 task 的成本結算

| | |
| --- | --- |
| 查詢 + pandas | 0.26 秒 |
| 30 次 Redis 寫入 | 0.20 秒 |
| **函式本身合計** | **約 0.5 秒** |
| Airflow 觀測到的 task | 1.97～4.08 秒 |
| **無法歸屬的部分** | **約 1.5～3.6 秒** |

**那 1.5～3.6 秒沒有查。** 合理的候選是 mapped task 各自 spawn process
所需的 import 與連線建立（A/B 是熱連線、單一 process 連續跑），
以及 Airflow 自身的 heartbeat 與 metadata 寫入 —— 但這是推測，不是測量。

### 未量測

- **上述那 1.5～3.6 秒的歸屬。**
- **舊版在 Airflow 容器內、12 個並行下的 task duration。**
  A/B 是在本機單執行緒跑的；容器內的絕對值會受並行競爭影響。

## 六、同病因但尚未修復的位置

### A. 同一病因、下一輪的候選

`aggregate_national_master()` 是同一個病因的 Redis 版本 —— 迴圈裡有 I/O：

| 位置 | 現象 |
| --- | --- |
| `:477` `for nm_key in batch_keys` → `get_cache()` | 12 趟 |
| `:485` `for nm in all_night_markets` → `get_cache()` | 348 趟讀取 |
| `:576` `for m_name, m_df in market_groups` → `set_cache()` | 323 趟寫入 |

解法是 Redis 的 `MGET`（一次送多把 key、一次拿回多個值）與 pipeline
（指令一條條發但不等每條回覆，全部送完再一次收），與本輪改寫 SQL 的手法無關。

### B. 刻意未處理

| 位置 | 現象 | 理由 |
| --- | --- | --- |
| `analysis_pesdestrian_involving_accident` 無索引 | 仍是全表掃描，只是從 348 次變 12 次 | 屬於 mart 層的 table swap 流程。實測顯示掃描只占省下時間的 39%，索引最多只能省掉那一半 |
| `SELECT *` 未改為明列欄位 | 欄位裁剪仍在 Python 端（`valid_cols`） | 下推到 SQL 會把「欄位不存在就跳過」的容錯變成硬失敗 |
| `radius_m_list` / `year_targets` 仍無呼叫端 | 現在是正確的（不可變預設、型別對、有測試），但依然沒有人用 | 使用者決定保留 |
