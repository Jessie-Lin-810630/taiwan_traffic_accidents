- 日期：2026-08-05
- 狀態：已採納（**尚未實作**）
- 範圍：`src/task/e_crawling_weather.py`、`src/task/l_fact_hourly_weather.py`、
  `dags/d07_track_recent_weather.py`、`dags/d08_track_hist_weather.py`
- 相關：[ADR-0009 預計算的查詢粒度以批次為單位](./0009-預計算的查詢粒度以批次為單位.md)（同樣是「粒度要一致」）、
  [ADR-0012 氣象網格精度](./0012-氣象網格精度.md)、
  [ADR-0003 快取層不再吞噬例外](./0003-快取層不再吞噬例外.md)
- 來源：[ADR-0011 執行摘要的 T-D](./0011-執行摘要-天氣-etl-併入既有存取介面.md#t-d-實跑發現需下一輪決議)

## 名詞

沿用 [`CONTEXT.md`](../../CONTEXT.md) 的**觀測點**（進位後的座標）與**批次**。
本 ADR 把「批次」的定義改了，見〈決策四〉，`CONTEXT.md` 需同步更新。

**斷點**：一次 DAG run 被額度打斷後，下一次 run 判斷「還缺什麼」的依據。

## 背景

### 病因：續跑的粒度與額度消耗的粒度不一致

額度消耗的單位是「觀測點 × 天」，但斷點只記到「觀測點」，而且是靠
GCS 上檔案的存在與否隱式表示的。一個觀測點抓了 214 天中的 214 天、
或 0 天，在 GCS 上長得一模一樣 —— **沒有任何地方記得「已經涵蓋到哪一天」**。

這就是「429 被觸發後，當日與跨日重跑都補不齊資料」的機制。
與 ADR-0009 是同一類問題：**續跑的粒度要與額度消耗的粒度一致。**

### 唯一的續跑機制：拿 GCS 既有檔名排除已抓過的觀測點

上面說的「隱式表示」，具體長這樣。`prep_batch_plan()` 列出 GCS 上已存在的檔案，
把檔名對得上的觀測點從待抓清單裡剔除，剩下的才切批次去抓。而它分兩條路：

```python
this_year = datetime.now(TAIPEI).year
if target_year < this_year:
    # 歷史年份：排除已存在的
    df_needed = df_acc_uniq_loc[~df_acc_uniq_loc["file_name"].isin(existing_files)]
else:
    # 當年度：不排除，全部重抓
    df_needed = df_acc_uniq_loc.copy()
```

T-D 認定根源是 `else` 那一支 —— 當年度整年重抓，每次 run 都從批號 0 開始，
額度在第 19 批用盡，批號 19、20 永遠輪不到。

**但 `if` 那一支也是壞的**，所以刪掉 `else` 並不能修好續跑。

#### 兩邊組的檔名根本對不上

```python
# prep_batch_plan() 組出來拿去比對的     → 24-15_121-5.parquet
# e_crawler_weatherapi() 實際存檔的名字  → cralwer_batch_3_24-15_121-5.parquet
# list_parquet() 回傳完整路徑，Path(f).name 取到的是後者
```

`isin(existing_files)` 恆為 False，**歷史年份那條路實際上也是整年重抓**。三個推論：

1. T-D 建議的臨時驗證手段（「暫時讓 d07 走歷史年份那條路跑一次」）**不會有效**
2. **d08 的四年回補同樣壞掉**，它走的就是 `if` 那一支
3. 檔名帶 `batch_id`，而批號隨每次 run 的 `df_needed` 內容浮動 ——
   同一個觀測點在不同 run 會落在不同批號，**產生重複檔案**

### 數字的來源與可信度

本 ADR 的每一個數字，標明它是量到的、算出來的、還是假設的。

| 數字 | 值 | 等級 | 怎麼來的 |
| --- | --- | --- | --- |
| 1 次額度 ≈ 25 個觀測點·天 | 25 | **實測** | 2026-08-05 實跑 d07，記於 T-D |
| 一批（50 點 × 214 天）的權重 | 526 | **實測** | 同上；由日限額反推 |

## 決策

### 一、GCS 檔名承載月份，`batch_id` 退出檔名

```
weather_cache_final/{年}/data/{年}-{月}/{lat}_{lon}.parquet
weather_cache_final/{年}/tmp/{年}-{月}/batch_no_{批號}.parquet
```

**檔案清單本身就是完整的進度表**，不需要第二份狀態、也不需要下載檔案內容才知道進度。
檔名完全由觀測點與月份決定，所以重跑會覆蓋同一個物件，
`batch_id` 浮動造成的重複檔案也就不會再出現。

暫存檔的路徑也要帶月份，否則不同月的同號批次會互相覆蓋。

**排除的做法：**

- **用 `fact_hourly_weather` 當進度表。** `t_fact_hourly_weather.py` 是 inner join，
  只保留「該觀測點、該小時剛好有事故」的列，抓回來的資料約 99% 在 T 階段就被丟掉。
  **所以這張表本來就缺絕大多數的「觀測點 × 小時」**，
  而「沒抓到」與「抓到了但那個時間那個地點沒事故」在表裡看起來一樣。

  退一步用 `MAX(observation_datetime) GROUP BY 觀測點` 只取「最後抓到哪一天」
  也不成立 —— 那個 max 是「該觀測點最後一次發生事故」的時間。一個只在一月
  出過事故的觀測點，之後每次 run 都會被從二月重抓到今天，
  而且**這個誤差不會隨時間縮小**。
- **新增一張 `weather_fetch_progress` 表。** 這避開了 inner join 的洞，但會有
  **兩份狀態**：GCS 上實際有哪些檔案、進度表說有哪些。兩份對不上時，沒辦法判斷
  誰才是對的。

  而且很容易對不上：寫完 GCS 檔案到寫進度表之間有一段時間差，task 只要在這中間
  中斷（429、`execution_timeout` 到了被殺、Airflow 重試），檔案就已經在 GCS 上、
  進度表卻沒記到。下一次 run 查進度表，會以為這段沒抓過，於是白抓一次。
- **整年一檔，只請求新天數再 concat 覆蓋寫回。** 檔案內容涵蓋到哪一天，
  檔名說不出來，得把檔案下載下來才知道 —— 那就回到本決策要解決的問題本身。

### 二、切月，不切季

決策一只說了「檔名要承載月份」，但一個月一檔或一季一檔，同樣都能讓檔名等於進度。
選月的理由是**額度餘裕**。

運作規則是「已結束的月永不重抓，當前月每次 run 整段重抓覆蓋」
（OpenMeteo 沒有 append，要多 3 天就得重寫整段；「已結束」的精確判定見決策三）。
所以一次 run 的額度是：

```
1,050 觀測點 × 當前月已過天數 / 25
```

| | 平均 | 最壞（月底／季底） | 佔時限額 5,000 |
| --- | --- | --- | --- |
| 月 | 630 | **1,302** | 26% |
| 季 | 1,932 | **3,864** | 77% |

季在季末只剩 23% 餘裕。更重要的是**兩段疊在一起**的情況：某次 run 若既要補一個
先前缺掉的月（或季）、又要抓當前的，季是 3,864 + 3,864 = **7,728，超過時限額 5,000**，
於是又撞 429；月的同樣情境是 1,302 + 1,302 = 2,604，仍在額度內。

GCS 請求數的代價，以年底全滿計：

| | 物件數 | E 階段 | L 階段 | 單次 run | 全年費用 |
| --- | --- | --- | --- | --- | --- |
| 月 | 12,600 | 1,105 | 12,613 | 13,718 | $1.29 |
| 季 | 4,200 | 1,097 | 4,205 | 5,302 | $0.87 |

月比季多 2.6 倍，**但差額是 $0.42/年，不足以當決策依據**。差距幾乎全在
L 階段逐檔 `read_parquet`；E 階段兩者幾乎相同，因為 E 只寫「當前月」的 1,050 個檔案。

### 三、一個月在「最後一天 ≤ today − 3」之前不算完成

`end_date = today - 3 天`（OpenMeteo 歷史資料的延遲）。若用「月已過去 = 完成」，
會發生這件事：

```
2026-01-31 的 run  →  寫出 2026-01/ 的檔案，涵蓋 1/01 ~ 1/28
2026-02-03 的 run  →  「1 月已過去，檔案存在」→ 跳過
                      1/29、1/30、1/31 永遠不會被抓到，而且不會報錯
```

每個月少最後 3 天，一年少 36 天。而且完全沒有跡象 —— 檔案在、進度說完成、
L 照常載入。現在的「零產出」至少一眼看得出來，這種缺法看不出來。

正確的規則是純日期算術：**月 M 完成 ⟺ M 的最後一天 ≤ today − 3**。
不讀檔案內容、不讀 GCS metadata。代價是月交界處有 1～2 次 run 要同時抓兩個月，
以 2/4 的 run 為例是 1,302 + 126 = 1,428 次，時限額的 29%。

**附帶效果：背景提到的 `if target_year < this_year` 年份分支整個刪除。**
歷史年份的每個月都自然滿足這條規則、一律視為完成；當年度用同一條規則得出正確答案。
d07 與 d08 從此走完全相同的邏輯，不再有兩條路。

### 四、批次 = 50 個觀測點 × 1 個月

切月之後，「缺什麼」不再是一維的觀測點清單，而是（觀測點 × 月）的組合。
`prep_batch_plan()` 展開成笛卡兒積，一個批次對應一個（50 點, 1 月）。

| | 一個 task 的額度 | task 數（首次／穩態） |
| --- | --- | --- |
| 一個 task 抓完該批所有缺的月（＝現況） | **428**，隨「缺幾個月」浮動 | 21 / 21 |
| 一個 task 一批一月 | **4～62**，由該月天數決定 | 168 / 21 |

428 正好落在 T-D 實測的「每批 417～455」區間 —— 因為那就是現況的行為。

選後者的理由：**額度變成事先算得出來的常數**（`batch_size × 該月天數 / 25`），
而且 429 打斷時只損失一個（批, 月）約 62 次額度，不會連累同批已抓好的月。
Airflow 這一層什麼都不用改，`expand()` 本來就吃一個 list，只是元素變多。

task 數 168 只出現在首次回補；穩態每次 run 只有當前月，21 個（月交界 42 個）。

### 五、`batch_size` 維持 50

`batch_size` 對總額度**毫無影響**（總額度 = 觀測點數 × 天數 / 25，與分幾批無關），
對穩態 task 數的影響也不大（50 → 21 個 task，200 → 6 個）。
調它換不到續跑能力，而續跑才是這輪要解決的事。

而 50 是唯一有實測依據的值 —— T-D 的「每批 526 次」「每批 30～40 秒」都是在
50 底下量到的。改成 200，回應從 26 萬個數值變 104 萬，`timeout=120` 是否還夠、
記憶體會不會爆，全都變成未經驗證的新風險。在一個至今零產出的 pipeline 上
同時改兩件事，出問題時分不清是哪一個造成的。

日後若要調，有兩個上限：每分鐘 600 額度給出 `batch_size ≤ 484`，
而常見的 8,192 bytes GET URL 上限在 350 左右就會先超過（實測 400 時 URL 已 9,080 bytes）。
**取 300 為安全上限。**

### 六、`trigger_rule` 放寬成 `all_done`，並記進度 log

`craw_done >> load_done`（`d07:84`）走的是 Airflow 的預設 `all_success`。
**這不是一個被做過的決策** —— `d07` 與 `d08` 兩支檔案都沒有出現過
`trigger_rule` 這個字，預設值是它成為現況的唯一原因。

`all_success` 沒有保護到任何東西：部分載入一直是安全的
（`l_fact_hourly_weather()` 自己列 GCS 上實際存在的檔案，`hash_value` 是唯一鍵、
upsert 冪等）。它的代價則是實測到的 —— 19 批已抓好的資料一列都沒進 MySQL，
T/L 兩層至今沒在真實資料上跑過。

新設計改變的是**頻率**：首次回補的 8,988 次額度對上 5,000/時、10,000/日的窗口，
**必然分成多次 run 完成**。「部分完成」從意外變成常態，
所以這個沒被想過的預設值會從偶爾出問題變成每次 run 都出問題。

代價：DagRun 狀態由 leaf task 決定（**推論，未實測**），`load_done` 成功會讓
DagRun 標成 success，即使上游有 mapped task failed。抓取失敗因此在 DagRun 這一層
看不出來 —— 與 ADR-0003 要消除的病因同一類，只是位置換到了 Airflow。

補救方式不需要新增任何呼叫：`prep_batch_plan()` 每次 run 記一行進度，
它讀的就是本來就要呼叫的 `list_parquet` 結果：

```
2026 年共需 168 個（批, 月）組合，GCS 上已完成 147 個，本次要抓 21 個
```

「已完成」不再增加就是真的卡住了。這比 DagRun 的成功／失敗狀態說明得更多，
而且將來有人問「這張表涵蓋到哪裡」時，這是唯一的答案來源。

### 七、d08 改成 daily schedule，補完後 pause

四年回補約 61,320 次額度（**推估**），受日限額 10,000 約束，需約 7 天。
d08 現在是 `schedule=None`，手動觸發。

改成 daily schedule，補完之後手動 pause。這只是把「7～8 次手動觸發」換成
「1 次手動 pause」，**沒有新增任何機制** —— d08 是一次性工作，
為一次性工作蓋自動化不划算。

代價：回補期間每天的 L 會把已有檔案全部重讀重 upsert（第 7 天約 5 萬個檔案），
`execution_timeout=4h` 撐得住，且此代價在 L 改增量後消失。

**排除的做法：把 d08 併進 d07。** 決策三已讓兩者邏輯完全相同，
差別只剩 `target_year` 與 `schedule`，90% 程式碼重複 —— 這是對的方向，
但需要新增「額度預算與優先序」機制（否則歷史年份會吃光當年度的額度），
而這一輪已經動了四樣東西（GCS 檔名佈局、完成判定、批次單位、`trigger_rule`）。
**列為下一輪的候選**，這一輪先讓 pipeline 真的產出資料。

### 八、429 的重試策略不變

三個現有機制在新設計下全部仍然成立：

- **`_should_retry()` 把 429 排除在 tenacity 之外。** T-D 實測證實先綁定的是
  每小時額度，而 Airflow 的 20 → 40 → 80 分重試跨得過小時窗口（第 12～19 批
  就是這樣完成的）；tenacity 的 2、4 秒必然徒勞。日限額耗盡時 Airflow 的三次重試
  （累計 140 分鐘）跨不過一天，task 會真的失敗 —— 那現在沒關係，續跑機制接手。
- **Airflow 的 `retries=3` 與指數退避。** 同上，實跑證實有效。
- **末尾的 `time.sleep(random.uniform(5, 10))`。** 它看起來像 ADR-0009 刪掉的
  `time.sleep(0.05)`，但兩者不同：ADR-0009 那個要節流的對象（逐夜市查詢）
  已經隨批次化消失了；這個佔著 `weather_api_pool` 的 slot，效果是讓每個 slot
  的發請求頻率降到每 35～50 秒一次，而它要節流的對象（每分鐘 600 的窗口）還在。

**但 `_should_retry()` 的 docstring 必須更正**（善後，非決策）。它目前寫著
「一批 50 地點 × 365 天 ≈ 1,300 次額度，日限額約 8 個批次用盡」——
數字高估 2.5 倍且誤判成日限額優先；以及「`prep_batch_plan()` 會排除 GCS 上
已存在的檔案」—— **這句目前不成立**，要等本 ADR 實作後才會成立。

## 後果

### 正面

- 續跑機制第一次真的能運作，撞到 429 的後果從「資料永久缺失」變成「進度暫停」
- 穩態每次 run 的額度從 8,988 降到 126～1,302（**推算**），是時限額的 3～26%
- 一個 task 的額度從浮動的 428 變成算得出來的 4～62
- 年份分支消失，d07 與 d08 走完全相同的邏輯
- 已抓到的資料會進 MySQL，`t_fact_hourly_weather` 與 `l_fact_hourly_weather`
  終於能在真實資料上被驗證

### 負面

- GCS 物件數從約 1,050 變 12,600（一年），L 階段逐檔讀取增為 2.6 倍
  （**假設**每次 60ms 的話約 12.6 分鐘）。此代價在 L 改增量後消失
- 首次回補的 mapped task 數從 21 變 168，Airflow UI 會很長
