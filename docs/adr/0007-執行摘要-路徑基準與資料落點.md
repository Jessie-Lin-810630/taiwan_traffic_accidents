## 一、病因定義

候選 8 的病因是：

> **路徑以 CWD 為基準推導，而 CWD 不是專案根目錄。**

三個可檢驗的判準：

1. **基準點錯誤** —— `Path().resolve()` 取得的是行程的工作目錄
2. **兩類路徑混用同一基準** —— 程式碼資產與資料落點的性質完全不同
3. **落點不持久** —— 容器中解析出的位置不在任何 volume 裡

實際掃描發現五處，且**每一處的註解都寫著「取得專案根目錄的絕對路徑」**：

| 位置 | 用途 | 判準 |
| --- | --- | --- |
| `e_crawling_traffic_accident:104` | `CWD/test/raw_data`、`processed_data` | 1、3 |
| `e_crawling_nightmarket:62`、`:395` | `CWD/test/raw_data`（兩處重複） | 1、3 |
| `t_fact_night_markets:17-20` | 模組層算路徑 + 日期，**零呼叫端** | 1 |
| `dags/d04:45` | `CWD/src/task/mart_table_sql` | 1、2 |

### 1. 落點隨 CWD 漂移

CLAUDE.md 記載「專案根目錄必須是所有指令的執行位置」—— 這是一個**未被強制的約定**。
違反它不會有錯誤訊息，只會讓檔案默默寫到別處。

實測（改動後）：

```
$ cd /tmp && python3 -c "from src.util.paths import RAW_DATA_DIR; print(RAW_DATA_DIR)"
實際 CWD : /private/tmp
RAW_DATA_DIR: <repo>/data/raw          ← 改動前會是 /private/tmp/test/raw_data
```

### 2. 容器中落在未掛載的位置（最嚴重）

```yaml
volumes:
  - ./dags:/opt/airflow/dags
  - ./logs:/opt/airflow/logs
  - ./src:/opt/airflow/src
  # ./test 沒有掛載
```

Airflow 容器的 WORKDIR 是 `/opt/airflow`，因此資料寫到
`/opt/airflow/test/raw_data` —— **不在任何 volume 裡**。
`d02` / `d03` / `d05` 抓回來的原始資料寫進容器可寫層，
`docker compose up --build` 之後就消失。

這不是潛在風險，是每次重建都在發生的資料遺失。

### 3. `d04` 的巧合

`CWD/src/task/mart_table_sql` **碰巧正確** —— 因為 `./src` 掛在
`/opt/airflow/src` 且 CWD 剛好是 `/opt/airflow`。它靠兩個獨立設定對上，
任一改動都會失效。而 SQL 檔的位置本來就該相對於**程式碼**，不是 CWD。

## 三、實際改動

### 新增單一基準

```python
# src/util/paths.py
PROJECT_ROOT = Path(__file__).resolve().parents[2]

DATA_DIR = PROJECT_ROOT / "data"
RAW_DATA_DIR = DATA_DIR / "raw"
PROCESSED_DATA_DIR = DATA_DIR / "processed"

MART_SQL_DIR = Path(__file__).resolve().parents[1] / "task" / "mart_table_sql"
```

`parents[2]` 在三個環境都成立，因為 `src/` 一律直接位於「根」之下：

| 環境 | `paths.py` 的位置 | `PROJECT_ROOT` |
| --- | --- | --- |
| 地端 | `<repo>/src/util/paths.py` | `<repo>` |
| Airflow 容器 | `/opt/airflow/src/util/paths.py`（`./src` 掛載） | `/opt/airflow` |
| Cloud Run | `/app/src/util/paths.py`（`COPY ./src ./src`） | `/app` |

這個關係由 `PYTHONPATH` 設定與 `pyproject.toml` 的
`packages = [{include = "src"}]` 共同保證 —— **`parents[2]` 依賴的是一個
本來就必須成立的約定，而 CWD 依賴的是一個沒有人保證的約定。**

`MART_SQL_DIR` 特意從 `parents[1]`（即 `src/`）推導而非專案根：
SQL 檔與程式碼同進退，即使 `src/` 被搬到別處也仍然正確。

### 呼叫端

```
src/task/e_crawling_traffic_accident.py
    _prepare_save_dirs()  8 行 → 4 行，改用 RAW_DATA_DIR / PROCESSED_DATA_DIR

src/task/e_crawling_nightmarket.py
    兩處「curr_working_dir → raw_data_save_dir → mkdir」樣板各 3 行 → 1 行

src/task/t_fact_night_markets.py
    刪除四行模組層死碼（含 import 時凍結的 datetime.now().date()）

dags/d04_analysis_pedestrian_accidents.py
    task_find_sql_files(Path().resolve() / "src/task/mart_table_sql")
    → task_find_sql_files(MART_SQL_DIR)
```

### 基礎設施

```yaml
# docker-compose.yml
volumes:
  - ./dags:/opt/airflow/dags
  - ./logs:/opt/airflow/logs
  - ./src:/opt/airflow/src
  # ETL 抓回的原始檔與處理後的 CSV（ADR-0007）。
  # 不掛載的話會寫進容器可寫層，docker compose up --build 之後就消失。
  - ./data:/opt/airflow/data
```

```gitignore
# ETL 抓回的原始檔與處理後的 CSV（ADR-0007）——
# 逐日累積且體積大，不進版控。
data/
```

### 語意變化摘要

| 情境 | 改動前 | 改動後 |
| --- | --- | --- |
| 從 `/tmp` 執行 ETL | 資料寫到 `/tmp/test/raw_data`，下游讀不到 | 寫到 `<repo>/data/raw` |
| Airflow 容器重建 | 原始資料在容器可寫層，**重建即消失** | 在掛載的 `./data`，地端與容器共用 |
| `d04` 找 mart SQL | `CWD/src/task/mart_table_sql`（靠巧合成立） | 由 `__file__` 推導，與程式碼同進退 |
| 爬回的原始資料 | `.gitignore` 無規則，會被 git 追蹤 | `data/` 已排除 |
| 生產資料的位置 | `test/`，與單元測試同住 | `data/`，與測試分家 |

## 四、驗證方式

```bash
poetry run pytest test/unit_test/          # 127 passed（前一輪 121 → 本輪 127）
poetry run pre-commit run --files <改動檔案>  # ruff check / ruff format 皆 Passed
```

本輪新增 6 個測試（`test_util_paths.py`）：

| 測試 | 釘住的行為 |
| --- | --- |
| `test_專案根含有_pyproject_toml` | `parents[2]` 的層數若算錯，這裡第一個發現 |
| `test_切換工作目錄不影響任何路徑` | **本輪核心** —— `monkeypatch.chdir` 後 reload，四個路徑全部不變 |
| `test_資料落點位於專案根之下` | 子決策 2（不引入環境變數） |
| `test_mart_sql_目錄指向實際存在的_sql_檔` | 子決策 1 —— 不只算得出路徑，還要真的指得到那 6 個檔 |
| `test_匯入時不建立任何目錄` | 子決策 7 —— 以 AST 確認模組內無 `mkdir` 呼叫 |
| `test_全_repo_不再以_cwd_為路徑基準` | 以 AST 掃描 `src/` 與 `dags/`，比對「無引數的 `Path()` 後接 `.resolve()`」 |

最後一個測試是**持續性的護欄**：日後有人再寫 `Path().resolve()` 會立刻紅燈，
不必依賴人工 review 或 grep。

另以真實的跨 CWD 執行佐證：

```
$ cd /tmp && python3 -c "...from src.util.paths import ..."
實際 CWD : /private/tmp
PROJECT_ROOT: <repo>
RAW_DATA_DIR: <repo>/data/raw
MART_SQL 檔數: 6
```

以及沿用前五輪的匯入健檢：`src/` 底下 35 個模組全部可獨立匯入。

### A. 本輪浮現、刻意未處理

| 位置 | 現象 | 歸屬 |
| --- | --- | --- |
| `import` 機制 | `src.xxx` 絕對匯入仍靠 CWD 或 `PYTHONPATH` 解析，CLAUDE.md 的「必須在專案根執行」不會因本輪消失 | 與資料落點無關，另一回事 |
| `data/` 的保留策略 | 抓回的原始檔逐日累積（檔名含日期），無任何清理機制 | 維運議題 |

| `parents[2]` | 仍是層數硬編碼，搬動 `paths.py` 會失效 | 只出現一次且有測試釘住 |

### B. 屬於其他候選（狀態更新）

| 位置 | 現象 | 歸屬 |
| --- | --- | --- |
| 全 codebase | 設定散在多個 `load_dotenv()` 與模組層全域變數，零驗證 | 候選 7 |
| `cal_accidents_nearby_nightmarket` | 一夜市一次 round-trip 的 N+1 查詢；查詢字串以 f-string 內插經緯度 | 候選 10 |

若日後真需要把資料放到外接儲存，那時再連同設定集中化一起處理。
