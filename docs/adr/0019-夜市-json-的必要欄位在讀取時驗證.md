# ADR-0019：夜市 JSON 的必要欄位在讀取時驗證

- 日期：2026-08-26
- 狀態：已採納
- 範圍：`src/task/t_fact_night_markets.py` 的 `read_googlemap_responsed_json()`
- 相關：
  [ADR-0003 快取層不再吞噬例外](./0003-快取層不再吞噬例外.md)（不把故障吞成「正常但空」）、
  [ADR-0006 抓取層區分暫時性與永久性故障](./0006-抓取層區分暫時性與永久性故障.md)（記 `warning` 或 `error` 的判準）
- 來源：使用者於 2026-08-26 提出，希望比照 `read_traffic_accident_file()` 的缺欄處理，
  替夜市 JSON 加上 schema 驗證

## 名詞

| 詞 | 意思 | 在程式碼的哪裡 |
| --- | --- | --- |
| **項目** | JSON 最外層 list 的一個元素，一次 Places API 查詢的回應 | `read_googlemap_responsed_json()` 迴圈裡的 `r` |
| **頂層鍵** | 一個夜市的 `result` 底下的第一層 key | `name`、`formatted_address`、`geometry`、`opening_hours`、`rating`、`url` |
| **必要頂層鍵** | 缺了就讓這一筆失去意義的頂層鍵 | 本文的決策內容，四個 |
| **缺欄比例** | 一筆夜市缺了幾個必要頂層鍵 ÷ 必要頂層鍵總數 | 本文的門檻判準 |

## 背景

### 問題 1：目前沒有任何一支函式會因為欄位改名而失敗

六支清洗函式讀取頂層鍵的方式一律是 `.get(key, 預設值)`：

| 函式 | 讀的頂層鍵 | 缺欄時填什麼 |
| --- | --- | --- |
| `_clean_night_market_name` | `name` | 無預設，會是 `None`，隨後 `.find()` 拋 `AttributeError` |
| `_clean_night_market_address` | `formatted_address` | 「無地址資訊」，五個欄位全成為「無匹配…」 |
| `_clean_night_market_geometry_location` | `geometry` | 六個座標全為 `None` |
| `_clean_business_datetime` | `opening_hours` | 空清單，這一筆完全不會進資料表 |
| `_clean_googlemap_rating` | `rating` | `None` |
| `_clean_googlemap_url` | `url` | 「未取得」 |

也就是說，若 Google 把 `formatted_address` 改名為別的字眼，整批夜市的地址五欄
會全部變成「無匹配縣市資訊」寫進資料表，pipeline 全綠、沒有一行 log。

`geometry` 缺欄更嚴重：緯度 + 經度 + 營業星期是 `fact_night_markets` 的唯一鍵，
座標全成 `None` 等於整批資料失去主鍵。

### 問題 2：實測真實資料的缺欄分佈

**事前實測：** 對 `data/raw/Taiwan_night_markets_from_map_api_2026-08-01.json`
（一份完整抓取全臺夜市的結果）跑過一遍，全部 471 個項目，**每一個都有 `result`**。
以下統計的母體是這 471 筆，與決策二選定的驗證母體一致：

| 頂層鍵 | 出現筆數 | 缺欄筆數 | 缺欄率 |
| --- | --- | --- | --- |
| `name` | 471 | 0 | 0% |
| `formatted_address` | 471 | 0 | 0% |
| `geometry` | 471 | 0 | 0% |
| `url` | 471 | 0 | 0% |
| `rating` | 455 | 16 | 3.4% |
| `opening_hours` | 432 | 39 | 8.3% |

以「四個必要頂層鍵」為分母，每一筆缺幾個：

| 缺幾個 | 筆數 | 缺欄比例 | 是否超過 30% |
| --- | --- | --- | --- |
| 0 個 | 432 | 0% | 否 |
| 1 個（都是 `opening_hours`） | 39 | 25% | 否 |
| 2 個以上 | **0** | ≥50% | 不適用 |

**這組數字有兩個意義：**

1. 門檻定在 30%、分母定為 4 個必要鍵，在現行真實資料上**一次都不會觸發 raise**，
   只會產生 39 筆 `opening_hours` 的 warning。不會誤殺正常資料。
2. 反過來說，這個規則要等到 Google 真的改動 schema 才會發聲：它是一道保險，
   不是對現有問題的修補。

## 決策

### 一、驗證分兩層：先驗 `result`，再驗四個必要頂層鍵

`result` 也是 JSON 裡的一個欄位，沒道理它缺了就拋一個難懂的 `KeyError`，
其他四個欄位缺了卻有完整訊息與門檻。兩層都寫成模組層常數：

```python
REQUIRED_RESULT_KEY = "result"
REQUIRED_KEYS = ("name", "formatted_address", "geometry", "opening_hours")
```

**第一層**：每個項目都要有 `result`。缺了就無從談後面四個鍵，
視為這一筆四個必要鍵全缺，缺欄比例 100%，直接走決策五的 `error` 路徑。
這一層取代現行 `r["result"]` 的 `KeyError`。

**第二層**：`result` 底下的四個必要頂層鍵。
`name`、`formatted_address`、`geometry` 缺了這一筆就沒有意義了，
甚至座標是唯一鍵必要的一部分。`opening_hours` 缺了這一筆會完全不進資料表
（`_clean_business_datetime()` 回空清單，`_t_clean_one_night_market()` 展開成零列）。

`rating` 與 `url` **不列入必要**：實測缺欄率 3.4% 與 0%，且冷門夜市本來就可能沒有評分，不需過於嚴苛。

### 二、兩層都在名稱過濾之前完成

現行流程是「取 `r["result"]` → 用名稱含「夜市」或「商圈」過濾 → 收進清單」。
驗證要插在過濾**之前**，母體是 JSON 裡的全部項目，不是過濾後的夜市。

理由有兩個：

1. `name` 本身就是過濾的依據。`name` 缺了現行程式會在 `"夜市" in None` 拋 `TypeError`，
   要先驗過才能安全地過濾。
2. Google 改 schema 是全域現象，不會只影響名字裡有「夜市」的那些。

代價是那些本來就要被丟棄的非夜市項目（實測 471 筆中有 28 筆）也會被計入統計。
實測這 28 筆裡有 19 筆四鍵齊全、9 筆缺 `opening_hours`，沒有任何一筆缺 2 個以上，
所以不影響門檻判斷，只讓 warning 的筆數從 30 變成 39。接受。

### 三、只驗證頂層鍵，不驗巢狀結構

不檢查 `geometry.location.lat`、`opening_hours.periods[].open.day` 這類內層鍵。
理由是那些知識屬於六支清洗函式，在讀取層再寫一份等於把同一件事維護兩處。
代價是「`geometry` 還在但 `location` 改名」這種情況攔不到，接受。

### 四、缺欄比例以「單一夜市」為單位計算，分母是 4

```
缺欄比例 = 這一筆缺的必要鍵數 ÷ 4
```

因為分母是 4，「超過 3 成」實際等於**缺 2 個以上就拋**（缺 1 個 = 25%，未達門檻；
缺 2 個 = 50%，超過）。這一點在實作與測試裡都要寫明，避免日後有人以為改成
「缺 1 個」也會觸發。

### 五、未達門檻記 `warning` 且彙總，達門檻記 `error` 後拋 `ValueError`

- **未達門檻**（缺 1 個）：記 `warning`，繼續處理。**彙總後記一次**，不逐筆記：
  實測有 39 筆缺 `opening_hours`，逐筆會刷出 39 行 log。
- **達門檻**（缺 2 個以上）：記 `error` 後 `raise ValueError`。

依 ADR-0006 第 5 條，schema 變動重試無效，是永久性故障，所以是 `error` 不是 `warning`。
依 ADR-0003 第 3 條，有 `raise` 就不帶 `exc_info=True`。


### 六、掃完全部才拋，不遇到第一筆就中斷

先掃過所有夜市，累積「哪些筆超標、各缺哪些鍵」，最後一次拋出。
理由是 schema 變動幾乎必然影響整批，一次列出全貌比只報第一筆更有診斷價值。
代價是多跑完一輪迴圈，471 筆的成本可忽略。

## 後果

### 正面

- Google 改動欄位名稱時會在讀取當下就停下並指名，不再靜默寫進整批「無匹配...」與 `None`
- 必要欄位從六支清洗函式的 `.get()` 預設值裡被抽出來，成為一份明文清單

### 負面

- 門檻是拍板出來的數字，不是從資料算出來的。實測顯示它在現行資料上不會觸發，
  但「30%」本身沒有統計依據

### 中性

- 個別筆的稀疏資料仍照常通過，行為與現況相同
- `read_googlemap_responsed_json()` 從純讀取函式變成「讀取 + 驗證」。函式名稱不改，
  但 docstring 的 `Raises` 要補上 `ValueError`
