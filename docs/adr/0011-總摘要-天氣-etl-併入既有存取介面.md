## 前言

一條在 ADR-0001～0010 之外成形的天氣 ETL（8 支檔案，OpenMeteo → GCS Parquet → MySQL），
以七個候選併回既有介面。**結構上的目標全數達成 —— `src/` 自此完全不依賴 Airflow ——
但 pipeline 至今零產出**，原因是實跑後才發現的額度問題（T-D），與本輪的重構無關。

## 病因主題

七個候選分成四個主題。下一輪要找新候選時，可以照這四個主題去看還有哪裡沒清乾淨。

| 主題 | 病因 | 候選 | 結清狀態 |
| --- | --- | --- | --- |
| **連線方式重複實作** | 同一個外部資源有兩套連線寫法 | 1（MySQL）、5（GCS 沒有共用的連線模組） | `src/` 內零筆 |
| **繞過既有樣板** | 取得連線後自己操作，不走 `create_tables()` / `upsert_to_table()` | 2（DDL）、4（UPSERT） | `src/` 內零筆 |
| **Airflow 滲入 ETL 層** | 例外型別、Hook 型別、`@task`、`Variable` 出現在 `src/` | 3、5、6 | `src/` 內零筆 |
| **領域建模** | 取樣精度與資料來源的實際解析度不符 | 7 | 已收成單一函式 |

前三個主題是技術債，第四個（候選 7）是本輪唯一的領域建模決策，
於候選 3 跑 `/grilling` 追問時浮現，因此另立 [ADR-0012](./0012-氣象網格精度.md) 與 `CONTEXT.md`。

執行順序最後是 1 → 2 → 5 → 3 → 7 → 4 → 6。順序被調整過兩次：
候選 5 提前（讓後續候選能被 import 級護欄測試驗證），候選 7 插在 4 之前
（先把批次數降下來，429 才會從常態變邊界情況）。

## 各候選的決策取捨

每個候選記四件事：選了什麼、解決了什麼、否決了什麼，
以及所選方案與被否決方案各自要付出的代價。

### 候選 1 —— 刪掉重複的 MySQL 連線寫法（commit sha : `dcacc3b`）

- **選了什麼**：刪掉兩支自有的 module（共 71 行），三處呼叫端改指
  `src/util/mysql_utils.py` 的等價函式。`database=None` 一律採 `mysql_utils.py`
  的語意，也就是「不指定資料庫」。

- **解決了什麼**：被刪掉的 `get_engine_sqlalchemy()` 裡面是裸的 `create_engine()`，
  在分批迴圈中每批都新建一個 Engine，一次 DAG run 生出數十個各帶 5 條連線的池，
  `pool_size` 那三個參數等於完全沒作用。另外兩個檔案各有一個同名的
  `get_table_from_sqlserver()`，看呼叫處無法判斷用的是哪一個，得回頭翻 import。

- **否決了什麼**：否決了「寫一層相容包裝，保留舊的 `os.getenv("MYSQL_DATABASE")`
  回退行為」。

- **所選方案的代價**：呼叫端從此必須顯式把 `database` 傳進來，少了一層 env 兜底。

- **被否決方案的代價**：留著回退等於同一個參數在專案裡有兩種語意，
  天氣模組會自成一套慣例，跟這一輪要做的事情正好相反。
  而且那條分支在實際路徑上是死碼 —— d07、d08 都明確傳入 `"traffic_accidents"`。

### 候選 2 —— DDL 回到宣告樣板（commit sha : `e049c48`）

- **選了什麼**：`src/util/create_weather_related_tables.py` 搬成
  `src/task/create_weather_tables.py`，DDL 改用模組層的 `WEATHER_TABLES` dict 宣告，
  執行交給 `create_tables(engine, WEATHER_TABLES)`，形狀與
  `create_night_markets_tables.py` 完全一致。

- **解決了什麼**：舊寫法用 `engine.connect()` 卻沒有 `commit()`，
  離開 context 其實會 rollback —— 它之所以能用，是因為 MySQL 的 DDL 帶隱式提交。
  這是靠資料庫特性掩蓋的錯誤寫法，換到任何支援交易式 DDL 的資料庫就會靜默失效。
  另外 `table_name` 被做成參數、內插進 DDL 本體與三個索引名，
  但全專案只有一個呼叫點、傳的永遠是同一個值。

- **否決了什麼**：否決了「既然表名固定下來了，順手把索引名縮短成 `idx_hw_obt`
  這類形式」。

- **所選方案的代價**：幾乎沒有，這是本輪範圍最小的一個候選。

- **被否決方案的代價**：生產環境的資料表可能已經用舊的索引名建好了，
  而 `CREATE TABLE IF NOT EXISTS` 不會重建它 —— 改名只會讓程式碼裡的宣告
  與資料庫實際的樣子出現無謂落差，索引名又不影響任何查詢。

### 候選 5 —— GCS 收攏成一支共用模組（commit sha : `d15fd74`）

- **選了什麼**：新增 `src/util/gcs_utils.py`（3 支公開函式 + Client 單例，
  走 Application Default Credentials），改用 `google-cloud-storage` 原生 client，
  7 個 `GCSHook` 呼叫點全數轉換。模組直接收送 DataFrame，Parquet 的序列化由它自己負責。

- **解決了什麼**：GCS 是專案的第三個外部資源，卻是唯一沒有共用模組的一個 ——
  bucket 名稱的字面量重複 4 次、路徑組法 4 次、`BytesIO` 序列化樣板 4 次。
  更關鍵的是 `GCSHook` 來自 `airflow.providers.google`，只要它出現在 `src/task/`，
  那支模組就永遠無法在無 Airflow 的環境被匯入；而這個 provider **根本不在
  `pyproject.toml` 也不在 `requirements.txt`**，只是官方 image 碰巧內建。

- **否決了什麼**：三件事 —— 包裝 `GCSHook`（方案 A）、模組只搬 bytes 不管序列化、
  在 GCS 呼叫外面自己再加一層重試。

- **所選方案的代價**：多一個依賴 `google-cloud-storage`；
  認證機制從 Airflow Connection 換成 ADC，而**這件事在地端無法證明**，
  要到 VM 上才知道 service account 的權限夠不夠。
  另外「不自行重試」意味著必須把函式庫的重試範圍講清楚，否則「以為有重試」
  跟「以為沒有」一樣危險，因此花力氣核對了 3.13.0 的原始碼，
  並留下一則陷阱提醒：日後若新增刪除或 metadata 異動的函式，那類操作走
  `ConditionalRetryPolicy`，**不帶 `if_generation_match` 時一次都不重試**。

- **被否決方案的代價**：包裝 `GCSHook` 等於為新資源在 ADR-0001 的護欄上開一個白名單，
  開了以後下一個資源沒有理由不比照。只搬 bytes 的話，序列化樣板會原封不動
  留在 4 個呼叫點，那是把重複搬家而不是消除它。自己再加一層重試，
  會讓重試上限變成 3×3。

### 候選 3 —— 天氣 API 改走故障分類（commit sha : `4ec33f2`）

- **選了什麼**：刪掉 `src/util/request_weather_api.py`，內化成
  `e_crawling_weather.py` 裡的 `_request_weather_api()`（站台專屬的東西不該待在
  `src/util/`）；自訂 `_should_retry()`，429 排除在重試之外；
  失敗率的分母改用「請求的地點數」並加上回傳筆數斷言；7 處 `print` 改 logger。

- **解決了什麼**：原本五種 requests 例外全被轉成 `AirflowException`，
  原始型別一被抹掉，`src/util/crawling_utils.py` 的 `is_transient()` 就再也認不出
  429 與 5xx，重試機制形同虛設。還有三個必然觸發的缺陷：`except Timeout` 區塊裡
  引用了尚未賦值的 `response`（`UnboundLocalError` 會蓋掉真正的網路錯誤）、
  3xx 會穿過所有分支隱式回傳 `None`、以及分母算法讓「一筆都沒存到」被算成完全成功。

- **否決了什麼**：否決了「429 也交給 tenacity 重試」，
  以及「改用回應裡的 `latitude`/`longitude` 來對應地點」。

- **所選方案的代價**：筆數斷言是本候選唯一新增的行為 ——
  萬一 OpenMeteo 在某些情況真的會回傳少於請求數的筆數（例如座標落在海上），
  原本能部分成功的批次會整批失敗。這一點還沒用真實回應驗證過。

- **被否決方案的代價**：429 交給 tenacity 只會在 log 留下三筆永遠不會成功的紀錄；
  改用回應座標則會讓下游的 merge 全部落空，因為那是網格中心座標、與事故端的值不同。

⚠ **這個決策成立，但當時寫的理由不對** —— 實跑後的修正見〈下一輪起點〉。

### 候選 7 —— 氣象網格精度（commit sha : `3bf99f2`、`ee7f0dc`）

- **選了什麼**：進位精度從 0.01 度改成 `GRID_STEP = 0.05`，
  高程固定為 `FIXED_ELEVATION_M = 10`，算法收成 `round_to_weather_grid()`
  單一函式，事故側與天氣側都呼叫它。

- **解決了什麼**：0.01 度（約 1.1 公里）遠比 OpenMeteo 的模式網格
  0.0703 度（約 7.8 公里）細，一年得到 11,000 個相異座標，多數相鄰座標拿回的是
  完全相同的資料，卻各自消耗一份額度 —— 實測 400 個座標只對應 15 種相異的天氣序列。
  另外 API 預設會依 90 公尺解析度的地形模型做高程降尺度，
  同一網格內的座標會因海拔不同而落到不同網格，使進位結果無法預測。

- **否決了什麼**：否決了 0.1 度。

- **所選方案的代價**：固定高程 10 公尺，等於主動承擔山區氣溫偏高的偏差 ——
  這是有意識的取捨，理由是車禍多發生在人口密集的平地市區。

- **被否決方案的代價**：0.1 度雖然能再把批次數砍一半，但它已經比模式網格粗，
  一個進位後的座標會橫跨約兩個網格，那是系統性地抹掉真實差異，而不只是邊界效應。

### 候選 4 —— 拆開 E/T/L 糾纏（commit sha : `97c3bab`）

- **選了什麼**：把一個 `l_` 檔裡橫跨三階段的四個函式拆成 `e_` / `t_` / `l_` 三支，
  `l_load_to_mysql_gcp.py`（331 行）刪除；分批迴圈留在 `l_` 層；
  手組的 UPSERT 改用 `upsert_to_table()`；`batch_size` 從 `Variable.get()` 改成函式參數。

- **解決了什麼**：連線在分批迴圈內建立、`finally` 卻在迴圈外，跑 N 批就洩漏 N−1 條；
  `except` 沒有 raise、`else` 裡又有 return，導致**寫入全數失敗的 task
  在 Airflow UI 上顯示綠色成功**；`Variable.get()` 在變數存在時回傳 `str`，
  餵給 `range()` 會 `TypeError`；空的檔案清單被吞成正常回傳。

- **否決了什麼**：三件事 —— 把分批迴圈上移到 DAG、把兩支 E 函式合併成一支、
  順手修掉 T 層的重工。

- **所選方案的代價**：`l_fact_hourly_weather(target_year, database, batch_size)`
  的簽章與其他接 DataFrame 的 `l_*` 不同形，這件事只能寫進 docstring 提醒。

- **被否決方案的代價**：迴圈上移到 DAG 會違反「改 ETL 邏輯改 `src/task/`」的分工，
  因為分批本身就是 ETL 邏輯。兩支 E 函式的粒度差很多（約 700 列 vs 約 40 萬列），
  合併等於為了 700 列從 MySQL 搬 40 萬列回來。T 層的重工則是刻意留著 ——
  進位是冪等的、行為確實正確，這個候選聚焦結構拆分，重工列入下一輪候選來源。

### 候選 6 —— `@task` 搬回 DAG 層（commit sha : `df114ae`）

- **選了什麼**：移除 `src/task/` 上的三個 `@task`，改在 d07／d08 內各自包裝；
  `pendulum` 換成 stdlib 的 `datetime` + `zoneinfo`（取台北時區）；
  移除三處 `sys.path.append("/opt/airflow")`；護欄測試的模組數量斷言改成下限。

- **解決了什麼**：重試策略、pool 配額、逾時這些純排程的設定，
  原本直接貼在 ETL 函式的定義上，使得那三支函式無法在 pytest 或地端單獨呼叫
  （`@task` 回傳的是 `XComArg` 而不是結果），也不能被別的 DAG 用不同的重試策略復用。
  順帶清掉最後一個 airflow 傳遞相依 `pendulum`，以及一個既存的不一致 ——
  容器沒設 `TZ`，`pendulum.now()` 取的是 UTC，但 API 請求固定要台北時區的資料。

- **否決了什麼**：否決了「抽一支 `dags/weather_tasks.py` 讓兩支 DAG 共用包裝」。

- **所選方案的代價**：兩個。一是 d07 與 d08 各多出約 20 行重複；
  二是改用台北時區算日期是**行為變化** —— `end_date` 會比原本晚最多一天，
  三天緩衝的實效縮成約 2.67 天，而這一點還沒實測。
  若第一次跑 d07 發現 `end_date` 那天是空值，把 `timedelta(days=3)` 調成 4 即可。

- **被否決方案的代價**：`dags/` 目前只有 `dNN_*.py`，多一支非 DAG 檔案是引入新的結構模式，
  為了消除 20 行重複並不划算；何況兩支 DAG 的排程需求本來就可能不同
  （d07 是常態增量、d08 是一次性回補），共用反而會綁死它們。

## 驗證結論

### 已證實

| 項目 | 證據 |
| --- | --- |
| **`src/` 完全脫離 Airflow** | 實際匯入 25 支模組，`airflow`/`pendulum` 殘留為零。護欄測試自 baseline（commit sha : `9de276c`）起紅了七個候選，於候選 6 轉綠 |
| 全套測試 | 171 → **183 passed, 0 failed**（候選 5 新增 10 個 `gcs_utils` 測試） |
| ADR 違規歸零 | 裸 `create_engine()`、手組 UPSERT、`finally` 裸 close、`AirflowException`，`src/` 內各零筆 |
| 拆檔後 merge 接得起來 | 合成資料端到端跑 T 層，3 列事故對到 3 列天氣，hash 唯一且長度 32 |
| `_should_retry` 行為 | 以真實 requests 例外逐項驗證 6 種情況 |
| 網格進位有效 | **實打 API**：落在同一模式網格的觀測點回傳完全相同的氣溫；高程確實固定在 10.0 |
| lint | 候選 6 是本輪第一個不需 `--no-verify` 的 commit |

### 未驗證

按「會怎麼壞」排序，不按候選順序：

1. **兩支 DAG 未在 Airflow 中 parse 過**。本機無 airflow，只做 AST 檢查。
   d08 的 `.override(task_id=...)` 若沒真的避開 task_id 重複，Airflow 會拒絕載入整支 DAG。
2. **候選 6 的時區改動是行為變化**：`end_date` 從 UTC 改台北，
   三天緩衝實效縮成約 2.67 天。若 `end_date` 那天回空值，把 `timedelta(days=3)` 調成 4。
3. **候選 3 的筆數斷言未經真實回應驗證**。若 OpenMeteo 在某些情況回傳少於請求數
   （例如座標落在海上），原本能部分成功的批次會整批失敗。
4. **未對真實 GCS／MySQL 實跑**：連線洩漏的修復、UPSERT 等價性、分批寫入正確性，
   都只由程式碼結構與合成資料保證。
5. **GCS 認證改走 ADC 未在 VM 上驗證**。分析上不會變（原本 `GCSHook` 的
   keyfile 欄位就是空的，本來就走 ADC），但 service account 的實際權限需實測。
6. **「11,000 → 約 700 個觀測點」是推算**，依實測合併比例外推，
   確切數字需在資料庫上跑一次 `COUNT(DISTINCT ...)`。

## 下一輪起點：T-D 實跑發現

2026-08-05 第一次實跑 d07（21 批），暴露**三個互相加乘的問題，結果是零產出**。
這不是本輪重構造成的，但擋住了 T 層與 L 層的第一次真實驗證。

### 實測的額度數字（取代候選 3 的推算）

| 項目 | 實測 |
| --- | --- |
| 一批（50 地點 × 214 天 × 7 變數） | **約 526 次** |
| 2026 年全部 21 批 | 約 11,053 次 = 日限額的 **111%** |
| 每日額度 10,000 撐得住 | 約 19 批 |

候選 3 第二章推算的「每批約 1,300 次」**高估約 2.5 倍，且誤判為日限額優先綁定**
—— 實際先綁定的是每小時額度，而 Airflow 的重試（20 → 40 → 80 分）跨得過去。
候選 3 的**決策仍然成立，只是理由要換**。

### 三個問題

1. **根源：當年度不排除既有檔案，等於整年重抓。**
   `prep_batch_plan()` 的原註解說的是「補上次存檔後多出的三天」，
   實作卻是全量重跑 —— 155 次 vs 11,053 次，**70 倍差距**。
   後果是每次都從批號 0 開始，批號 19、20 永遠跑不到。
2. **整年需求超過單日額度。** 改 `batch_size` 完全無效（權重 = 地點數 × 天數）。
3. **L 階段 `all_success` 要求全批成功。** 19 批的資料躺在 GCS 上，
   卻因 20、21 批未完成而一列都沒進 MySQL。

## 一句提醒給改動天氣 pipeline 的人

`t_fact_hourly_weather` 的 merge 能成立，靠的是事故側與天氣側呼叫**同一支**
`round_to_weather_grid()`。只要有一側算法不同，merge 會一列都對不上，
**而且不報錯**。這是本 pipeline 最容易靜默壞掉的地方（ADR-0012）。
