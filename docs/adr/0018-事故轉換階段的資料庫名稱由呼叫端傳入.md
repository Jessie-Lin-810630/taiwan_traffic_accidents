## 背景

事故 pipeline 的三個階段對「要操作哪個資料庫」的處理方式並不一致。

### 1. `l_` 收參數，`t_` 卻自己寫死

載入階段的三支 `l_fact_accident_*()` 都有 `database` 參數，由 DAG 從
`os.getenv("MYSQL_DATABASE")` 取值後傳入。轉換階段的三支 `t_fact_accident_*()`
則沒有這個參數，它們在函式內部查維度表與事故主檔時，把資料庫名稱直接寫成
字面常數：

```python
df_dim_accident_day = get_table_from_sqlserver(query, database="traffic_accidents")
```

三支合計 8 處（`t_fact_accident_env` 4 處、`t_fact_accident_main` 2 處、
`t_fact_accident_human` 2 處）。

同一條 DAG 裡，同一個 task 內先後呼叫 `t_` 與 `l_`：

```python
t_done_main = t_fact_accident_main(pathlist)      # 讀 traffic_accidents（寫死）
l_fact_accident_main(t_done_main, database)       # 寫 database（環境變數）
```

**讀與寫的目標資料庫由兩個不同方式決定。** 兩者一致時看不出問題，但是
`MYSQL_DATABASE` 一旦指向別的資料庫（例如: 換環境、開測試庫），
`t_` 仍會去讀 `traffic_accidents` 的維度表，取回來的外鍵被寫進另一個資料庫的事實表。


### 2. 三支 `t_dim_*` 不受影響

同一批 task 裡的 `t_dim_accident_type()`、`t_dim_road_design()`、
`t_dim_lane_design()` 只讀 CSV、不查資料庫，故沒有第一點提到的問題。

### 3. `MYSQL_DATABASE` 缺值時未提醒

`database = os.getenv("MYSQL_DATABASE")` 在 `MYSQL_DATABASE` 未設定時回傳 `None`，
一路傳到 `get_engine_to_mysql(None)`。該函式對 `None` 有明確語意與對應要做的行為，也就是
建立一條「不指定資料庫」的連線（ADR-0004），供建立資料庫本身時使用；
但對事故 pipeline 而言，指派 database 為 `None`，並不是一個有意義的行為，所以要設缺值提醒。

---

## 決策

**會查資料庫的轉換階段，資料庫名稱一律由呼叫端傳入；DAG 在取得環境變數的
當下就驗證它不是 `None`。**

### 四項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | 三支 `t_fact_accident_*()` 新增 `database` 參數，函式內不再出現資料庫名稱字面值 | 與 `l_fact_accident_*()` 對齊。 |
| 2 | 參數型別為 **`database: str`（必填），不給預設值** | 這三支必定要查資料庫，沒有「不指定」的合理情境。 |
| 3 | DAG 在 `os.getenv("MYSQL_DATABASE")` 之後立即檢查，為 `None` 時 `raise ValueError` | 檢查放在取值處，訊息能直接說出設定名稱（遵循 ADR-0008 的原則）。 |
| 4 | 本輪只改 `d02`、`d03` 兩支 DAG | 它們是事故三支 `t_` 的全部呼叫端。其餘五支 DAG 見「未納入本次範圍」 |

---

## 後果

### 正面

- 事故 pipeline 的讀與寫指向同一個資料庫，且只有一個來源。
- 換資料庫只需要改 `MYSQL_DATABASE` 一個地方。
- `MYSQL_DATABASE` 缺失時，第一行錯誤訊息說的是設定名稱，
  而不是 MySQL 的 `No database selected`。
- 測試可以直接指定資料庫名稱，不必依賴或 patch 掉那個字面值。

### 負面

- **是破壞性的簽名變更**。三支 `t_` 的所有呼叫端都要跟著改，
  包含 `d02`、`d03` 與 `test/unit_test/` 下的既有測試。
  漏改的地方會在執行時拋 `TypeError`，不會在 import 時被發現。
- **多一個要傳的參數**。`d03` 的 `task_t_and_l_other_facts` 走 dynamic task
  mapping，`database` 是 `partial()` 帶進去的，改動要同時顧到 `expand()` 那一側。

### 中性

- `t_fact_*` 轉換邏輯本身不需要動：清洗步驟、主鍵演算法、去重與排序的依據都不變。
- 不動到 "ADR-0008 對 `MYSQL_USER` / `MYSQL_PASSWORD` 的檢查"。
- 本輪加的是 `MYSQL_DATABASE`，不動到 `mysql_utils` 公用函式庫。

## 未納入本次範圍

- **其餘五支 DAG 的 `MYSQL_DATABASE` 檢查**（`d01`、`d04`、`d05`、`d07`、`d08`）。
  它們有同樣的 `database = os.getenv("MYSQL_DATABASE")`，也有同樣的 `None` 路徑。
- **`src/task/core/c_db.py` 的資料庫名稱字面值**。
  也有 10 處同樣是硬編碼，但這份檔案沒有從 DAG 那樣的參數來源傳遞過來，從哪裡傳遞可以再討論。
- **`exec_mart_sql()` 內的 `os.getenv("MYSQL_DATABASE")`**。
  它的 `database` 參數已經是 `str | None = None`，`None` 時才回頭讀環境變數，
  語意與本輪的三支不同。
