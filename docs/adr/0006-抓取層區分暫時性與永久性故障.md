- 來源：[ADR-0003 執行摘要](./0003-執行摘要-快取層與日誌職責.md)第五章 A 提出的「候選 6」

## 背景

前三輪（ADR-0003、0005）處理的是「故障被吞掉」。抓取層的病灶更前面一步：
**故障根本沒有被分類** —— 暫時性故障、永久性故障與「查無資料」三者
共用同一條回傳路徑，於是沒有任何一種能被正確處置。

### 1. 非 200 回傳 `None`，呼叫端 `.extend(None)`

```python
# download_and_extract_zip / download_csv
else:
    logger.error(f"無法下載zip檔案，response.status_code: {response.status_code}")
    return None
```

呼叫端：

```python
csvfile_paths_a_hist_year = download_and_extract_zip(...)
csvfile_paths_historical.extend(csvfile_paths_a_hist_year)   # None → TypeError
```

`e_crawling_historical_traffic_accident` 與 `e_crawling_latest_traffic_accident`
共三處 `.extend()`。實際發生 HTTP 503 時，Airflow log 裡最醒目的是
`TypeError: 'NoneType' object is not iterable` —— 真正的原因（狀態碼）
只是上一行的一則 `logger.error`。

### 2. `find_download_links` 非 200 靜默跳過

```python
response = requests.get(url, headers=headers, verify=False, timeout=120)
if response.status_code == 200:          # 沒有 else
    soup = BeautifulSoup(response.text, "html.parser")
...
else:
    if soup is not None:                 # 非 200 時整個 url 被跳過
        ...
```

五個歷年資料頁面中有一個回 503，回傳的 `download_links` 就少一年份，
而整個流程照常成功。**這與 ADR-0005 剛修好的 `find_tw_night_markets_list`
是完全相同的結構。**

### 3. Google Places API：HTTP 200 不代表成功

```python
data = response.json()
if data.get("candidates"):
    return data["candidates"][0]["place_id"]
return None                              # 其餘一律當成「找不到」
```

Places API 的失敗是寫在 body 的 `status` 欄位裡，HTTP 狀態碼一律是 200：

| `status` | 真實語意 | 現行處置 |
| --- | --- | --- |
| `OK` | 成功 | 正確 |
| `ZERO_RESULTS` | 真的查無此地點 | 正確 |
| `NOT_FOUND` | Place Details 專有：place_id 已失效 | **當成成功資料回傳** |
| `OVER_QUERY_LIMIT` | 配額或 QPS 超限，**暫時性** | 當成「找不到」 |
| `REQUEST_DENIED` | 金鑰無效、API 未啟用或超出授權範圍，**永久性** | 當成「找不到」 |
| `INVALID_REQUEST` | 通常是缺少必要參數，即**呼叫端的程式錯誤**，永久性 | 當成「找不到」 |
| `UNKNOWN_ERROR` | 伺服器暫時錯誤 | 當成「找不到」 |

淨結果：**API 金鑰過期時，300 個夜市全部「找不到」，
`e_crawling_nightmarket` 仍然成功回傳一個空的 json 檔路徑**，
失敗率只出現在最後一行 log 裡。下游 `t_fact_night_markets` 拿到空清單。

### 4. 零重試

`data.gov.tw` 的大檔下載與 Google API 的 QPS 限制都是典型的暫時性故障，
但整個抓取層沒有任何重試。目前唯一的重試在 Airflow task 層（`retries: 2~3`）——
粒度是「整個 task 重跑」。

### 5. 兩套抓取實作並存

`src/util/crawling_utils.py`（322 行，**零呼叫端**）與
`src/task/e_crawling_traffic_accident.py`（324 行，**實際使用**）有三支同名函式。
新版已經用了 `raise_for_status()` 與 typed except，舊版沒有。

CLAUDE.md 記載的接上阻礙是「`download_and_extract_zip()` 的參數順序與現有呼叫端
不相容」—— 實測後確認差異只有一個：新版在第 2 位多了 `headers`。
`find_download_links` 的回傳結構 `{href: (file_type, page_topic)}` 兩版完全相同。

## 決策

**抓取層必須把故障分成三類，並讓每一類走不同的路徑：**

| 類別 | 處置 | 理由 |
| --- | --- | --- |
| **暫時性故障** —— 5xx、429、連線錯誤、`OVER_QUERY_LIMIT`、`UNKNOWN_ERROR` | 退避重試；耗盡後 `raise` | 重跑可能成功，值得在函式層先試 |
| **永久性故障** —— 4xx（429 除外）、`REQUEST_DENIED`、`INVALID_REQUEST` | 立即 `raise`，不重試 | 金鑰或參數錯誤，重試只是浪費配額並延後告警 |
| **查無資料** —— `ZERO_RESULTS`、`NOT_FOUND` | 回傳 `None`，由呼叫端計入失敗清單 | 這不是故障。Google Maps 找不到某個夜市是常態；`NOT_FOUND` 是 Place Details 專有的「place_id 已失效」 |

### 九項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | **切換到 `crawling_utils`**，`e_crawling_traffic_accident` 的三支重複實作刪除 | 不切換的話，本輪的修正要在兩套程式碼各做一次。實測確認兩版回傳結構相容，阻礙只是 `headers` 參數的位置 |
| 2 | 新增 `tenacity` 依賴實作重試 | 見下節「為什麼不是只靠 Airflow 的 retries」 |
| 3 | Google `status` 採三分法（見上表），並以**成對的例外型別**表達 | HTTP 狀態碼看不見 body 裡的失敗，必須顯式檢查 `status`。型別區分不只是命名 —— `retry_if_exception_type` 需要可辨識的型別才能只重試暫時性故障 |
| 4 | `e_crawling_nightmarket` 失敗率 **超過 50%** 即 `raise`，常數 `MAX_FAILURE_RATE = 0.5` | 「一個都沒拿到才失敗」漏掉「維基頁面改版導致大量名稱對不上」的情境。50% 是可調的門檻，寫成具名常數而非魔術數字 |
| 5 | **不加主動節流** | Places API 的主要限制是每日配額，QPS 上限寬鬆。固定 `sleep` 的間隔值沒有依據，且會無條件拖慢 600 次呼叫。`OVER_QUERY_LIMIT` 發生時由退避重試回應，這是有依據的 |
| 6 | **`verify` 參數化，預設 `True`**；停用者需明確傳入並自行記錄警告 | 停用 SSL 驗證是 MITM 風險，不該由共用工具替所有呼叫端決定。全專案只有 `data.gov.tw` 需要停用，由 `e_crawling_traffic_accident` 的 `VERIFY_SSL = False` 具名承擔 |
| 7 | 重試參數：`stop_after_attempt(3)` + `wait_exponential(multiplier=2, max=10)` | 最壞約 12 秒，不會卡住 `d05` 的 `execution_timeout`；上層還有 Airflow 的 `retries` 接手 |
| 8 | 修 `crawling_utils.download_csv` 的 `headers={}` 硬編碼，補上 `headers` 參數 | 切換的前置條件 —— `data.gov.tw` 可能拒絕沒有 User-Agent 的請求 |
| 9 | `e_crawling_*` 協調函式的回傳型別由 `list[str] | None` 收緊為 `list[str]` | 子決策 1、3 之後，失敗一律 `raise`，`None` 不再是可能的回傳值 |
| 10 | **`crawling_utils` 只留通用能力**：`find_download_links` 搬到 `e_crawling_traffic_accident`，`download_and_extract_zip` 的檔名篩選改成 `filename_filter` 參數，`_fetch_soup` 公開為 `fetch_soup` | 見下節「util 與 e_ 的分界線」 |
| 11 | **刪除 `iterate_crawling_similar_urls`** | 見下節 —— 模板不是程式碼 |
| 12 | **SSL 警告搬到 `e_crawling_traffic_accident`** | 只有 data.gov.tw 需要 `verify=False`。放在 `crawling_utils` 會讓每個 import 它的模組都噴一行不符事實的警告 |
| 13 | **請求失敗的日誌級別依「是否還會被重試」而定** | 見下節「重試與日誌級別」 |

### 為什麼不是只靠 Airflow 的 `retries`

DAG 層已經設了 `retries: 2~3`，理論上「什麼都不做」也有重試。但兩者的粒度差三個數量級：

| | Airflow task `retries` | 函式層重試 |
| --- | --- | --- |
| 重試單位 | 整個 task | 單一 HTTP 請求 |
| 300 個夜市查到第 299 個時 429 | 前 298 次成功的呼叫**全部重做**，配額再燒一輪 | 只重試那一次 |
| 五個年度頁面第 3 個 503 | 已下載的兩個大 zip 重下載 | 只重試那一個請求 |
| 退避間隔 | `retry_delay=10 分鐘`（固定） | 2 → 4 → 8 秒（指數） |
| 對永久性故障 | 一樣重跑，浪費 30 分鐘才紅燈 | 立即 `raise`，馬上告警 |

暫時性故障的典型持續時間是**秒級**，用十分鐘的固定間隔去對付它，
代價是把一次 429 放大成整批重跑。兩層是互補而非重複：
函式層吸收秒級抖動，Airflow 層處理「整個來源掛了半小時」。

### 例外型別：成對，且共用基底

```
PlacesAPIError(RuntimeError)
├── TransientPlacesAPIError   ← tenacity 只重試這個
└── PermanentPlacesAPIError
```

一度只為暫時性失敗定義型別，永久性失敗直接 `raise RuntimeError`。
那是錯的：`TransientPlacesAPIError` 是 `RuntimeError` 的子類，
呼叫端寫 `except RuntimeError` 想攔永久性失敗時會**連帶攔到暫時性的**，
兩者的區分只剩訊息字串。

型別成對之後：
- tenacity 用 `retry_if_exception_type(TransientPlacesAPIError)` 精確挑出要重試的；
- 呼叫端可以用 `PlacesAPIError` 一次攔下所有 API 層失敗，也可以分開處理；
- 「這個失敗該不該重試」寫在型別裡，而不是靠讀訊息判斷。

**兩種永久性失敗的訊息必須分開**。依官方文件，`REQUEST_DENIED` 是授權問題
（金鑰無效、API 未啟用），`INVALID_REQUEST` 則通常是缺少必要參數 ——
那是**呼叫端自己的程式錯誤**。用同一句「請檢查 API 金鑰」會把排查方向帶偏。

### 分類表放在哪：一張表，不掛在例外類別上

分類知識收在單一的模組層對照表，而**不是**掛成例外類別的屬性：

```python
API_STATUS_ERRORS: dict[str, tuple[type[PlacesAPIError], str]] = {
    "OVER_QUERY_LIMIT": (TransientPlacesAPIError, "配額或 QPS 超限"),
    "REQUEST_DENIED":   (PermanentPlacesAPIError, "金鑰無效、API 未啟用或超出授權範圍"),
    ...
}
```

把 status 清單掛進例外類別（`TransientPlacesAPIError.STATUSES = {...}`）看似內聚，
實則有三個問題：

1. **職責錯位** —— 例外的職責是表示一個錯誤，不是記住 API 協定有哪些 status。
2. **不對稱無法消除** —— `ZERO_RESULTS` / `NOT_FOUND` 不是錯誤，沒有例外類別可掛。
   分類表會被拆到兩處，讀者想知道「這個 status 怎麼處理」得找兩個地方。
3. **暫時性失敗不需要 per-status 訊息** —— `OVER_QUERY_LIMIT` 與 `UNKNOWN_ERROR`
   對使用者的處置完全相同（等重試）。為了對稱而各寫一句沒人讀的字串是虛工。

判斷函式因此改名為 `_has_data()` 並**回傳 `bool`** —— 三類的處置由
「一張錯誤表 + 一個布林回傳值」完整表達，`_NOT_FOUND_STATUSES`
退化為函式內部細節，不再是與另兩者平級的公開常數。

### 兩種失敗來源，一個判斷式

`search_place_id` / `get_place_details` 有兩種暫時性失敗來源：

| 來源 | 例外 | 判斷依據 |
| --- | --- | --- |
| 傳輸層 —— 連線斷、Google 回 5xx／429 | `requests` 的例外 | `crawling_utils.is_transient()` |
| body 層 —— HTTP 200 但 `status` 是 `OVER_QUERY_LIMIT` | `TransientPlacesAPIError` | 型別 |

**兩個條件併成單一判斷式，不疊兩層裝飾器。**

```python
def _should_retry(exc: BaseException) -> bool:
    return isinstance(exc, TransientPlacesAPIError) or is_transient(exc)
```

疊兩層（`@retry_on_transient_api` + `@retry_on_transient`）行為其實是對的 ——
兩者的 `retry=` 條件互斥，不會互相觸發。但：

- **重試上限變成隱患** —— 兩層各有 `stop_after_attempt(3)`。今天靠條件互斥
  維持 3 次，哪天有例外同時滿足兩個條件就會變成 3×3 = 9 次。
- **可讀性差** —— 讀者必須推敲兩層裝飾器的交互作用，才能回答
  「這個函式到底會重試幾次」。

為此把 `crawling_utils._is_transient` 改為公開的 `is_transient` ——
它現在是一個可組合的判斷函式，讓有額外重試條件的模組併進自己的判斷式，
而不是被迫再包一層。

### util 與 `e_` 的分界線：通用能力 vs 資料來源專屬

分界的判準是**「換一個資料來源，這段程式碼還成立嗎」**：

| 程式碼 | 判定 | 歸屬 |
| --- | --- | --- |
| 重試、故障分類、`fetch_soup`（抓一頁 + 解析） | 換來源仍成立 | `crawling_utils` |
| zip 的 cp437／cp950 檔名亂碼處理 | 換來源仍成立（亞洲 zip 的通病） | `crawling_utils` |
| `download_csv`（下載 → 存檔） | 換來源仍成立 | `crawling_utils` |
| `#__nuxt > ...` 選擇器、「下載檔案」regex | 只對 data.gov.tw 成立 | `e_crawling_traffic_accident` |
| `"A1" in filename or "A2" in filename` | 只對交通事故資料成立 | `e_crawling_traffic_accident`，經 `filename_filter` 參數傳入 |

`download_and_extract_zip` 原本整支被視為專屬，實際上只有**一行**是專屬的
（原註解自己就寫著 `Adjust ".csv", "A1", "A2" as needed.`）。
整支搬走會把通用的亂碼處理一起帶走，下一個 zip 下載需求就要重寫，
因此只把那一行外提為參數。

### 不留「通用模板」函式

`iterate_crawling_similar_urls` 是一支零呼叫端的範本函式，函式體大半是註解，
回傳 `result["your_key"] = "value_you_find"`。本輪**直接刪除**，
且不為搬走的函式各留一份模板。

它自己就是這個做法的實驗結果：真實的 `find_download_links` 這輪加了重試、
抽出 `fetch_soup`、移除靜默跳過，模板一行都沒跟上 —— **已經分岔了**。
留著它只會讓照著寫的人產出一份沒有重試、會靜默跳過失敗的爬蟲。

模板的價值是**文件價值**，該由文件承載：`fetch_soup` 的 docstring 裡放一段
urls loop 的用法範例，說明「解析規則因站而異，屬呼叫端職責」。
放成函式只會讓 linter 與測試把它當程式碼看待，卻沒有任何執行保證 ——
這也正是 ADR-0001 決策 5（凍結三檔拖三輪才刪）與本 ADR 子決策 1
（刪除重複實作）共同的教訓。

### SSL 憑證驗證：預設安全，停用需具名

`verify=False` 原本硬編碼在 `crawling_utils` 的三支函式裡 ——
共用工具替所有呼叫端決定了「不驗證憑證」。

一度只把警告搬到 `e_crawling_traffic_accident`，但那是半套：
**警告在 A 模組、行為在 B 模組**。第二個呼叫端接上 `crawling_utils` 時，
會在不知情的情況下也停用驗證，而警告不會出現。

最終形狀是**預設安全 + 停用具名**：

```python
# crawling_utils —— 不替呼叫端決定
def fetch_soup(url, headers, *, verify: bool = True) -> BeautifulSoup: ...

# e_crawling_traffic_accident —— 全專案唯一停用處
VERIFY_SSL = False    # data.gov.tw 的憑證鏈有問題
urllib3.disable_warnings(urllib3.exceptions.InsecureRequestWarning)
logger.warning("SSL certificate verification is disabled (verify=False)...")
```

停用的**決定、原因、警告**三者同居一處，且全 repo 只有一個 `VERIFY_SSL = False`。
三支對外函式的預設值必須一致，否則會有安全破口 —— 由
`test_兩支下載函式同樣預設驗證` 把關。

### 重試與日誌級別

引進重試後產生一個 ADR-0003 沒涵蓋的互動：**同一個錯誤在時間上重複**。
一次 503 會讓內層的 `logger.error` 執行三次，監控上放大成三筆告警，
但實際只有一次最終失敗。

（ADR-0003 子決策 5 處理的是「同一錯誤被**多層**重複記錄」，不是這個。）

**規則：請求失敗的日誌級別，依「這次失敗是否還會被重試」而定。**

```python
def _log_attempt_failure(message: str, exc: BaseException) -> None:
    if is_transient(exc):
        logger.warning(f"{message}（暫時性故障，將視情況重試）")
    else:
        logger.error(message)
```

| 情境 | 級別 | 理由 |
| --- | --- | --- |
| 5xx／429／連線錯誤 | `warning` | 可能自癒，用 ERROR 會誤觸告警 |
| 其餘 4xx | `error` | 不重試，這一筆就是確定的失敗 |
| 非 `requests` 例外（解壓縮、寫檔） | `error` | 同上 —— 不在重試範圍內 |

最終失敗的完整 traceback 仍由呼叫端負責：DAG 路徑上由 Airflow 自動輸出
（ADR-0003 子決策 5 的既有規則）。

### 為什麼是 tenacity 而不是 urllib3 的 `Retry`

`requests.Session` + `HTTPAdapter(max_retries=Retry(...))` 不需新增依賴，
但它**看不見 `OVER_QUERY_LIMIT`** —— 那是 HTTP 200，重試邏輯在傳輸層，
而失敗寫在 body 裡。本輪最重要的病灶正好是它，
所以無論如何都需要一個能對「回傳值」做判斷的重試機制。

既然如此，就用同一套機制處理兩者，而不是讓 codebase 同時存在
「傳輸層重試」與「語意層重試」兩種寫法。

## 後果

- `d02` / `d03` 在 `data.gov.tw` 回 503 時，Airflow log 的第一行是
  `HTTPError: 503`，而不是 `TypeError: 'NoneType' object is not iterable`。
- `d05` 在 API 金鑰失效時**立即失敗**（`REQUEST_DENIED` 不重試），
  而不是跑完 600 次呼叫後回傳一個空 json。
- 暫時性的 429 / 503 由函式層在秒級吸收，不再放大成整批 task 重跑。
- `src/util/` 與 `src/task/` 不再有同名的兩套抓取實作；
  `crawling_utils` 從零呼叫端變成 `e_crawling_traffic_accident` 的唯一依賴。
- `crawling_utils` 內**沒有任何 data.gov.tw 的痕跡**，且每一支函式都可執行、可測試
  （不再有零呼叫端的範本）。
- SSL 警告只在真正停用憑證驗證的模組出現；`e_crawling_nightmarket`
  （憑證驗證正常開著）不再噴出不符事實的警告。
- 新增一個生產依賴（`tenacity`）。

### 誠實的限制

- **50% 的失敗率門檻是選出來的，不是算出來的**。它擋得住「金鑰失效」與
  「維基頁面大改版」，但擋不住「三成夜市查不到」這種慢性劣化。
  若日後發現長期落在 40% 上下，該做的是查明原因，而不是調高門檻。
- **`data.gov.tw` 的憑證驗證仍是停用的**。本輪讓這個決定變得明確且可搜尋
  （`VERIFY_SSL = False` 一處），但沒有解決憑證鏈本身的問題。
  真正的修法需要確認該站台的憑證能否通過驗證，屬後續工作。
- **`filename_filter` 是為單一呼叫端設計的參數**。嚴格說違反「不為尚未存在的需求
  設計介面」，這裡的取捨是：不外提就得把通用的 cp437 亂碼處理一起搬走。
- **重試會拉長失敗的回饋時間**。最壞情況下，一個永久性的 5xx（例如來源網站
  下架）要等 3 次嘗試約 12 秒才會 `raise`。這是刻意的取捨 ——
  5xx 無法從回應本身判斷是暫時或永久。
- `tenacity` 的重試發生在函式內部，**呼叫端看不到「重試過幾次」**。
  診斷時需要看 log（tenacity 的 `before_sleep_log` 會記錄）。
