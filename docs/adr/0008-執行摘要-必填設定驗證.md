**範圍收斂**：候選 7 原本的描述是「設定散在多個 `load_dotenv()` 與模組層全域變數，

---

## 一、病因定義

候選 7 的病因收斂為：

> **必填設定缺失時不會有人說話，直到下游以另一種面貌失敗 ——
> 錯誤訊息指向錯的方向。**

三個可檢驗的判準：

1. **缺設定不報錯** —— `os.getenv` 回 `None`，程式繼續往下走
2. **症狀掩蓋原因** —— 下游的錯誤訊息與真正的原因無關
3. **檢查位置與使用位置不一致** —— 有檢查的路徑與實際用到設定的路徑不同

實際掃描的結果：

| 設定 | 缺失時的實際錯誤 | 真正的原因 | 判準 |
| --- | --- | --- | --- |
| `MYSQL_USER` / `MYSQL_PASSWORD` | `Access denied for user 'None'` | 環境變數少一行 | 1、2 |
| `REDIS_PASSWORD` | `NOAUTH Authentication required` | 同上 | 1、2 |
| `GOOGLE_MAP_API_KEY` | `REQUEST_DENIED` → 經 ADR-0006 分類後訊息說「金鑰無效」 | **根本沒有金鑰** | 1、2、3 |

第三項還多一個問題：`e_crawling_nightmarket()` 函式內有檢查
（`if not API_KEY: raise ValueError("找不到 API 金鑰...")`），
但 `search_place_id()` 與 `get_place_details()` 直接使用 `API_KEY`，
單獨呼叫它們時沒有任何檢查。

### grilling 階段推翻的兩個方案

**（一）「`load_dotenv()` 集中到 DAG d01～d06」—— 查證後否決**

這個方案有兩個致命問題：

- **執行順序來不及**：DAG 檔在第 15 行左右就 `from src.util.mysql_utils import ...`，
  這一行會執行 `mysql_utils` 的模組層（含 `os.getenv`）。
  `load_dotenv()` 無論寫在 import 之後或 `@dag` 函式體內都太晚。
- **非 DAG 入口沒人載入**：`python -m src.task.xxx`（CLAUDE.md 記載的用法）、
  `streamlit run`、`pytest` 三條路徑都沒有 DAG。

**（二）「`load_dotenv()` 也放到 `crawling_utils` / `c_db` / `c_data_service`」—— 查證後否決**

這三支**完全不讀任何設定**：

| 模組 | 讀設定嗎 | import 鏈 |
| --- | --- | --- |
| `crawling_utils` | 不讀 | 只 import `logger_crtx` |
| `c_db` | 不讀 | → `mysql_utils`（它的 `load_dotenv()` 會先跑） |
| `c_data_service` | 不讀 | → `c_db`、`redis_utils`（同上） |

加上去是**執行不到的**。

**結論**：`load_dotenv()` 的位置**本來就是對的** ——
只有真正讀設定的三個模組才呼叫它。而且它在容器中是 no-op
（compose 用 `env_file` + `environment` 注入，Cloud Run 用 `--set-env-vars`），
真正有作用的場合只有地端開發，且冪等、找不到檔案不報錯。

**這是本輪最有價值的產出之一：確認了一個看起來像問題的東西不是問題。**

## 三、實際改動

### MySQL：一支檢查，三個入口

```python
# src/util/mysql_utils.py
def _require_credentials() -> None:
    if not username:
        raise ValueError("未設定 MYSQL_USER，請檢查環境變數設置")
    if not password:
        raise ValueError("未設定 MYSQL_PASSWORD，請檢查環境變數設置")
```

呼叫點三處：`_create_engine()`、`get_pymysql_conn_to_mysql()`、
`get_pymysql_conn_to_mysql_multistatement()` —— 它們共用同一組帳密，
檢查抄三次是 ADR-0005 剛消滅過的樣板。

### Redis：在建立連線池時

```python
# src/util/redis_utils.py — _get_redis_pool()
if not redis_password:
    raise ValueError("未設定 REDIS_PASSWORD，請檢查環境變數設置")
```

### Google Places API：擴大到兩支 API 函式

```python
# src/task/e_crawling_nightmarket.py
def _require_api_key() -> None:
    if not API_KEY:
        raise ValueError("未設定 GOOGLE_MAP_API_KEY，請檢查環境變數設置")
```

呼叫點三處：`search_place_id()`、`get_place_details()`、`e_crawling_nightmarket()`。
最後一處原本是自成一格的寫法（`"找不到 API 金鑰，請確認 .env 檔"`），
一併收攏成同一句。

### 語意變化摘要

| 情境 | 改動前 | 改動後 |
| --- | --- | --- |
| 缺 `MYSQL_USER` | `Access denied for user 'None'` ← 排查方向：帳號權限 | `未設定 MYSQL_USER，請檢查環境變數設置` |
| 缺 `REDIS_PASSWORD` | `NOAUTH Authentication required` | `未設定 REDIS_PASSWORD，請檢查環境變數設置` |
| 缺 `GOOGLE_MAP_API_KEY` | `REQUEST_DENIED` →「金鑰無效」 | `未設定 GOOGLE_MAP_API_KEY，請檢查環境變數設置` |
| 單獨呼叫 `search_place_id()` | 無檢查，白花一次 API 配額 | 送出請求前就擋下 |
| 缺設定時 import 模組 | 正常（讀成 `None`） | 正常（驗證在使用時，不在模組層） |

### 一個實作中發現的問題：測試原本依賴本機環境

加上驗證後測試仍然全綠 —— 但那是因為**本機有設定檔**。實測確認：

```
API_KEY 有值: True
MYSQL_USER 有值: True
REDIS_PASSWORD 有值: True
```

在沒有設定的環境（CI、剛 clone 的機器）會失敗。這是本輪引入的問題，
處理方式是讓受影響的測試**明確宣告自己的前提**：

```
test_util_mysql_engine_cache.py     新增 _fake_credentials autouse fixture
test_task_e_crawling_nightmarket.py 新增 _fake_api_key autouse fixture
```

並以一個臨時的 `conftest.py` 把三個模組層設定強制清空，重跑驗證：

```
（模擬完全沒有設定的環境）
140 passed
```

**測試現在不依賴任何本機設定。**

### 範本檔的一致性：已核對，無缺漏

環境變數共 15 個，兩群互不重疊：

| 群 | 數量 | 內容 |
| --- | --- | --- |
| Python 讀取（本輪範圍） | 9 | `MYSQL_HOST/PORT/USER/PASSWORD/DATABASE`、`REDIS_HOST/PORT/PASSWORD`、`GOOGLE_MAP_API_KEY` |
| 基礎設施專用 | 6 | `MYSQL_AIRFLOW_DATABASE`、`MYSQL_ROOT_PASSWORD`、`AIRFLOW_SECRET_KEY`、`AIRFLOW_ADMIN_USER/PASSWORD/EMAIL` |

範本檔與程式碼的 `os.getenv` 完全吻合，**無缺漏也無多餘**。
第二群雖然 Python 從不讀取，但是 Airflow 啟動與建立自身 metadata database
的必要條件 —— 「不進 Python 的必填清單」與「可以從範本檔刪除」是兩件事。

以及沿用前六輪的匯入健檢：`src/` 底下 35 個模組全部可獨立匯入。

## 五、同病因但尚未修復的位置

候選 7 的病因（必填設定缺失時不報錯）在 `src/` 內已無殘留。

### A. 刻意未處理

| 位置 | 現象 | 理由 |
| --- | --- | --- |
| `MYSQL_HOST` / `MYSQL_PORT` / `REDIS_HOST` / `REDIS_PORT` | 有預設值（`localhost` / `3306` / `6379`），缺了會靜默連往本機 —— 在 Cloud Run 上必定失敗且訊息不提設定 | 有預設值代表「缺了也能運作」，列入必填會讓地端開發更囉唆 |
| `port = os.getenv("MYSQL_PORT", 3306)` | 預設是 `int`、環境變數來的是 `str`，型別隨「有沒有設定」而變 | 後續 `int(port)` 蓋掉了；`_create_engine()` 的 f-string 直接內插不受影響 |
| 設定仍在模組層讀取 | import 時凍結；測試要換設定需 reload 或 `monkeypatch.setattr` | 本輪只加驗證，不改讀取時機 |
| `MYSQL_DATABASE` 在 6 處讀取 | `exec_mart_sql` + 五支 DAG | 那是「由呼叫端決定操作哪個資料庫」的參數傳遞，不是模組層設定 |
| 範本檔中 compose 專用的 6 個變數 | Python 從不讀取，故不進必填清單 | **不可刪除** —— Airflow 靠它們啟動並建立自身的 metadata database |

## 六、誠實的評估

**這輪的價值主要是排查時間，不是正確性。** 正式部署由 GitHub Secrets 注入，
缺設定的情境不常見；受益最大的是地端第一次設定環境的人，
以及 `.env` 少一行時的排查者。

**但本輪有一個超出預期的收穫**：查證過程確認了「三處 `load_dotenv()` 重複」
與「設定分散」其實不是問題 —— 前者的位置本來就是對的，
後者的規模（9 個設定、3 個獨立子系統）撐不起一層抽象。
候選 7 從「設定分散」收斂成「零驗證」，避免了為 9 個設定引入
`dataclass` + `get_settings()` 這種與規模不相稱的結構。

**若日後要做設定層**，觸發點應該是：設定數量顯著成長、
或出現需要在執行期切換設定的需求（例如讀寫分離、多租戶）。
屆時 ADR-0004 的「誠實的限制」已記下 `_ENGINES` 以 `database` 為鍵的前提。
