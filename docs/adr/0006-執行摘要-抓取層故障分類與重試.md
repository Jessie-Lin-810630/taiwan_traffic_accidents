## 一、病因定義

候選 6 的病因是：

> **抓取層沒有把故障分類，暫時性故障、永久性故障與「查無資料」
> 共用同一條回傳路徑，於是沒有一種能被正確處置。**

三個可檢驗的判準：

1. **暫時性故障未重試** —— 秒級的 429／503 直接放大成整批 task 失敗
2. **永久性故障未快速失敗** —— 金鑰失效仍跑完全部呼叫
3. **故障與「查無資料」共用回傳值** —— `None` 同時代表兩者

實際掃描的結果：

| 位置 | 判準 1 | 判準 2 | 判準 3 |
| --- | --- | --- | --- |
| `download_and_extract_zip` / `download_csv` | ✓ 零重試 | — | ✓ 非 200 → `return None` |
| `find_download_links` | ✓ 零重試 | — | ✓ 非 200 靜默跳過該 url |
| `search_place_id` / `get_place_details` | ✓ 零重試 | ✓ `REQUEST_DENIED` 被當成「找不到」 | ✓ 七種 `status` 全歸為 `None` |
| `e_crawling_nightmarket` | — | — | ✓ 全數失敗仍回傳空 json 路徑 |

淨結果：

- **`data.gov.tw` 回 503 時**，呼叫端 `.extend(None)` 拋
  `TypeError: 'NoneType' object is not iterable`；真正的狀態碼只在上一行 log。
- **Google API 金鑰過期時**，300 個夜市全部「找不到」，
  `e_crawling_nightmarket` 成功回傳一個空 json，失敗率只出現在最後一行 log。

### 四項實作中浮現的調整

**（一）重試單位是單一請求**

原案只說「加上重試」。若把裝飾器套在 `find_download_links` 上，第三個頁面 503
會導致**前兩個已成功的頁面重抓**，與 ADR 中「重試單位是單一 HTTP 請求」矛盾。
因此把單頁抓取抽成 `fetch_soup()` 並只在它上面套重試。

**（二）例外型別必須成對**

一度只為暫時性失敗定義型別、永久性直接 `raise RuntimeError`，
但 `TransientPlacesAPIError` 本身就是 `RuntimeError` 的子類 ——
呼叫端 `except RuntimeError` 會連帶攔到暫時性失敗。
改為兩個型別共用 `PlacesAPIError` 基底。

連帶修正兩處：`REQUEST_DENIED`（授權問題）與 `INVALID_REQUEST`（缺少參數，
屬呼叫端的程式錯誤）訊息分開；Place Details 專有的 `NOT_FOUND` 原本會落到
「成功資料回傳」，改為併入「查無資料」。

**（三）兩種失敗來源，一個判斷式**

Google API 的暫時性失敗來自傳輸層（5xx）與 body 層（`OVER_QUERY_LIMIT`）兩處。
一度用兩層裝飾器各管一種，行為雖正確（條件互斥），但兩層各有
`stop_after_attempt(3)`，重試上限靠「條件互斥」維持在 3 次而非 9 次 ——
是個隱患，且讀者得推敲兩層的交互作用。改為單一的 `_should_retry()` 判斷式。

**（四）分層重整** —— 見第三章。

## 三、實際改動

### 分層：util 與 `e_` 的分界線

分界的判準是「換一個資料來源，這段程式碼還成立嗎」。

```
src/util/crawling_utils.py（318 行，零 data.gov.tw 痕跡，全部可執行可測試）
    RETRY_ATTEMPTS / RETRY_WAIT / TRANSIENT_STATUS_CODES
    is_transient()              公開，供呼叫端組合自己的重試條件
    _log_attempt_failure()      級別依「是否還會被重試」而定
    retry_on_transient          共用裝飾器（reraise=True）
    fetch_soup()                抓一頁 + 解析；重試的最小單位
    download_and_extract_zip()  含 cp437/cp950 亂碼處理；篩選由 filename_filter 決定
    download_csv()
    ── 三支對外函式一律 verify: bool = True，不替呼叫端決定憑證驗證

src/task/e_crawling_traffic_accident.py（324 → 202 行）
    VERIFY_SSL = False                    ← 全專案唯一停用憑證驗證之處
    urllib3.disable_warnings + SSL 警告   ← 決定、原因、警告三者同居一處
    _DOWNLOAD_LINK_SELECTOR               ← data.gov.tw 的 CSS 選擇器
    find_download_links()                 ← 專屬解析，自 util 搬回
    _is_accident_csv()                    ← A1/A2 篩選，傳給 filename_filter
    _prepare_save_dirs() / _timestamped_name()
    兩支協調函式

已刪除：iterate_crawling_similar_urls（零呼叫端的範本函式）
```

`download_and_extract_zip` 原本整支被視為專屬，實際上只有**一行**是專屬的
（原註解自己就寫著 `Adjust ".csv", "A1", "A2" as needed.`）；
cp437/cp950 亂碼處理是通用的亞洲 zip 通病，整支搬走會把它一起帶走。

**不留通用模板**：`iterate_crawling_similar_urls` 自己就是模板做法的實驗結果 ——
真實的 `find_download_links` 這輪加了重試、抽出 `fetch_soup`、移除靜默跳過，
模板一行都沒跟上。模板的價值改由 `fetch_soup` 的 docstring 承載。

### 重試基礎設施

```
RETRY_ATTEMPTS = 3
RETRY_WAIT = wait_exponential(multiplier=2, max=10)
TRANSIENT_STATUS_CODES = {429, 500, 502, 503, 504}
```

`reraise=True` 讓重試耗盡時拋出的是原始的 `HTTPError`，
而非 tenacity 的 `RetryError` —— 呼叫端不必知道中間有重試這回事。

### Google Places API 的故障分類

```
src/task/e_crawling_nightmarket.py
    PlacesAPIError                    API 層失敗的共同基底
    ├── TransientPlacesAPIError       tenacity 只重試這個
    └── PermanentPlacesAPIError
    API_STATUS_ERRORS                 status → (例外型別, 排查提示) 的單一對照表
    _NOT_FOUND_STATUSES               {ZERO_RESULTS, NOT_FOUND}，_has_data() 的內部細節
    MAX_FAILURE_RATE = 0.5
    _has_data()                       三分法的判斷點，回傳 bool
    _should_retry()                   傳輸層 + body 層兩種來源，一個判斷式
```

**分類表收成一張，不掛在例外類別上**：曾考慮把 status 清單做成例外類別的屬性，
但那會讓例外知道它不該知道的 API 協定細節，且 `ZERO_RESULTS` / `NOT_FOUND`
不是錯誤、沒有類別可掛，分類表反而被拆到兩處。

### 日誌級別

引進重試後產生一個 ADR-0003 沒涵蓋的互動：**同一個錯誤在時間上重複**。
一次 503 讓內層的 `logger.error` 執行三次，監控上放大成三筆告警。

```
改動前 —— HTTP 503：            改動後 —— HTTP 503：
ERROR   HTTP 回應異常            WARNING HTTP 回應異常（暫時性故障，將視情況重試）
WARNING 第 1 次嘗試失敗          WARNING 第 1 次嘗試失敗
ERROR   HTTP 回應異常            WARNING HTTP 回應異常（暫時性故障，將視情況重試）
WARNING 第 2 次嘗試失敗          WARNING 第 2 次嘗試失敗
ERROR   HTTP 回應異常            WARNING HTTP 回應異常（暫時性故障，將視情況重試）
→ 3 個 ERROR                     → 0 個 ERROR

                                改動後 —— HTTP 404：
                                ERROR   HTTP 回應異常
                                → 1 個 ERROR，且不重試
```

比「一律降 warning」更精確：永久性故障仍保有 ERROR，
最終失敗不會完全沒有 error 級別的記錄。

### 語意變化摘要

| 情境 | 改動前 | 改動後 |
| --- | --- | --- |
| `data.gov.tw` 回 503 | 立即 `return None` → 呼叫端 `TypeError` | 重試 3 次後拋 `HTTPError` |
| `data.gov.tw` 回 404 | 同上 | 立即拋 `HTTPError`，不重試 |
| 五個年度頁面有一個失敗 | 靜默少一年份，流程照常成功 | 中止並拋出 |
| Google `OVER_QUERY_LIMIT` | 當成「找不到地點」 | 重試 3 次後拋 `TransientPlacesAPIError` |
| Google `REQUEST_DENIED` | 當成「找不到地點」 | **立即**拋 `PermanentPlacesAPIError`，不重試 |
| Google `INVALID_REQUEST` | 當成「找不到地點」 | 同上，但訊息指向參數而非金鑰 |
| Google `NOT_FOUND`（place_id 失效） | **當成成功資料回傳** | 回 `None`，計入失敗清單 |
| Google `ZERO_RESULTS` | 回 `None` | 回 `None`（不變，這不是故障） |
| 300 個夜市全查不到 | 回傳空 json 路徑 | 拋 `ValueError`（失敗率 100% > 50%） |
| 匯入 `e_crawling_nightmarket` | 噴一行「SSL 驗證已停用」（不符事實） | 靜默 —— 它的憑證驗證正常開著 |
| 新的呼叫端接上 `crawling_utils` | 在不知情下停用憑證驗證，且無警告 | 預設 `verify=True`；要停用得明確傳入 |
