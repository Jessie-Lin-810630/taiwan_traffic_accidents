# ADR-0015：事故事實表的載入以「檔案批次」為單位

- 日期：2026-08-09
- 狀態：已採納
- 範圍：`dags/d03_track_hist_traffic_accidents.py`
- 相關：[ADR-0014 事故主鍵由事故內容決定](./0014-事故主鍵由事故內容決定而非單次run排序名次.md)（批號不得進入任何鍵，是本 ADR 能成立的前提）、
  [ADR-0013 天氣抓取的斷點以觀測點乘月為單位](./0013-天氣抓取的斷點以觀測點乘月為單位.md)（同樣用 `expand()` 切批，併發靠 pool 控管）、
  [ADR-0010 事故 CSV 的讀取契約集中於單一 module](./0010-事故-csv-的讀取契約集中於單一-module.md)（`t_fact_*` 中段查 FK 是刻意保留的，本 ADR 不改它）、
  [ADR-0009 預計算的查詢粒度以批次為單位](./0009-預計算的查詢粒度以批次為單位.md)
- 來源：VM（8 GB RAM）上執行 d03 時發生 OOM，task 被系統殺掉。
  實際爆掉的位置是 `l_fact_accident_human()` 的寫入，
  `task_t_and_l_dim_tables` 與 `task_t_and_l_fact_main` 都跑完了

## 名詞

**檔案批次**：一次 `t_` → `l_` 循環所涵蓋的 CSV 檔案集合，預設 2 個檔案。

`CONTEXT.md` 裡「批次」已經有兩個互不相干的意思（天氣的「觀測點 × 月」、
預計算的「夜市集合」）。這是第三個，所以一律寫**檔案批次**，不簡稱「批次」。

## 背景

### 病因：一次 run 的記憶體需求與機器容量無關

`t_fact_accident_human()` 與 `t_fact_accident_env()` 的結構是「逐檔讀進 list →
`pd.concat` → 查外鍵 → 回傳整份 DataFrame」，`d03` 再把這份整份 DataFrame 交給
`l_`。於是**記憶體佔用正比於 `e_` 階段抓回來的檔案總量**，而那個總量由資料來源
決定，跟執行它的機器有多少記憶體沒有任何關係。

峰值出現在**寫入那一刻**，不是 `pd.concat` 那一刻。`upsert_to_table()` 走
`cursor.executemany(dml_str, df.values.tolist())`，而 `df.values.tolist()` 會在
DataFrame 還活著的時候，另外建出一份等量的 Python list of lists。兩份同時存在，
所以 `l_` 的需求比 `t_` 高出約一倍 —— 這與實際觀察到的「dim 與 main 都跑完了，
爆在 `l_fact_accident_human()`」一致。

d02 抓的是今年度至今（7 支 CSV、294 MB）所以撐得住；d03 是五年回補，同一段程式碼
就爆掉。這不是 d03 特有的缺陷，是同一個結構在較大的輸入下顯露出來。

### 量到的數字

2026-08-09 在本機（macOS、Python 3.12、pandas）量測，`data/processed` 下
d03 會拿到的 65 個檔案：

| 數字 | 值 | 等級 | 怎麼來的 |
| --- | --- | --- | --- |
| d03 的 `pathlist` 檔案數 | 65 | **實測** | 五年 ×（12 支 A2 + 1 支 A1） |
| 同上，磁碟總量 | 2.6 GB | **實測** | `du -ch` |
| 同上，總列數 | 4,359,391 | **實測** | `wc -l` |
| 讀單一檔案的 peak RSS（human） | 479 MB | **實測** | 47 MB 的 `114年度A2交通事故資料_5.csv` |
| 讀單一檔案的 peak RSS（env） | 576 MB | **實測** | 同一個檔案 |
| 單檔讀完後保留的 DataFrame（human） | 78 MB / 74,952 列 | **實測** | `memory_usage(deep=True)` |
| 單檔讀完後保留的 DataFrame（env） | 98 MB / 74,952 列 | **實測** | 同上 |
| 每列成本（human / env） | 1.04 KB / 1.31 KB | 算術 | 由上兩列相除 |
| 全量 concat 後的保留量（human） | 約 4.5 GB | **推算** | `4,359,391 × 1.04 KB` |
| 全量 concat 後的保留量（env） | 約 5.7 GB | **推算** | `4,359,391 × 1.31 KB` |
| `df.values.tolist()` 單列大小（human） | 1,320 bytes | **實測** | `sys.getsizeof` 逐欄加總 |
| 同上，相對於 DataFrame 的倍率 | 約 1.2 倍 | 算術 | 94 MB / 78 MB。**不是數倍** —— object 欄位在 pandas 裡本來就存 Python `str`，`tolist()` 只多建了 list 與指標 |
| 全量寫入時 `tolist()` 的量（human） | 約 5.4 GB | **推算** | `4,359,391 × 1,320 bytes` |
| VM 記憶體 | 8 GB | **已知** | GCP VM 規格 |
| `fact_accident_main` 列數 | — | **未量測** | 每個檔案批次都要查一次全表，見〈後果〉 |

**單檔 peak RSS 479 MB、但保留下來只有 78 MB**，兩者差 6 倍。差額是
`read_traffic_accident_file()` 的 `pd.read_csv(..., skipfooter=2, engine="python")`
造成的：python engine 為了 `skipfooter` 要逐列建 Python 物件、且會把 CSV 的**全部**
欄位都讀進來，`column_map` 挑欄是讀完之後的事。這是**一次性的暫態**，每個檔案
各付一次、讀完就釋放，所以它決定的是「單批的地板」而不是「總量」。

總量由保留下來的部分決定，而峰值出現在 `l_fact_accident_human()` 的寫入：

```
DataFrame 本身                      約 4.5 GB
df.values 的 object ndarray         約 0.7 GB   （21 欄 × 4.36M × 8 bytes）
df.values.tolist() 的 list          約 5.4 GB
                                  ─────────
                                    約 10.6 GB
```

8 GB 的機器上必然 OOM，**與有沒有 swap、跑得多慢無關**。env 的 DataFrame 更大
（5.7 GB），但它排在 human 之後，跑不到就先掛了。

## 決策

### 一、檔案批次 = 2 個 CSV，`t_` → `l_` 每批各跑一次

`d03` 把 `pathlist` 切成每 2 個一組，每組獨立走完
`t_fact_accident_human()` → `l_fact_accident_human()` →
`t_fact_accident_env()` → `l_fact_accident_env()`。

峰值從「正比於總檔案量」變成「正比於 `batch_size`」。

一批之內，記憶體用得最兇的有兩個時刻，要分開看：

**時刻 A —— 讀第 2 個檔案的當下。** 第 1 個檔案已經讀完、留著 78 MB 的
DataFrame，第 2 個檔案正在被 `pd.read_csv(engine="python")` 解析，那一段的
暫態實測 479 MB（env 576 MB）。兩者相加：

```
human   78 + 479 = 約 557 MB
env     98 + 576 = 約 674 MB
```

**時刻 B —— 寫入的當下。** 兩個檔案的 DataFrame 已合併（155 MB／195 MB），
`upsert_to_table()` 再建一份 `tolist()`，實測是 DataFrame 的約 1.2 倍：

```
human   155 + 186 = 約 341 MB
env     195 + 234 = 約 429 MB
```

**A 比 B 大**，所以一批的峰值由讀檔決定，約 560～680 MB。

這件事的用處在於**知道 `batch_size` 往下調沒有意義**：時刻 B 會隨
`batch_size` 等比縮小，時刻 A 不會 —— 那 479 MB 是解析**一個**檔案的成本，
`batch_size=1` 也照付。所以 560～680 MB 是這個實作的地板，
調 `batch_size` 只能往上加，不能往下減。

反過來說，往上調到 4 之前都還被時刻 A 壓著：`batch_size=4` 的時刻 B 是
682 MB（human），才剛追上時刻 A。這是〈尚未決定的事〉說「可以往上調」的依據。

**2 是起手值，不是量出來的最佳值。** 依實跑的 RSS 再調 —— 往上調能減少
〈後果〉提到的重複查詢次數。65 個檔案切 2，得到 33 個檔案批次。

### 二、用 `expand()` 動態展開，不用 task 內迴圈

兩種寫法都能讓峰值正比於 `batch_size`，選 `expand()` 的理由有兩個：

- **記憶體回收是 process 級的硬保證。** 每個 mapped instance 是獨立 process，
  跑完就退出，記憶體必定還給 OS。task 內迴圈是同一個 process，前一輪的
  DataFrame 是否真的還給 OS 取決於 allocator 的行為 —— 這個場景下多半會
  （pandas 的 block 夠大、走 mmap），但「多半會」在一個已經 OOM 過的機器上
  不夠。**這是本輪要解決的問題本身，不能用推測的機制去解。**
- **失敗的那一批可以單獨重跑。** 33 批裡爆掉一批，`clear` 那一格即可；
  task 內迴圈只能整支重跑，等於 2.6 GB 全部重做一遍。

代價是多一個 `task_prep_file_batches`（把 `pathlist` 切成 `list[list[str]]`），
以及 Airflow UI 上多出 33 個 mapped instance。

### 三、併發壓成 1，用 pool

`expand()` 預設會讓 mapped instance 並行，**這會讓事情比現在更糟** ——
33 個 process 同時各佔 600 MB，8 GB 直接見底。所以本決策的一半是把併發壓成 1。

做法是 `pool="accident_load_pool"`，與 d07 的 `weather_api_pool` 同一個路數。

**要限制的東西是 VM 的 8 GB，而那是整台機器共用的**，不是某一支 DAG 私有的。
pool 是跨 DAG 的閘門，形狀正好對上：日後 d02、或決策五提到的 main/dim 也改成
分批時，掛同一個 pool 就不會在同一台機器上疊起來。反過來說，
`max_active_tis_per_dag` 只管單一 DAG 內部，那個範圍比實際的限制條件窄。

**這個 pool 必須先到 Airflow UI 建立、slots 設 1**，跟 `weather_api_pool` 一樣
（`d07:100` 的註解也記了這件事）。**pool 不存在的話 task 不會執行**，
這是實作時最容易漏掉的一步。

d03 是手動觸發的一次性回補（`schedule=None`），把它跑慢不是代價。

### 四、批號不得出現在任何鍵或檔名裡

這是 ADR-0014 的教訓在新脈絡下的重述：**只要鍵的值取決於「這次跑的時候輸入是
什麼、排第幾」，重跑就會產生嵌合資料。** 分批之後，「輸入是什麼」多了一個維度
（這一批有哪些檔案），所以要明確寫下來。

現況已經滿足這條，分批不會破壞它：

- `fact_accident_human` 的唯一鍵是 `row_hash`，由 6 個內容欄位算 SHA-256 而來
- `fact_accident_env` 的鍵是 `accident_id`，ADR-0014 之後由事故內容決定
- 檔案批次的切法是按 `pathlist` 的順序切，切點與資料內容無關

因此**同一個檔案批次在任何時候跑，算出來的鍵都一樣**，upsert 冪等，重跑安全。

### 五、這一輪只改 human 與 env

`task_t_and_l_fact_main` 與 `task_t_and_l_dim_tables` 是同一個病因
（都是 concat 全部 65 檔再一次載入），但這一輪不動：**實際觀察到它們兩個都跑完了**，
OOM 才發生在後面的 `l_fact_accident_human()`。

這與欄數對得上 —— `fact_accident_main` 的對照表只有 10 欄、三張維度表 3～5 欄，
human 是 21 欄、env 是 23 欄。而且維度表在 concat 後會 `drop_duplicates` 收斂成
很小的結果。

它們仍然是「記憶體正比於資料來源給多少」的結構，只是這批輸入還沒撐破。
輸入再長大時會需要同樣處理，屆時**照本 ADR 的四條做即可，是同一個決策的延伸
而非新決策**，不需要新開 ADR。

## 後果

### 正面

- 記憶體峰值從「正比於資料來源給多少」變成「正比於 `batch_size`」，
  由執行它的機器決定，而不是由資料來源決定
- 失敗的粒度從「整批 2.6 GB」縮到「2 個檔案」，且可單獨重跑
- Airflow UI 上看得出跑到第幾批、哪一批失敗

### 負面

- **每個檔案批次都要重查一次全表。** `t_fact_accident_human` 中段會
  `SELECT accident_id, day_id, accident_time, longitude, latitude FROM fact_accident_main`
  （`t_fact_accident_env` 還多查三張維度表）。這是**不隨 `batch_size` 縮小的固定成本**，
  切成 33 批就付 33 次，且同時是時間成本與記憶體成本。
  實際數值取決於 `fact_accident_main` 的列數，**未量測** ——
  它有可能高過決策一算出的 560～680 MB 而成為真正的地板，實跑時要一併看。
- 從 all-or-nothing 變成部分批次已落地。因為鍵是內容決定的（決策四）、
  upsert 冪等，重跑安全，但「跑到一半失敗」現在會留下已寫入的資料，
  而不是什麼都沒有。
- `t_fact_accident_human` 的 `row_hash` 重複計數 log 從全域變成每批一筆，
  用它檢查「這 6 欄是否足以區分不同當事人」時要自己加總。
- `t_fact_accident_env` 的 `drop_duplicates` 只在批內生效。跨批的重複改由
  MySQL 的 upsert 收斂 —— 結果相同，但去重發生在資料庫而不是 pandas。

### 中性

- 三張表的綱要、`t_`/`l_` 六支函式的程式碼都不動，只改 `d03` 的串接方式
- d02 不動。它的輸入是 7 支 CSV、294 MB，沒有這個問題

## 尚未決定的事

- **`batch_size` 的實際值。** 2 是起手，要看實跑的 peak RSS 才知道能不能往上調。
  往上調的收益是減少〈後果〉負面第一項的重複全表查詢。
- **`t_`/`l_` 兩層是否該自己支援分批**（像 `l_fact_hourly_weather(batch_size=50)`
  那樣）。那樣 d02、d03 都自動受惠，但會讓 `t_` 從「純轉換」變成「轉換 + 載入」，
  破壞 `e_`/`t_`/`l_` 的分工。這一輪把分批放在 DAG 這一層，因為分批是**編排**
  的決定，不是轉換邏輯的一部分。
- **`read_traffic_accident_file()` 的 `engine="python"`。** 它是單檔 480 MB 暫態
  的來源。改用 C engine 需要另外處理 `skipfooter=2`（例如讀完再 `iloc[:-2]`），
  能把地板壓低，但那是 ADR-0010 的契約，要另開決策文。
