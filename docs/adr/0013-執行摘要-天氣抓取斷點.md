## 一、病因定義

**續跑的粒度與額度消耗的粒度不一致。**

額度消耗的單位是「觀測點 × 天」，但斷點只記到「觀測點」，而且靠 GCS 上
檔案的存在與否隱式表示。一個觀測點抓了 214 天中的 214 天或 0 天，
在 GCS 上長得一模一樣 —— 沒有任何地方記得「已經涵蓋到哪一天」。

### T-D 的判斷不完整

T-D 認定根源是「當年度不排除既有檔案，等於整年重抓」。**那只是 `else` 那一支。**
`if` 那一支（歷史年份）也是壞的：

```python
# prep_batch_plan() 組出來拿去比對的     → 24-15_121-5.parquet
# e_crawler_weatherapi() 實際存檔的名字  → cralwer_batch_3_24-15_121-5.parquet
# list_parquet() 回傳完整路徑，Path(f).name 取到的是後者
```

`isin(existing_files)` 恆為 False，**排除從來沒有排除掉任何東西**。所以：

- T-D 建議的臨時驗證手段（「暫時讓 d07 走歷史年份那條路跑一次」）不會有效
- **d08 的四年回補同樣壞掉**，它走的就是 `if` 那一支
- 檔名帶 `batch_id`，而批號隨每次 run 的待抓清單浮動，同一觀測點在不同 run
  會落在不同批號，**產生重複檔案**

### 第二個病灶：完成判定用錯了判準

抓取的迄日是 `today - 3`（OpenMeteo 的歷史資料延遲）。若用「月已過去 = 完成」，
1/31 的 run 只抓到 1/28，而 2/03 之後就再也不會有人回頭補 1/29～1/31。
每個月少最後 3 天，一年少 36 天，且檔案在、載入照常，完全看不出來。

這個病灶在舊版不會發作（因為根本沒有月的概念），但切月之後會 —— 屬於
本輪引入的風險，決策三處理掉了。

## 二、決策摘要

八項，完整論證見 ADR-0013。

| # | 決策 | 排除的做法 |
| --- | --- | --- |
| 一 | GCS 檔名承載月份，`batch_id` 退出檔名 | `fact_hourly_weather` 當進度表（inner join 後只剩事故那幾小時，滿是缺口）；新增 `weather_fetch_progress` 表（兩份狀態會分歧） |
| 二 | 切月，不切季 | 季在季末吃掉時限額 77%，補洞疊加會爆掉 |
| 三 | 月 M 完成 ⟺ M 的最後一天 ≤ today − 3 | 「月已過去 = 完成」（見第一章第二個病灶） |
| 四 | 批次 = 50 個觀測點 × 1 個月 | 一個 task 抓完該批所有缺的月（額度浮動，就是現況） |
| 五 | `batch_size` 維持 50 | 調大到 200～300（換不到續跑能力，卻引入未驗證的風險） |
| 六 | `trigger_rule` 放寬成 `all_done`，並記進度 log | 維持 `all_success`（它不是決策，是預設值，且保護不了任何東西） |
| 七 | d08 改 daily schedule，補完後 pause | 併進 d07（需新增額度預算機制，列為下一輪） |
| 八 | 429 的重試策略不變，只更正 docstring | — |

### 實作期新增的一項決定（不在 ADR 正文）

**d07 的 cron 從每 3 天改成每月 3、18 號**（`schedule="00 07 3,18 * *"`）。

ADR-0013 的決策二說「當前月每次 run 整段重抓覆蓋」，但沒有規定「每次」有多頻繁。
以每 3 天計算，同一個月會被重抓 10 次（當前月已過天數 3、6、9…30），
只有最後一次的資料是完整的：

| 排程 | run/年 | API 額度/年 | 新鮮度 | 失敗後補救 |
| --- | --- | --- | --- | --- |
| 每 3 天（原本） | 122 | **83,160** | 6 天 | 3 天 |
| **每月 3、18 號（採用）** | 24 | **22,882** | 17 天 | 15 天 |
| 每月 3 號 | 12 | 15,322 | 34 天 | 1 個月 |
| 每 3 天 + 跳過當前月 | 122 | 15,322 | 34 天 | 3 天 |

**省 72%，程式邏輯一行未改** —— 決策二、三的規則原封不動就產生這個行為：
3 號那次抓剛完成的上個月（1,277 次額度），18 號那次抓當月 1～15 日（630 次）。

依據是**事故資料兩週發布一次**（使用者提供）。天氣是 inner join 掛在事故上的，
抓得比事故新沒有意義。代價是 `fact_hourly_weather` 落後 `fact_accident_main`
最多 17 天（原本 6 天）—— **不是資料遺失**，L 全量重讀 + `hash_value` upsert，
天氣一落地，下一次 L 就會把先前配不上的事故補齊。

沒有選「每 3 天 + 跳過當前月」（同樣省 82% 又保留 3 天補救），是因為它要推翻
決策二並重寫 ADR-0013 那一整節，而 ADR 生效後不改。

### 1. 新增一個 seam：`blob_file_name()`

```python
def blob_file_name(lat: float, lon: float) -> str:
    return f"{str(lat).replace('.', '-')}_{str(lon).replace('.', '-')}.parquet"
```

`prep_batch_plan()` 用它組「該有哪些檔案」，`e_crawler_weatherapi()` 用它決定
「要存成什麼檔名」。**兩處必須是同一支函式** —— 這正是第一章那個病灶的修法，
與 ADR-0010 的 `read_traffic_accident_file()` 同一類（承重的契約只能有一處）。

### 2. GCS 路徑

```
改動前  data/cralwer_batch_{批號}_{lat}_{lon}.parquet
        tmp/batch_no_{批號}.parquet

改動後  data/{年}-{月}/{lat}_{lon}.parquet
        tmp/{年}-{月}/batch_no_{批號}.parquet
```

暫存檔也要帶月份，否則不同月的同號批次互相覆蓋。

### 3. 三支新的日期函式，年份分支整個刪除

```python
is_month_complete(target_year, month, today)   # M 的最後一天 <= today - 3
months_to_fetch(target_year, today)            # M 的一號 <= today - 3
month_date_range(target_year, month, today)    # (起日, min(月底, today-3))
```

`API_LAG_DAYS = 3` 把原本散在兩處的字面值收成一個常數。

**`if target_year < this_year` 的年份分支刪除。** 歷史年份的每個月都自然滿足
完成判定；當年度用同一條規則得出正確答案。d07 與 d08 從此走完全相同的邏輯。

### 4. `prep_batch_plan()` 回傳 `list[dict]`

```python
# 改動前  [0, 1, 2, ...]
# 改動後  [{"batch_id": 0, "target_year": 2026, "month": 1}, ...]
```

逐月盤點缺口：已完成的月排除既有檔案，尚未完成的月整月重抓覆蓋。
DAG 端從 `.partial(target_year=...).expand(batch_id=...)` 改為 `.expand_kwargs(batches)`。

**回傳空 list 是正常結果**（該年度已全部抓完），不 raise —— d08 補完之後
每天都會走到這裡。

### 5. 進度 log

```
2026 年共需 8,400 個（觀測點, 月）組合（1,050 個觀測點 × 8 個月），
GCS 上已有 7,350 個，本次排出 21 個批次
```

**粒度與 ADR-0013 決策六寫的不同。** ADR 的例子是「168 個（批, 月）組合」，
實作成（觀測點, 月）：「已有」直接等於 GCS 物件數，算得出來也對得上；
換算成批數要處理「某月只缺 3 個觀測點也算一批」的畸零，反而失真。

### 6. 一併清掉的東西

| 位置 | 移除的 | 理由 |
| --- | --- | --- |
| `prep_batch_plan()` | `del` + 函式內 `import gc` + `gc.collect()` | 千列的 DataFrame 上沒有意義；`import` 寫在函式體內 |
| `prep_batch_plan()` | `df_a_batch["batch_id"] = batch_id` | 下游從不讀它，批號現在在 plan 的 dict 裡 |
| `_should_retry()` docstring | 「一批 50 地點 × 365 天 ≈ 1,300 次額度，日限額約 8 個批次用盡」 | 高估 2.5 倍且誤判成日限額優先（T-D 已更正） |

| 項目 | 內容 |
| --- | --- |
| 命名 | `observation_file_name` → `blob_file_name`（與 `gcs_utils` 內部用詞一致）；`_latest_available_date` → `_latest_available_date_from_api` |
