# ADR-0014：事故主鍵由事故內容決定，而非單次 run 的排序名次

- 日期：2026-08-09
- 狀態：已採納（程式碼已實作，**資料尚未重灌**）
- 範圍：`src/task/t_fact_accident_main.py`、`src/task/l_fact_accident_main.py`、
  `src/task/create_traffic_accident_tables.py`、`src/task/t_fact_accident_human.py`、
  `src/task/t_fact_accident_env.py`
- 相關：[ADR-0002 upsert 邏輯集中於單一 module](./0002-upsert-邏輯集中於單一-module.md)（`update_columns` 的語意）、
  [ADR-0003 快取層不再吞噬例外](./0003-快取層不再吞噬例外.md)（對不到主檔要 raise，不要吞成空）、
  [ADR-0010 事故 CSV 的讀取契約集中於單一 module](./0010-事故-csv-的讀取契約集中於單一-module.md)（`t_fact_*` 中段查 FK 是刻意保留的）
- 來源：2026-08-09 d02 的 `task_t_and_l_other_facts` 寫入 `fact_accident_human`
  時拋出 IntegrityError（`accident_id` 為 NULL）

## 名詞

**唯一鍵四欄**：`day_id`、`accident_time`、`longitude`、`latitude` 的組合，
即 `uk_fact_accmain_daytimelonlat`。全專案識別「同一件事故」都用這四欄，
`t_fact_accident_human` 與 `t_fact_accident_env` 也是靠它回查 `accident_id`。

**單次 run 的輸入**：一次 d02（或 d03）執行時，`e_` 階段抓回來的那些 CSV 裡的
全部資料列，也就是 `t_fact_accident_main()` 收到的 `csvfile_paths` 讀出來的內容。
d02 每兩天重抓今年度的整年檔案，所以**每次 run 的輸入都是一份重新下載的全量快照**，
來源補登過什麼，這份快照就跟著變。

**嵌合列**：`fact_accident_main` 中一列，其 `accident_time` 來自 A 事故、
`longitude`/`latitude` 來自 B 事故，四欄組合在來源資料中不存在。本 ADR 的病灶。

## 背景

### 病因：主鍵是「這次 run 的輸入裡排第幾」，不是事故的身分

`t_fact_accident_main.py` 生成主鍵的方式是先按唯一鍵四欄排序，
再依 `groupby(accident_date).cumcount()` 給當日流水號：

```python
df_fact_accident_main = df_fact_accident_main.sort_values(
    by=["day_id", "accident_time", "longitude", "latitude"]
).reset_index(drop=True)
df_fact_accident_main["cumcount"] = (
    df_fact_accident_main.groupby("accident_date").cumcount() + 1
)
```

於是 `accident_id` 的值取決於**這次 run 的輸入裡有哪些列**。同一件事故，在不同
次 run 會拿到不同的編號。而 d02 每兩天重抓一次今年度的整年檔案，只要來源在某個
既有日期補登一筆事故，該日那一筆之後的所有事故名次全部 +1。

### 這如何變成 NULL accident_id

`l_fact_accident_main.py` 的 upsert 是 `INSERT ... ON DUPLICATE KEY UPDATE`，
而 `update_columns=["accident_time"]`。名次位移後，新算出的編號撞到 DB 裡
**別件事故**已佔用的主鍵，於是不是插入，而是把那一列的 `accident_time`
蓋成新事故的時間 —— 座標留在原地，產生嵌合列：

```
run 1:  D-0001 = a1(05:00, X)   D-0002 = a2(08:00, Y)   D-0003 = a3(09:00, Z)
        ↓ 來源補登一筆 a0(04:00, W)，排序後插在最前
run 2:  這次算出 D-0001=a0  D-0002=a1  D-0003=a2  D-0004=a3
        D-0001~0003 撞主鍵 → 只更新 accident_time
        DB 實際變成： D-0001(04:00, X)  D-0002(05:00, Y)  D-0003(08:00, Z)  D-0004(09:00, Z)
                            ↑ 時間來自 a0，座標來自 a1 —— 四欄組合不存在於任何來源
```

`t_fact_accident_human.py` 用唯一鍵四欄 `how="left"` 回查 `accident_id`，
對上嵌合列時四欄無一能全等，得到 NULL，寫入時撞 `accident_id VARCHAR(16) NOT NULL`
與外鍵，IntegrityError 就是這麼來的。

三個推論：

1. **`how="left"` 不是肇因，而是這次能發現問題的原因。** 它讓對不到主檔的列留下
   NULL，寫入時才會失敗；換成 inner 只會讓這些當事人靜靜消失，
   與 ADR-0003 要消除的病因同一類。
2. **重跑不會修正已落地的汙損。** 下一次 run 算出的仍是同一個編號、撞同一個主鍵，
   `update_columns` 只碰 `accident_time`，座標永遠停在錯的值。
3. **`fact_accident_env` 走完全相同的回查方式，受害範圍一樣**，只是它排在
   `l_fact_accident_human` 之後，這次還沒執行到就先失敗了。

### 兩個看似合理、實際上偵測不到此病的檢查

排查初期用過這兩句 SQL，都回空值，一度被當成「已排除撞號」——**它們在結構上
就不可能偵測到**，記在這裡避免下次再繞路：

| 檢查 | 為何無效 |
| --- | --- |
| `LEFT(accident_id,8) <> 日期` | 前綴就是日期本身，撞號必然發生在同一天內部，前綴永遠正確 |
| 每日 `COUNT(*) <> MAX(序號)` | 位移造成的撞號是從第 k 名起密集連續的，末尾照常 INSERT，`COUNT` 與 `MAX` 仍相等 |
| 同日內 `accident_id` 遞增而 `accident_time` 遞減 | 錯位是**整段往後平移一位**，每一列拿到的都是前一名的時間，時間序列仍然遞增 |

三者都是只看 `fact_accident_main` 自己。**平移錯位在表內部是自洽的**，
任何不參照來源資料的檢查都偵測不到它 —— 唯一的判準是拿表裡的唯一鍵四欄
去跟來源 CSV 比對，嵌合列的四欄組合在 CSV 中不存在。

### 數字的來源與可信度

| 數字 | 值 | 等級 | 怎麼來的 |
| --- | --- | --- | --- |
| 來源網站更新載點的日期 | 2026-08-08 | **實測** | 使用者查看 data.gov.tw 資料集頁面 |
| 受影響的 `day_id` 區間 | 2009–2024（＝2026 年 7 月） | **實測** | Airflow UI log 中 NULL 列的 `day_id` 分布 |
| 具體嵌合列 | `2026070200000030` | **實測** | 該列 `06:47:00` 對應補登事故，座標仍是原 `06:53:00` 那件的 |
| 單次 run 的 CSV 列數／事故數 | 71,821 / 31,666 | **實測** | 2026-08-09 離線重跑 A1 即時檔 + A2 第 4 分檔 |
| 同一次 run 的輸入內 NULL `accident_id` | 0 列 | **實測** | 同上；證實兩支 `t_` 的清洗邏輯本身對得上，病灶只在跨 run 時出現 |
| 來源經緯度小數位 | ≤ 6 | **實測** | 同上兩檔；排除 `decimal(10,6)` 四捨五入的可能 |
| `dim_accident_type` 五個鍵欄的 NaN | 0 | **實測** | 同上；排除 inner join 篩掉整件事故的可能 |
| MySQL `TIME` 回讀後的字串格式 | `05:37:00` | **實測** | pandas 推成 `timedelta64[ns]`，含 NULL 亦同；排除前導零的可能 |
| 下游解析 `accident_id` 格式的位置 | 0 處 | **實測** | `grep` 過 `mart_table_sql/`、`core/`、`pages/`，全部只當不透明識別碼 |
| 單日事故數 | 約 149 | **推算** | 31,666 件 ÷ 約 212 天 |
| 16 碼雜湊的碰撞機率（5 年） | ≈ 1e-11 | **推算** | 以單日 500 件（保守上限）代生日問題，64 bit |
| 8 碼雜湊的碰撞機率（5 年） | ≈ 5% | **推算** | 同上算式，32 bit |
| 歷年資料列數 | 約 390 萬 | 既有記載 | `CLAUDE.md`，未於本輪重新量測 |
| **已落地的嵌合列總數** | — | **未測** | 只能比對 CSV 與 DB 取得，見〈驗證〉；已知至少 1 筆 |

## 決策

### 一、`accident_id` = 日期八碼 + 唯一鍵四欄的 SHA-256 前 16 碼

欄位加寬為 `VARCHAR(24)`，`fact_accident_main`、`fact_accident_env`、
`fact_accident_human` 三處同步。

```
accident_id = YYYYMMDD + sha256(f"{date}|{time}|{lon:.6f}|{lat:.6f}")[:16]
```

主鍵從此**只由事故本身決定，與這次 run 讀到哪些資料無關**。同一件事故無論在
哪一次 run、和多少筆資料一起被處理，都得到同一個編號；補登插隊不會讓任何既有
事故換號，upsert 也就回到「同一件事故更新、新事故插入」的正確語意。

經緯度必須先格式化成固定 6 位小數字串再進雜湊，否則 float 的字串表示
會讓同一筆事故在不同次 run 算出不同的值 —— 這正是本 ADR 要消除的那類不穩定。

做法與 `fact_accident_human` 既有的 `row_hash`（SHA-256 前 32 碼當唯一鍵）
同源，不是新機制。

**`sort_values` 一併移除。** 它存在的唯一理由是替流水號定出名次；主鍵改成雜湊後
它不再影響任何輸出，留著只會讓人以為順序仍有意義 —— 而「順序有意義」正是這次
出事的根源。`drop_duplicates` 保留（唯一鍵的去重仍然必要），其後接 `reset_index`。

**保留日期前綴的理由**：InnoDB 的主鍵即聚簇索引，前綴帶日期讓實體儲存
順序貼近日期，按日期範圍掃描的區域性較好（**推論，未實測**）；
排查時也能一眼看出一列屬於哪一天。

**排除的做法：**

- **純 16 碼雜湊，不加日期前綴。** 剛好塞得進現有的 `VARCHAR(16)`，DDL 零變更，
  但失去上述兩項好處，且排查時必須 join `dim_accident_day` 才知道日期。
  既然嵌合列本來就得重灌、表本來就要動，省下的 `ALTER` 換不到什麼。
- **日期前綴 + 8 碼雜湊（維持 `VARCHAR(16)`）。** 碰撞需在同一天內兩件事故
  雜湊相同，**推算**五年累積約 5%，且隨資料量成長惡化。主鍵碰撞的後果是靜默
  丟資料，與本 ADR 要根除的病同一類，不能接受。
- **保留流水號，改成續編**（T 階段先查 main 取得該日已配號的事故，既有的沿用、
  新事故往後編）。外觀與現況完全相同、歷史資料不必重灌，但 `t_` 從純函式
  變成有狀態、可測性下降，而且併發或重跑順序不同時仍可能配出不同的號 ——
  沒有真正解決「編號取決於執行脈絡」這件事。
- **改用 `AUTO_INCREMENT` 代理鍵。** 同樣能讓編號穩定，但 `accident_id` 的語意
  變成純序號，且 T 階段仍要回查主檔取得它（現況已如此，不算新增成本）。
  改動面與方案一相當，卻少了日期前綴的好處。
- **把唯一鍵四欄直接當複合主鍵。** 語意上最誠實，但 `fact_accident_env` 與
  `fact_accident_human` 的外鍵要跟著變成四欄複合鍵，兩張表各約 390 萬列的
  索引明顯變肥，且所有既有 join 都要改寫。

### 二、`update_columns` 只列非鍵欄位，且必須排除 `weather_record_id`

```python
update_columns = ["accident_type_id", "death_count", "injury_count"]
```

改為內容雜湊後，主鍵與唯一鍵同源，衝突只剩「同一件事故重複出現」一種情況，
該更新的就是這三個非鍵欄位 —— 它們正好是 d02 寫入的欄位裡，扣掉主鍵、
唯一鍵四欄與 `weather_record_id` 之後剩下的全部。

兩條不可退讓：

- **唯一鍵四欄不得列入。** 它們是身分的組成，更新它們就是製造嵌合列。
- **`weather_record_id` 不得列入。** 它由天氣 ETL 回填、不由 d02 產生，
  不在 d02 的職責範圍內。（列入的後果**推測**是被清成預設的 -1 —— d02 的 INSERT
  不帶這欄，`VALUES(weather_record_id)` 取到的應是欄位預設值，**未實測**；
  但即使後果不是如此，上面那個職責的理由仍然成立。）

**排除的做法：只補齊 `update_columns`、不動主鍵定義。** 把四個鍵欄也放進
update 範疇，看起來能讓每一列被後一筆「推正」，但正確性依賴 `executemany`
逐列且按名次遞增的執行順序（脆弱的隱含依賴），中途只要出現唯一鍵衝突，
整個 `executemany` 就會 rollback；而且無法處理來源**刪除**一筆的情形 ——
名次往前縮，末尾會殘留一列沒有任何新資料對應的孤兒。
根源是編號會浮動，不在 update 範疇。

### 三、T 階段對不到主檔一律 raise

`t_fact_accident_human` 與 `t_fact_accident_env` 在回查 `accident_id` 之後
立即檢查，有 NULL 就 `raise`，訊息帶上對不上的鍵與筆數。

現況是把 NULL 丟給 MySQL 的 `NOT NULL` 與外鍵去擋，錯誤訊息離現場很遠 ——
這次排查花掉的大部分時間就在從 IntegrityError 回推到主檔。照 ADR-0003 的精神，
故障要在能說清楚原因的地方停下來。

`how="left"` **維持不變**：對不到主檔的列要留下 NULL 才有東西可以檢查，
改成 inner 是把那些列直接丟掉，等於吞掉故障。

### 四、三張事實表重灌

已落地的嵌合列不會因為重跑而被修正（見〈背景〉推論 2），且主鍵定義一換，舊編號
全部作廢，而 `fact_accident_env`、`fact_accident_human` 的外鍵都指向它。
三張表一起重建、重跑 d02（今年）與 d03（歷年）。

`dim_*` 四張維度表不受影響，不動。

**排除的做法：只重灌受影響的日期區間。** 範圍小，但要自行確保刪除順序滿足
外鍵約束，而且「受影響的區間」本身要靠量測界定 —— 主鍵定義既然要換，
舊編號在全表都作廢，省不下什麼。

## 驗證

災情規模只能靠比對來源量測（見〈背景〉——純 SQL 的檢查都偵測不到平移錯位）：
把 `fact_accident_main` 的唯一鍵四欄與同一批來源 CSV 清洗出的四欄做 anti-join，
對不到的就是嵌合列。需在能同時讀 CSV 與 MySQL 的環境以 pandas 執行。
**重灌後就沒有機會量了**，但這只是存證，不影響要做的事。

實作後應成立：

1. main 的唯一鍵四欄集合與來源 CSV 清洗後的四欄集合完全一致，anti-join 兩邊皆空。
2. 同一份 CSV 連跑兩次 d02，`fact_accident_main` 的列數與每列的
   `accident_id` 完全不變（冪等）。
3. 人為在某日中段插入一列後重跑，該日既有事故的 `accident_id` 一個都沒變，
   只多出新事故那一列。
4. `task_t_and_l_other_facts` 不再出現 NULL `accident_id`。

## 後果

### 正面

- 主鍵冪等，來源補登不再造成錯配或資料遺失
- 重跑 d02／d03 從有風險變成安全操作
- 故障在 T 階段就停下來並說明原因，不再由 IntegrityError 間接暴露

### 負面

- 三張表需 `ALTER` 加寬並重灌，歷年約 390 萬列要重跑 d03
- `accident_id` 從 16 字元變 24 字元，兩張子表的外鍵索引隨之變大
- 失去「序號能讀出當日第幾件」的性質（無下游依賴，見數字表）

### 中性

- 唯一鍵四欄的定義完全不變
- 下游 SQL 與前端不受影響 —— 全部只把 `accident_id` 當不透明識別碼
- `fact_accident_human` 的 `row_hash` 含 `accident_id`，會全部重算；
  重灌時自然發生，不需額外處理

## 尚未決定的事

- **來源刪除一筆事故時，DB 中的孤兒列如何處理。** 本 ADR 讓編號穩定，
  但沒有處理「來源不再有這件事故」的情形 —— 那一列會留在表裡。
  這在現況同樣存在，不是本輪引入的，暫不處理。
