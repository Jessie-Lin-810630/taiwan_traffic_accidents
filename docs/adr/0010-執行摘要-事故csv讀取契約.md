## 一、病因定義

同一份 data.gov.tw 事故 CSV 的讀取契約被複製成六份 implementation，
六份對「欄位缺失」與「空 pathlist」給出**三種互不相容的失敗語意**。

```python
# 六支 t_*.py 的迴圈開頭，一字不差複製六份
df = pd.read_csv(file_path, encoding="utf-8", skipfooter=2, engine="python")
required_columns = [k for k in <某個 col_map>.keys()]
df = df.loc[:, required_columns]                    # ← 缺欄即 KeyError（五支）
renamed_required_columns = [<某個 col_map>[k] for k in required_columns]
df.columns = renamed_required_columns               # ← 按「位置」賦名 ← 病灶
df = df.map(lambda x: x.strip() if isinstance(x, str) else x)
```

ADR-0009 當時把它評為「只有『重複』，缺少明確的失敗語意病因」而未採納。
這個保留意見是錯的 —— 病因不只存在，而且已經污染生產資料。

### 病灶：按位置賦名，遇到缺欄就整批錯位

`t_fact_accident_human` 比其餘五支多一段缺欄補償：

```python
matched_columns   = [m for m in required_columns if m in df.columns]
unmatched_columns = [u for u in required_columns if u not in df.columns]
df = df.loc[:, matched_columns]
for new_col in unmatched_columns:
    df[new_col] = None          # ← 補在最「後面」
df.columns = renamed_required_columns   # ← 但名字按「原順序」賦值
```

`df` 的欄序是 `matched + unmatched`，`renamed_required_columns` 是對照表原順序。
兩個順序一旦不同，缺席欄之後的每一欄都往前挪一格。

### 這不是推論：用真實檔案跑出來的

`data/processed` 現有 72 個 CSV，兩種表頭：

| 表頭 | 欄數 | 檔數 | 有 `共享經濟或外送平台的名稱` |
| --- | --- | --- | --- |
| 舊 | 51 | **59** | 否 |
| 新 | 52 | 13 | 是 |

該欄在 `fact_accident_human_col_origin_map` 排第 16 位（共 21 個），其後還有 5 個 key。
拿 `data/processed/111年度A1交通事故資料.csv` 實跑舊實作：

```
英文欄名                                ← 實際裝著的原始中文欄
serving_sharing_economy_or_delivery    ← 車輛撞擊部位大類別名稱-最初   （值："機車"）
impact_point_major_initial             ← 車輛撞擊部位子類別名稱-最初   （值："前車頭"）
impact_point_minor_initial             ← 車輛撞擊部位大類別名稱-其他
impact_point_major_other               ← 車輛撞擊部位子類別名稱-其他
impact_point_minor_other               ← 肇事逃逸類別名稱-是否肇逃
hit_and_run                            ← （補上的 None）→ apply 後恆為 0
```

一欄缺席，21 欄中 15 欄錯位。

### 已經寫進 MySQL 的量（修正前）

本機 `mysql_server` 容器內的 `traffic_accidents.fact_accident_human`，共 4,814,400 列：

| 欄位 | 實際裝的值 | 列數 |
| --- | --- | --- |
| `impact_point_minor_other` | 「否」3,856,167 ＋「是」47,901 —— 這是**肇逃**的值 | 3,904,068（81%） |
| `serving_sharing_economy_or_delivery` | 「機車」1,049,284、「汽車」1,044,006、「機車與自行車」947,621 —— 這是**車種** | 約 304 萬 |

只有 13 個新表頭檔案貢獻的列是對的
（`serving_sharing_economy_or_delivery` = 「其他(非共享經濟與外送平台)」775,033 列）。

`impact_point_minor_other` 還參與 `row_hash` 的計算，而 `row_hash` 在 MySQL 是 `UNIQUE`。

### 另一個症狀

| 症狀 | 現象 |
| --- | --- |
| 空 `pathlist` | `t_dim_road_design` 有 `if all_df:` 守衛，回空 DataFrame（upsert 0 列、DAG 綠燈）；其餘五支讓 `pd.concat([])` 拋 `ValueError: No objects to concatenate` |

### 為什麼缺欄不能一律 raise

`共享經濟或外送平台的名稱` 是 114 年度才新增的欄位，舊表頭沒有它是**正常的**。
一律 raise 會讓 59/72 個既有檔案全部處理不了。
要修的不是「該不該容錯」，而是「容錯的實作用錯了對應方式」。

## 三、實際改動

### 1. 新增 `src/util/read_traffic_accident_file.py`

```python
def read_traffic_accident_file(
    csvfile_path: str | Path, column_map: dict[str, str]
) -> pd.DataFrame:
    df = pd.read_csv(csvfile_path, encoding="utf-8", skipfooter=2, engine="python")

    missing_columns = [c for c in column_map if c not in df.columns]
    if missing_columns:
        logger.warning(f"{csvfile_path} 缺少欄位 {missing_columns}，這些欄位將為 NaN")

    df = df.rename(columns=column_map)
    df = df.reindex(columns=list(column_map.values()))

    return df.map(lambda x: x.strip() if isinstance(x, str) else x)
```

`reindex` 一次做完三件事：挑出要的欄、丟掉不要的欄、把缺席的欄補成 `NaN` 且放在正確位置。
> 錯位在結構上不發生。

## 五、同病因但尚未修復的位置

### A. 既存 lint 債（狀態未變）

`ruff check src dags` 仍未通過的檔案清單見
[ADR-0003 執行摘要](./0003-執行摘要-快取層與日誌職責.md)第五章 C。本輪改動的檔案皆已通過。

### 評估後決定不改：三支 `t_fact_*` 中段的維度查閱

`t_fact_accident_main`（2 次）、`t_fact_accident_env`（4 次）、`t_fact_accident_human`（2 次）
在 transform 中段呼叫 `get_table_from_sqlserver()` 取 FK。

探索時曾把它列為下一個候選，理由是「MySQL 洩漏過 transform 的 seam」，
解法是維度以參數傳入、由 DAG 決定資料來源。**評估後決定維持現狀**，三條理由：

1. **取 FK 本來就是 transform 的職責。** 星狀綱要的 ETL 在 transform 階段做
   surrogate key lookup 是標準做法。`t_fact_*` 的工作定義就是「把 CSV 對到星狀綱要」，
   要對得上就必須知道 dim 表現在長什麼樣 —— 這不是洩漏。

2. **改了也只能改一半。** 四個 dim 表夠小可以參數傳入
   （`dim_accident_day` 2,191、`dim_accident_type` 1,215、`dim_lane_design` 615、
   `dim_road_design` 172 列），但 `t_fact_accident_env` 與 `t_fact_accident_human`
   中段查的是 **`fact_accident_main`，2,135,698 列** —— 它不是維度表，
   走 Airflow XCom 傳遞會出事。那兩支仍然得在函式內連 MySQL。
   付出 DAG 變複雜的代價，只換來 mock 從 4 個減成 1 個。

3. **可測性已經成立。** 本輪用 monkeypatch 把三支都測起來了，
   `t_fact_accident_env` 一次假造四張表也沒有困難。「難測」的前提不成立。

寫測試時遇到的 dtype 摩擦**是測試資料的問題，不是程式碼缺陷**：
假資料若拿 `"1"` 當維度鍵，pandas 會推斷成 `int64`，與 mock 維度表的 `object`
就 merge 不起來（`ValueError: You are trying to merge on int64 and object columns`）。
真實的維度鍵都是中文字串，兩邊同為 `object`，生產上不會發生。
測試改用非數字的假資料即可，記在這裡是為了下一輪寫 mock 時不必再撞一次。

**這一節的用途是讓未來的架構檢視不要再提議一次。**
