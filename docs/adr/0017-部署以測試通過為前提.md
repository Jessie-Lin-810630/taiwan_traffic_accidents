# ADR-0017：部署以測試通過為前提

- 日期：2026-08-12
- 狀態：已採納
- 範圍：`.github/workflows/deploy-backend-vm.yml`、`.github/workflows/deploy-cloud-run.yml`
- 相關：[ADR-0001 不使用 AirflowException，一律原樣拋出](./0001-不使用-airflowexception-一律原樣拋出.md)
  （測試釘住的就是這類「不可退讓的規矩」，沒有 gate 就只能靠人記得跑）
- 來源：README 的 What's Next 長期掛著「沒有 CI 測試 gate，測試需在本機自行跑過」。
  推 `main` 會直接重建 VM 上的 compose 並部署 Cloud Run，中間沒有任何自動檢查。

## 名詞

**gate**：部署流程中的一道前置檢查。不通過就不往下走，而不只是「留下一筆紅色紀錄」。

## 背景

### 現況：推上去就部署

兩支 workflow 都是 `on: push` 直接進入部署動作，沒有任何前置檢查：

| workflow | 觸發條件 | 做的事 |
| --- | --- | --- |
| `deploy-backend-vm.yml` | push 到 `main`，`paths-ignore` 排除 `**.md` 與 `docs/**` | 經 IAP tunnel SSH 進 VM，寫 `.env`、`git pull`、`docker compose up -d --build` |
| `deploy-cloud-run.yml` | push 到 `main`，白名單 `paths`（前端相關路徑） | build image 推 Artifact Registry，`gcloud run deploy` |

也就是說，**任何能通過本機 pre-commit 的 commit，推上去就會直接改動生產環境**。
測試是否跑過、跑的是哪個版本，完全取決於推的人當下有沒有記得。

### 測試現況：便宜到沒有理由不跑

實測（2026-08-12，本機）：

| 項目 | 值 | 等級 |
| --- | --- | --- |
| 測試數 | 213 | **實測**，`pytest --collect-only` |
| 執行時間 | 1.26 秒 | **實測**，`poetry run pytest test/unit_test/ -q` |
| 是否需要 MySQL／Redis／網路 | 否 | **實測**，全部走 `unittest.mock`／`monkeypatch` |
| 是否需要環境變數 | 否 | **實測**，`test_util_required_settings.py` 專門釘住「缺設定不影響模組匯入」 |
| CI 上的執行時間 | — | **未量測**，多出的是安裝依賴的時間 |

**測試本身的成本可以視為零**，gate 的實際成本是安裝依賴那一段。

### 為什麼不是「另開一支 test workflow 就好」

GitHub Actions 的 `needs` 只能指向**同一支 workflow 內**的 job。另開一支
`ci-test.yml` 只會產生一筆獨立的檢查結果，**不會阻止 deploy workflow 繼續跑**
—— 兩者是平行的兩個 workflow run。

要達成「測試不過就不部署」，測試 job 必須內嵌在部署 workflow 裡。

## 決策

### 一、兩支部署 workflow 各自內嵌一個 `test` job，deploy job 以 `needs: test` 相依

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: pytest test/unit_test/

  deploy:            # 或 build-and-push
    needs: test
    ...
```

測試 job 失敗時 deploy job 不會啟動，也就不會有半套部署。

### 二、跑全部測試，不挑子集

不因為「這次只改前端」就只跑 `test_task_*`。理由是**挑選的維護成本高於它省下的
1.26 秒**，若分流測試，就得有人維護「哪個路徑對應哪組測試」這份對照表，而一定會有幾份是
過期。

### 三、依賴以 `requirements.txt` 安裝，不用 Poetry

CI 上不裝 Poetry，直接 `pip install -r requirements.txt`。

除了快之外，這一條有額外的作用：`requirements.txt` 正是容器實際安裝的清單，而
**它與 `pyproject.toml` 不會自動同步**。用它來跑測試，
等於順帶檢查了「這份清單裝得起來，而且裝完測試會過」。若有人改了依賴卻忘記
`poetry export`，gate 會在部署前就抓到。

### 四、gate 的觸發範圍等於它所在 workflow 的觸發範圍

兩支 workflow 的路徑過濾規則不同，gate 直接繼承，**不另外調整**：

- 只改 `dags/` 或 `src/task/e_*.py`：觸發 backend-vm，其 gate 會跑；cloud-run 完全
  不觸發，所以也沒有 gate。
- 只改 `docs/**` 或 `**.md`：兩支都不觸發，兩邊的 gate 都不跑。


### 五、gate 只跑 pytest，不納入 ruff

pre-commit 已經在本機擋掉 ruff 的問題，且 lint 失敗不會讓部署出來的服務壞掉。
把兩件事綁在一起，只會讓「格式沒對齊」變成「不能部署」。

### 六、VM 上拉取的分支由觸發部署的分支決定

`deploy-backend-vm.yml` 原本硬寫 `git pull origin refactor/util-connection-layer`
（第 74 行），而觸發條件是 push 到 `main` 或 `refactor/util-connection-layer`。也就是**推 `main` 會讓 VM 去拉一支已經作廢的 refactor 分支**，這是本輪盤點時發現的，與沒有寫測試 gate 無關。

改為：

- 兩支 workflow 的 `branches` 一致，都是 `main` 與 `UAT`，refactor 舊分支移除
- VM 上改拉**觸發本次部署的那一支**：`git pull origin "${GITHUB_REF_NAME}"`

`UAT` 是 production-similar 環境的分支，角色是上線前的驗收兼測試環境，往後 `main` 的內容併回 `UAT` 時，由 `UAT` 的 push 觸發該驗收兼測試環境的部署。

## 後果

### 正面

- 推 `main` 不再可能把測試紅燈的版本送上生產環境
- 依賴清單不同步會在部署前被抓到，而不是在容器啟動失敗時
- 「測試需在本機自行跑過」這句話可以從現行的 README 拿掉
- 後端 VM 拉到的分支與觸發部署的分支從此一致

### 負面

- **部署時間變長**，多出 checkout、裝 Python、裝依賴三段。實際增加多少**未量測**，
  裝依賴是主要成本（90 行的 `requirements.txt`，含 pandas、streamlit 等大套件）。
- **兩支 workflow 各裝一次依賴**。同時觸發時會重複做一樣的事。不共用是因為跨
  workflow 無法共享 job，而合併成一支會讓兩條部署路徑互相綁死。
- **gate 擋不住「沒有觸發 workflow 的變更」**。例如只改 `src/task/l_*.py` 時
  cloud-run 不觸發，若該改動確實影響前端，這條路徑上沒有檢查。
- 開發分支的 push 不跑測試（`branches` 只列 `main` 與 `UAT`），所以問題仍然是到了
  合進這兩支的時候才會被發現。如果之後要回到更前面的開發分支，需要記得抽出純自動測試 job 部分另存 workflow，該 workflow 不做自動部署，自動部署由 `main` 與 `UAT` 主導。

### 中性

- 部署的其他行為完全不變：認證方式、image tag 規則、`gcloud run deploy` 的參數都不動
- 測試本身不改，只是換一個地方執行
- **後端 VM 的內容始終取決從哪一支分支觸發最後一次觸發部署。** 推 `main` 之後
  再推 `UAT`，VM 上就會 `UAT` 的內容。由於是小型專案、個人維護，所以接受這種部署到同台 VM 省下第二台生產環境 VM 經費的做法，原本的 workflow 已知有這個事實，本次修改後預計仍然不變，僅記得兩支分支都會部署到同一台 VM。

## 尚未決定的事

- **要不要快取 pip。** 得先量到裝依賴實際花多久才有判斷依據。
- **`test/unit_test/` 之外要不要有整合測試。** 目前全部走 mock，沒有任何測試會真的
  連上 MySQL 或 Redis，因此 gate 保證的是「邏輯沒壞」，不是「連得上」。
