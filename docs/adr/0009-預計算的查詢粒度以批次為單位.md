# ADR-0009：預計算的查詢粒度以「批次」為單位

- 日期：2026-07-31
- 狀態：已採納
- 範圍：`src/task/core/c_data_service.py` 的 `cal_accidents_nearby_nightmarket()`
- 相關：[ADR-0003 快取層不再吞噬例外](./0003-快取層不再吞噬例外.md)（子決策 2、3）
- 來源：[ADR-0008 執行摘要](./0008-執行摘要-必填設定驗證.md)第五章 B 提出的「候選 10」

## 名詞

本文只用這六個詞，其餘一律用白話。

| 詞 | 意思 | 在程式碼的哪裡 |
| --- | --- | --- |
| **批次** | 30 個夜市組成的一個 list | `get_and_slice_nightmarkets_multibatches()` 用 `batch_size = 30` 切出來，存進 Redis，只把 key 交給 Airflow |
| **查詢來回** | 送一句 SQL 給 MySQL、等它把結果傳回來，這樣一趟 | `get_accident_table_pedestrian_involved_in()` 每被呼叫一次就是一趟 |
| **粗篩** | 用夜市中心點 ±3 公里的方框，把該區域的事故撈出來 | 改動前由 SQL 的 `WHERE latitude BETWEEN ... AND longitude BETWEEN ...` 做 |
| **細篩** | 在粗篩結果上，再用更小的半徑或指定年份過濾一次 | `itertools.product(radius_m_list, year_targets)` 那個迴圈 |
| **契約 key** | `traffic:nearby_v12:{lat}_{lon}_3.0_all_sample` | 由粗篩寫入，是 `aggregate_national_master()` 唯一會讀的一把 |
| **N+1** | 本來一趟可以問完的事，拆成迴圈裡 N 趟去問 | 見下 |

## 背景

### 這支函式長什麼樣

`d06_precompute_to_redis` 把全台夜市切成每批 30 個，用 Airflow 的 `.expand()`
展開成約 10 個 mapped task，每個 task 呼叫一次
`cal_accidents_nearby_nightmarket(batch_key)`。

改動前的骨架如下（省略細節，只留結構）：

```python
def cal_accidents_nearby_nightmarket(batch_key, radius_m_list=[3000], year_targets=["all_sample"]):
    batch = get_cache(batch_key)                     # ← 拿到 30 個夜市

    for a_nightmarket in batch:                      # ══ 逐夜市迴圈：跑 30 圈 ══
        query = f"""SELECT * FROM analysis_pesdestrian_involving_accident
                    WHERE latitude  BETWEEN {nm_lat - 0.027} AND {nm_lat + 0.027}
                      AND longitude BETWEEN {nm_lon - 0.027} AND {nm_lon + 0.027}"""
        df = get_accident_table_pedestrian_involved_in(query)   # ← 粗篩：一趟查詢來回
        df = df[valid_cols]                                     #   （每圈各一趟，共 30 趟）

        set_cache(f"...{lat}_{lon}_3.0_all_sample", df)          # ← 粗篩寫入（契約 key）

        for r_m, y_target in itertools.product(radius_m_list, year_targets):
            #                              ══ 細篩迴圈：巢狀在逐夜市迴圈「裡面」══
            #                              預設參數下 product 只有一組，所以只跑 1 圈
            df_target = df[mask]                                 # 用更小的半徑／指定年份再篩
            set_cache(f"...{lat}_{lon}_{r_km}_{y_target}", df_target)

        time.sleep(0.05)                             # ← 每圈結尾空等
```

**細篩迴圈是巢狀在逐夜市迴圈裡面的**，不是接在它後面。
所以「30 個夜市 × 細篩迴圈的圈數」才是細篩實際跑的次數。

### 問題 1：查詢在迴圈裡，所以一個批次要跑 30 趟

`get_accident_table_pedestrian_involved_in()` 被放在逐夜市迴圈**內**，
於是 30 個夜市 = 30 趟查詢來回，全台約 10 個批次 = 約 300 趟。這就是 N+1。

而這 30 趟問的是**同一張表**，而且問到的內容**大量重疊**。舉實際的例子：

| | 士林夜市 | 寧夏夜市 |
| --- | --- | --- |
| 中心點 | (25.0878, 121.5240) | (25.0570, 121.5150) |
| 兩者相距 | \<— 約 3.54 公里 —\> | |
| ±3 公里方框 | 6.0 km × 5.46 km | 6.0 km × 5.46 km |

兩個方框有 **約 36% 的面積重疊**。落在那塊重疊區的事故，
第 1 趟為士林撈一次，第 2 趟為寧夏又撈一次 —— 同樣的資料列從 MySQL 傳了兩遍。
全台幾百個夜市裡，同一個都會區的鄰居都是這種關係。

### 問題 2：這張表沒有索引，所以每一趟都是全表掃描

`analysis_pesdestrian_involving_accident` 由
`src/task/mart_table_sql/analysis_overview_pedestrian_accidents.sql` 產生：

```sql
CREATE TABLE IF NOT EXISTS analysis_pesdestrian_involving_accident_tmp
    AS (SELECT * FROM v4_v3_dimday_factenv_v1);
```

`CREATE TABLE ... AS SELECT` **不會帶來任何索引**。
所以 `WHERE latitude BETWEEN ...` 無從定位，MySQL 只能從頭掃到尾。

**那 300 趟不是 300 次索引查找，是 300 次全表掃描。**

### 問題 3：座標用 f-string 內插回 SQL

```python
params = {"min_lat": nm_lat - max_offset, ...}   # dict 建好了
query = f"""... WHERE latitude BETWEEN {params["min_lat"]} AND ..."""   # 卻是印回字串
df = get_accident_table_pedestrian_involved_in(query)                  # params 沒傳下去
```

`get_accident_table_pedestrian_involved_in(dql_str, params)` 第二個參數本來就支援
綁定值，同一個檔案裡的 `get_pedestrian_trend()` 用的正是 `:min_lat` 這種寫法。
兩種寫法並存於同一支模組。

### 問題 4：細篩迴圈在預設參數下寫的是跟粗篩一模一樣的東西

唯一的呼叫端（`dags/d06_precompute_to_redis.py:43`）只傳 `batch_key` 給這個函式，
所以細篩迴圈使用預設值 `radius_m_list = [3000]`、`year_targets = ["all_sample"]` 執行，
導致細篩迴圈的 `itertools.product` 只產出一組 `(3000, "all_sample")`，也就是只跑 1 圈。
而這一圈做出來的結果：

| | 粗篩那圈 | 細篩迴圈唯一那圈 |
| --- | --- | --- |
| 寫入 redis 的變數 key | `traffic:nearby_v12:{lat}_{lon}_3.0_all_sample` | 同左 |
| 該圈在篩選的範圍 | SQL `BETWEEN ±(3000 / 1000) / 111` | pandas `between ±3.0 / 111` |

粗篩與細篩迴圈跑出來的數值是一樣的，而因為在粗篩迴圈，每一輪的語意是篩選出單一夜市的周遭方形區域，所以當兩個迴圈的執行結果是一樣、且全台有約 300 個夜市的時候，就導致了會產出相同結果這件事情發生了 300 次，對資料庫 Redis 來說，寫入 Redis 這件事變成**同一把 key、同一份資料，寫了兩次。**

### 問題 5：兩個可變預設值，其中一個型別標註是錯的

```python
radius_m_list: list[float | int] | None = [3000],
year_targets:  list[int] | None = ["all_sample"],   # 標 list[int]，裝的卻是 str
```

### 問題 6：`time.sleep(0.05)`

在逐夜市迴圈的結尾。節流的對象是自己家的 MySQL 與 Redis，不是有配額限制的外部 API。
全台約 300 個夜市，純等待約 15 秒。

## 決策

**查詢的粒度要跟使用它的粒度一致。**

`cal_accidents_nearby_nightmarket` 一次被呼叫是為了服務**一個批次**，
那它問 MySQL 的次數就該是**一次**，而不是批次裡有幾個夜市就問幾次。

做法是把查詢從逐夜市迴圈**裡面**移到**外面**，並且讓那一句 SQL 一次涵蓋
這 30 個夜市的方框：

```python
# 改動後的骨架
query, params = _build_batch_bbox_query(batch)              # 30 個框組成 OR 聯集
df_batch = get_accident_table_pedestrian_involved_in(query, params)   # ← 唯一一趟查詢來回

for a_nightmarket in batch:                                 # ══ 逐夜市迴圈：仍跑 30 圈 ══
    df_nearby = df_batch[該夜市的框]                          # ← 粗篩改在記憶體中切
    set_cache(契約 key, df_nearby)
    for r_m, y_target in itertools.product(...):            # ══ 細篩迴圈（位置不變）══
        if 這圈的 key == 契約 key: continue                   # ← 預設情境下就是跳過
        set_cache(...)
```

`_build_batch_bbox_query()` 組出來的 SQL 長這樣（30 個夜市就 30 個括號）：

```sql
SELECT * FROM analysis_pesdestrian_involving_accident
 WHERE (latitude BETWEEN :min_lat_0 AND :max_lat_0 AND longitude BETWEEN :min_lon_0 AND :max_lon_0)
    OR (latitude BETWEEN :min_lat_1 AND :max_lat_1 AND longitude BETWEEN :min_lon_1 AND :max_lon_1)
    OR ...
```

重疊區的事故因此只從 MySQL 傳一次；至於它同時屬於士林和寧夏這件事，
在記憶體中切兩份就好，不必再問一次資料庫。

### 八項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | 病因定義為**查詢粒度與使用粒度不一致**，範圍是整支函式 | 問題 1～6 全是同一個粒度錯配的症狀。一次收乾淨，好過分兩輪動同一支函式 |
| 2 | 查詢粒度提升到**批次**（一批一趟），**DAG 不動** | mapped task 的隔離性與重試語意完全保留。改成「全台只查一趟」要多一個上游 task 與一把大 key，且失敗影響面從一批擴大到全部 |
| 3 | `WHERE` 用 30 個框的 **OR 聯集**，座標全走綁定參數 | SQL 字面上就是「這個批次要的資料」。順帶解掉問題 3。批次是夜市清單的順序切片，可能橫跨基隆到屏東，改取「整批的外接大框」幾乎等於全台，等同不加條件 |
| 4 | **保留** `radius_m_list` / `year_targets`，但預設值改 `None`、型別標註改對 | 多半徑／分年度的預計算是可預見的需求；可變預設值與錯誤標註則是無條件要修的缺陷 |
| 5 | 粗篩寫入**維持無條件執行**，細篩迴圈碰到同名 key 就 `continue` | 契約 key 是 `aggregate_national_master()` 唯一會讀的，它的存在不能取決於呼叫端有沒有把 `3000` 與 `"all_sample"` 傳進來 |
| 6 | **移除** `failed_markets` 與逐夜市 `try/except`，查詢失敗即整批失敗 | 見下節 |
| 7 | **刪除** `time.sleep(0.05)` | 查詢移出迴圈後，迴圈內已無查詢來回，節流連名義上的對象都沒有了 |
| 8 | 等價性這樣證明：**把改動前的篩選邏輯原封不動抄一份到測試檔裡，餵同一份假資料給新舊兩邊，比對兩邊算出來的表是否逐列相同** | 地端連不到 MySQL（`MYSQL_HOST=mysql-db` 只在 compose 網路內解析），沒辦法拿真資料跑前後比對。用假資料就不需要資料庫，而且 CI 每次都能重跑 |

### 子決策 6：這不是推翻 ADR-0003 子決策 3

ADR-0003 子決策 3 訂的是「逐個夜市失敗僅跳過，累計失敗清單，迴圈結束後判定」。
它當時被討論的情境是「**迴圈裡若有一趟 SQL 查詢，則先跳過，累計失敗紀錄清單後判定此次查詢品質**」。

但如果照上述決策，將 MySQL 查詢移到迴圈外執行之後，迴圈裡預計只剩 pandas 做資料清理與寫入 Redis：

| 動作 | 會失敗嗎 | 失敗了該怎樣 |
| --- | --- | --- |
| pandas 框選（`Series.between` + `&`） | 幾乎不會 | —— |
| `set_cache()` | 會（Redis 故障） | 寫入快取資料必須根據 ADR-0003 子決策 2：預計算的產出就是快取，寫不進去即 raise。 |

但在修改程式碼前，`set_cache()` 原本就已經放在設計成直接 raise；而被挪到迴圈外的 MySQL 查詢失敗，基於「這一趟查詢必須服務整批下游任務，若它失敗就是整批沒資料，下游的清洗與寫入都會歪掉」的觀點，其實本來就該**直接 raise**。所以按照此預計修改的話，迴圈**內部**就不再有「該累計、該跳過」的任何失敗了。結論是，原訂在**ADR-0003 子決策 3**要去解決的問題，經過這個改動計劃實作的話，就反而不存在，不需要去解決了。

### 為什麼不改成加索引

一度考慮在 mart SQL 建完表之後補一句 `CREATE INDEX idx_lat_lon (latitude, longitude)`，
維持 300 趟查詢但讓每趟走索引。否決的理由：

- **沒有解決病因** —— 來回次數不變，重疊區域仍被重複撈回。
  粒度錯配仍在，只是因為索引優化查詢速度的效果，稀釋粒度錯配的嚴重性。
- **`BETWEEN` 雙欄只吃得到索引前綴** —— `latitude BETWEEN ... AND longitude BETWEEN ...`
  只有 `latitude` 能用索引定位，`longitude` 仍是回表後過濾。
- **索引維護落在 table swap 流程上** —— `src/task/mart_table_sql/analysis_overview_pedestrian_accidents.sql` 的 `swap_analysis_table2()` 會搭配迴圈每輪重建 tmp 表，索引得跟著重建，等於每輪 mart 重算都多付一次建索引的成本。

真的要做，它是獨立的一輪（見「未納入本次範圍」）。

## 後果

- 一個批次的查詢來回從 **30 趟降為 1 趟**，全台從約 300 趟降為約 10 趟。
- 重疊區的事故只從 MySQL 傳一次，不再被鄰近夜市各撈一遍。
- SQL 裡不再出現座標的字面值。
- 每個夜市少一次重複的 Redis 寫入、少 0.05 秒的空等。
- 失敗語意變單純：查詢失敗 → 整批 `raise`；快取寫入失敗 → `raise`。

### 誠實的限制

- **仍然是全表掃描，只是從 300 次變成 10 次。**
  表上沒有索引這件事沒有改變，OR 聯集也用不到索引。
- **收益未經實測。** 地端連不到 MySQL，本輪驗證的是輸出等價，不是執行時間。
  真實的加速倍數要等 d06 在 VM 上實跑才知道。
- **傳輸量的變化方向確定、幅度未知。** 聯集去掉了重疊區的重複傳輸，
  但單次結果集變大；總量應該下降，未量測。
- **方框在經度方向其實不到 3 公里。** 程式對緯度與經度套用同一個
  `3.0 / 111` 度偏移，但在北緯 25 度，1 度經度只有約 101 公里 ——
  方框實際是 6.0 km（南北）× 5.46 km（東西）。這是改動前就有的行為，
  本輪原樣保留（否則輸出就不等價了）。
- **`SELECT *` 維持不變。** 欄位裁剪仍在 Python 端做
  （`valid_cols = [c for c in ACCIDENT_MAP_COLUMNS if c in df.columns]`）。
  下推到 SQL 會把「欄位不存在就跳過」的容錯變成硬失敗，那是另一個決策。
- **`radius_m_list` / `year_targets` 保留但仍無呼叫端。**
  它們現在是正確的（不可變預設、型別標註對），但依然沒有人用。

## 未納入本次範圍

- **為 `analysis_pesdestrian_involving_accident` 建索引**：屬於 mart 層
  （`analysis_overview_pedestrian_accidents.sql` 的 table swap 流程），
  且需要實測才能判斷值不值得。見[為什麼不改成加索引](#為什麼不改成加索引)。
- **欄位裁剪下推到 SQL**：見「誠實的限制」。
- **`c_db.py` 其餘的 `SELECT *` 全表查詢**（`get_night_markets_table`、
  `get_accident_table_with_env` / `_with_human`）：它們的呼叫端確實要整張表，
  粒度沒有錯配。
- **`aggregate_national_master()` 逐夜市 `get_cache()` 的 N+1**：
  結構上是同一個病因的 Redis 版本（約 300 趟來回），
  但 Redis 一趟來回的成本與無索引全表掃描差好幾個數量級，
  且解法是 Redis 自己的批次指令（一次送多把 key 拿回多個值、或一次送多筆寫入），
  與本輪改寫 SQL 的手法無關。列為下一輪候選。
