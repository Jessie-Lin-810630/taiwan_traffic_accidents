## 一、病因定義

**減量發生在下載之後。**

`get_accident_heatmap_data()` 要的是 8000 個地圖熱點，但取得它們的方式是先把整張
`fact_accident_main JOIN dim_accident_day` 撈進 pandas，再依序做三件事：剔除臺灣
範圍外的座標、按座標 `groupby` 取 `count >= 3`、超量就抽樣。

```python
# c_data_service.py（修改前）
df = get_accident_table_with_main_day()      # ← 無參數 = 全表
if df.empty:
    return []
df = df.dropna(subset=["latitude", "longitude"])
df = df[(25.93916 > df["latitude"]) & ...]   # 減量從這裡才開始
df = df.groupby(by=["latitude", "longitude"]).size().reset_index(name="count")
df = df[df["count"] >= 3]
```

於是**記憶體需求由事故總筆數決定，與執行它的容器有多少記憶體無關**，
這與 ADR-0015 在 d03 遇到的是同一個病因，只是換到了前端。

放大這件事的還有兩個結構：

1. `get_accident_table_with_main_day()` 的簽章是
   `start_date=None, end_date=None`，**把「撈走整張事故主檔」放在最省事的呼叫
   方式上**。呼叫端什麼都不給，就會拿到全部。
2. 該函式回傳前會 `df.apply(..., axis=1)` 逐列組 `tooltip_text`，成本正比於列數。
   而熱點圖 `groupby` 之後只留三欄，**這個欄位從頭到尾沒被用到**。

### 為什麼是現在才炸

`docker-compose.yml` 的服務只有 `mysql-db`、`redis-cache` 與四支 airflow，
**沒有 streamlit**（2026-08-10 查證）。這段程式碼在部署到 Cloud Run 之前，
只在開發者本機執行過。**它是第一次被放進有硬性記憶體上限的環境。**

本機是否曾成功撈完全表、生產 Redis 上 `traffic:global_heatmap_lite_v2` 是否曾被
寫入，**都未查證**。能確定的只有：Cloud Run 上這條路徑從未成功過， 第一次全表
載入就被砍，快取永遠寫不進去，每次冷啟動重演。

### 額外發現：這個快取沒有消費端

盤點 `traffic:global_heatmap_lite_v2` 的讀寫（2026-08-10）後發現，**沒有任何頁面
讀它**。三個分頁讀的是 `market:national_master_df` 與
`traffic:nearby_v12:{lat}_{lon}_3.0_all_sample`；`app.py` 本身也沒有畫地圖，
版面上的「300+」「150 萬+」「5+」是寫死在 HTML 裡的文案。

也就是說：**首頁撈 390 萬列，是為了預熱一個沒有人讀的快取。**

`app.py:105` 的註解「僅為預熱 Redis 快取，回傳值本頁未使用」自己說了這件事，
只是沒有人追問過「那誰在讀」。

## 二、決策摘要

| # | 決策 | 一句話 |
| --- | --- | --- |
| 一 | 首頁不再呼叫 `get_accident_heatmap_data()` | 產物沒有消費端，移除即解 OOM |
| 二 | 減量下推到 SQL | `WHERE` + `GROUP BY` + `HAVING` 由 MySQL 做，回傳熱點而非事故 |
| 三 | 抽樣留在 pandas | 固定亂數種子的可重現性不換 `ORDER BY RAND()` |
| 四 | `get_accident_table_with_main_day()` 日期改必填 | 危險的行為不該是預設值 |
| 五 | 查無資料回傳空 DataFrame | 與其他路徑型別一致，不再回 `[]` |

分界線是：**能大幅減少傳輸量的下推，不能的留在原地。**

## 三、實際改動

程式碼：commit `dc5a7c4`，三個檔案、114 行新增 / 56 行刪除。
決策文：commit `86a4c30`。

### `src/task/core/c_db.py`

新增 `get_accident_hotspots()`（編號 `2-1`，如此不必動到後面所有函式的編號註解）：

```sql
SELECT latitude, longitude, COUNT(*) AS count
FROM fact_accident_main
WHERE latitude BETWEEN :lat_min AND :lat_max
  AND longitude BETWEEN :lon_min AND :lon_max
GROUP BY latitude, longitude
HAVING COUNT(*) >= :min_count
```

不 JOIN `dim_accident_day`、不組 `tooltip_text`。五個值全部走 bind parameter。

`get_accident_table_with_main_day()` 的簽章從
`start_date: tuple[int] | None = None, end_date: tuple[int] | None = None`
改為 `start_date: tuple[int, int, int], end_date: tuple[int, int, int]`，
`WHERE` 與 `params` 隨之無條件組出，原本「兩個都不給」的分支消失。
函式內既有的兩道檢查都保留。

### `src/task/core/c_data_service.py`

`get_accident_heatmap_data()` 改呼叫 `get_accident_hotspots()`，
臺灣國土範圍的四個邊界值與 `min_count=3` 從 pandas 條件式變成具名引數。
刪掉 `dropna`、範圍過濾、`groupby`、`count >= 3` 四段。`return []` 改 `return df`。

### `src/app.py`

移除 `ds.get_accident_heatmap_data()` 那一行，`main()` 的 docstring 與第 4 段的
註解跟著改成「取得夜市主檔」。`try/except` 區塊保留， `get_all_nightmarkets()`
仍可能拋出，前端仍是例外停止傳播之處。

### 偏離決策文的地方

**`BETWEEN` 含端點，原本的 pandas 過濾是嚴格不等式。** 決策文寫的 SQL 用
`BETWEEN`，實作照做，但這與 `(25.93916 > df["latitude"])` 有一個端點的差異。
座標剛好等於邊界值時，新舊行為不同。實務上不可能發生（那是六位小數的邊界值），
但這是實作期的取捨，記在這裡而不回頭改決策文。

## 五、同病因但尚未修復的位置

病因是「查詢的粒度大於使用它的粒度」。以 2026-08-10 的盤點：

### 1. `get_accident_table_with_env()` / `get_accident_table_with_human()`

```python
"""SELECT * FROM fact_accident_env;"""     # c_db.py:216
"""SELECT * FROM fact_accident_human;"""   # c_db.py:240
```

無 `WHERE`、無上限的全表查詢。**兩支目前都沒有任何呼叫者**（`src/`、`dags/` 全掃，排除 `temp_try_*`）。
所以它們現在不會造成故障，但只要有人接上前端就會重演本輪的 OOM。


### 2. `get_accident_table_with_main_day()` 仍可能回傳大量資料

決策四把「不給日期 = 全表」拿掉了，但**沒有加上筆數或期間長度的上限**。
呼叫端給 `(2020, 1, 1)` 到 `(2026, 12, 31)` 一樣會撈回五年份，
外加逐列 `apply` 組 `tooltip_text`。

危險的預設值移除了，危險的用法還在，只是不再是最省事的那一種。

### 3. `get_night_markets_table()` 的 `SELECT *`

同樣是無條件全表，但**性質不同**：夜市數量以「300+ 個 × 營業日」為界，
由業務本身封頂，不隨事故資料成長。列在這裡是為了盤點完整，
不建議改動。
