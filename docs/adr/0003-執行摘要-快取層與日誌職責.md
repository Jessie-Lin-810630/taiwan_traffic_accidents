## 一、病因定義

候選 5 的病因是：

> **中間層把故障吞成「正常但空」的回傳值，使故障無法與「查無資料」區分，
> 導致上游監控失效。**

三個可檢驗的判準：

1. **吞噬** —— `except` 後回傳空值而非拋出
2. **語意混同** —— 同一個回傳值同時代表「無資料」與「故障」
3. **監控失效** —— 上游（DAG／前端）無從得知發生過錯誤

實際掃描發現的情形比報告預估的更嚴重：

| 位置 | 現象 |
| --- | --- |
| `get_or_set_cache_from_redis` 3 個函式 | 全部吞掉例外，僅 `print` |
| `c_data_service` 4 處 | MySQL 故障吞成空 `DataFrame`／空 list |
| `c_data_service` 4 處 | 「快取寫入失敗僅記錄」的 `except` **是死碼** —— `set_cache` 內部已吞掉例外，該 `except` 永遠不會執行 |
| `cal_accidents_nearby_nightmarket` | 逐個夜市 `except: continue`，全數失敗仍回傳成功訊息 |
| `aggregate_national_master` | 聚合不到任何資料時只 `print` 一行後正常結束 |

淨結果：**MySQL 完全無法連線時，`d06` 六個 task 全綠，Redis 被寫入一批空結果，
前端安靜地顯示「查無資料」。**

## 二、決策摘要

| # | 決策 | 狀態 |
| --- | --- | --- |
| 1 | `c_data_service` 一律 `raise`，不再回空 `DataFrame`／空 list | 依原案 |
| 2 | 快取寫入失敗依情境區分：預計算路徑 `raise`，read-through 路徑僅 `warning` | 依原案 |
| 3 | 逐個夜市保留跳過，但累計失敗清單，迴圈結束後有失敗即 `raise` | 依原案 |
| 4 | 前端納入本輪，切至 `redis_utils` 並加降級 | 依原案 |
| 5 | **`exc_info=True` 只在例外停止傳播之處使用** | 實作中新增 |

### 子決策 5 的來由

子決策 1～4 完成後，一次 Redis 寫入失敗會印出兩份 traceback
（`redis_utils` 一份、`c_data_service` 一份）。根源是 ADR-0001 訂下的
「一律 `logger.error(..., exc_info=True)` 後 `raise`」—— 這個模式在單層可行，
在分層程式碼中則是「既處理又不處理」。

最終規則：**有 `raise` 就不帶 `exc_info`，沒有 `raise` 才帶。**

過程中曾嘗試更激進的做法（內層完全不記錄，並刪除因此變成空殼的 `try/except`），
實測後判定**可讀性變差**：空殼 `try/except` 雖技術上冗餘，卻標示了
「這裡預期會出錯」，刪除後維護者不知該在何處補處理。故還原並改採現行規則。

### B. 建議新開「候選 9：資料庫連線資源生命週期」

本輪檢視 `get_table_from_sqlserver()` 時發現，與現有任何候選都不同病因，
故建議獨立成案。

```python
def get_table_from_sqlserver(dql_str, params=None, *, database=None):
    engine = create_engine_to_mysql(database)   # 每次呼叫都建一個新 Engine
    with engine.connect() as conn:
        ...
    return df                                    # 從不 dispose
```

- `create_engine_to_mysql` 設定了 `pool_size=5`、`pool_recycle=3600`、
  `pool_pre_ping=True`，但**每次呼叫都建立全新 Engine（即全新連線池）**，
  開一條連線、用完歸還自己的池，然後整個池被丟棄。池永遠不會服務第二個請求，
  這三個參數形同虛設。
- Engine 從未 `dispose()`，只能等 GC 非確定性回收。
- **熱路徑代價高**：`c_data_service.py:360` 位於
  `for a_nightmarket in batch` 迴圈內，一個夜市一次查詢。以 300+ 個夜市計，
  `d06` 每輪約建立 300 個 Engine。全 repo 共 16 個呼叫點。

**同一 repo 內已有正解**：`redis_utils._get_redis_pool()` 以模組層單例解決了
完全相同的問題 —— Redis 有做，MySQL 沒有。修法明確：`mysql_utils` 增設
以資料庫名為鍵的 Engine 快取。

歸類理由：候選 1 的病因是「重複的錯誤處理樣板」、候選 5 是「例外語意」、
候選 7 是「設定分散」，本項是**資源生命週期／效能**，與三者皆不同。
