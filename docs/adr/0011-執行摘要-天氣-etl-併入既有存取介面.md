## 候選 1：刪除第二套 MySQL 存取面

- 狀態：**已驗收**
- commit：`dcacc3b`
- 引用：[**ADR-0004**（MySQL Engine 以資料庫名為鍵的單例快取）](./0004-mysql-engine-以資料庫名為鍵的單例快取.md)、
  [**ADR-0008**（必填設定在使用時驗證）](./0008-必填設定在使用時驗證.md)

### 一、病因定義

一個外部資源在專案中應該只有一個**存取面**。天氣 pipeline 帶進了 MySQL 的第二套。

症狀最尖銳的形式是兩個同名函式並存：

```python
# src/util/get_table_from_mysql_gcp.py
def get_table_from_sqlserver(dql_str, *, database=None) -> pd.DataFrame: ...

# src/util/mysql_utils.py
def get_table_from_sqlserver(dql_str, params=None, *, database=None) -> pd.DataFrame: ...
```

呼叫端寫 `get_table_from_sqlserver(query, database=database)` 時，
讀者無法從呼叫處判斷用的是哪一個 —— 必須回頭看 import 行。

#### 病灶：每次呼叫新建 Engine

`get_engine_sqlalchemy()` 內是裸 `create_engine(...)`，沒有 ADR-0004 的 `_ENGINES` 快取：

```python
# 刪除前
def get_engine_sqlalchemy(database: str = default_database) -> Engine:
    engine = create_engine(
        f"mysql+pymysql://{username}:{password}@{host}:{port}/{database}?charset={charset}",
        pool_size=5, pool_pre_ping=True, pool_recycle=300, ...)
    return engine
```

`l_transform_and_load_to_mysql()` 在分批迴圈裡逐批呼叫查詢與建表，
一次 DAG run 生出數十個各帶 5 條連線的池。三個 pool 參數全部無效 ——
這正是 ADR-0004 定義的病因，只是換了一個檔案重演。

#### 一併帶進來的規範外事物

| 項目 | 問題 |
| --- | --- |
| `CHARSET` 環境變數 | 會成為第 16 個變數，`CLAUDE.md` 與 `.env.example` 皆無 |
| `MYSQL_HOST` 預設 `"mysql8"` | 既有 `mysql_utils` 是 `"localhost"`，同一變數兩種預設 |
| `writer`（`AIRFLOW_ADMIN_EMAIL`） | 被 import 但全專案零使用 |
| 缺 `_require_credentials()` | 缺 `MYSQL_USER` 時連線字串成 `None:None@`，錯誤訊息誤導排查方向（ADR-0008） |

### 二、決策摘要

**刪除兩支自有的 MySQL 存取模組，呼叫端改指向 `mysql_utils` 的等價函式。**

| 刪除的 | 改用 |
| --- | --- |
| `get_engine_sqlalchemy(database)` | `get_engine_to_mysql(database)` |
| `get_conn_pymysql(database)` | `get_pymysql_conn_to_mysql(database)` |
| `get_table_from_mysql_gcp.get_table_from_sqlserver()` | `mysql_utils.get_table_from_sqlserver()` |

#### 一併決定的一件事：`database=None` 的語意

刪除前，`get_engine_sqlalchemy()` 不帶參數時回退到 `os.getenv("MYSQL_DATABASE")`；
`mysql_utils.get_engine_to_mysql(None)` 則是「不指定資料庫」。兩者語意不同。

**決定採 `mysql_utils` 的語意，不做相容包裝。** 三個理由：

1. 該回退分支在實際路徑上是死碼 —— [`d07`](../../dags/d07_track_recent_weather.py) / [`d08`](../../dags/d08_track_hist_weather.py) 一律傳入明確的 `database="traffic_accidents"`
2. 專案慣例是由 DAG 以 `os.getenv("MYSQL_DATABASE")` 解析後往下傳（見 [`d02`](../../dags/d02_track_recent_traffic_accidents.py)）
3. 在天氣模組保留 env 回退會生出第二套慣例，與本輪目的相反

## 候選 2：DDL 回到宣告樣板

- 狀態：**已驗收**
- commit：`e049c48`

### 一、病因定義

建表在既有 codebase 已有明確的位置與形狀：DDL 以 dict 宣告在
`src/task/create_*_tables.py`，執行交給 `mysql_utils.create_tables(engine, tables)`。
天氣這支卻放在 `src/util/`、自己開 connection、自己 `conn.execute()`。

#### 病灶 1：`engine.connect()` 沒有事務收尾

```python
with engine.connect() as conn:
    ddl_text = text(f"""CREATE TABLE IF NOT EXISTS {table_name}(...)""")
    conn.execute(ddl_text)          # ← 無 commit()，離開 context 會 rollback
```

SQLAlchemy 2.x 的 `connect()` 預設不自動提交。這段之所以「碰巧」有效，
是因為 MySQL 的 DDL 帶隱式提交 —— 靠資料庫特性掩蓋的錯誤寫法，
換成任何支援交易式 DDL 的資料庫就會靜默失效。

`create_tables()` 用的是 `engine.begin()`，離開 context 自動提交、失敗自動復原。

#### 病灶 2：沒有第二個使用者的參數

`table_name` 被做成參數並內插進 DDL 本體與三個索引名：

```python
INDEX idx_{table_name}_obt(`observation_datetime`),
INDEX idx_{table_name}_long(`longitude_round`),
INDEX idx_{table_name}_lat(`latitude_round`)
```

全專案只有一個呼叫點、傳的永遠是 `"fact_hourly_weather"`。
這個「彈性」沒有第二個使用者，卻開了一道 DDL 字串內插的口子。

#### 病灶 3：`print` 而非 logger，且 `return None` 寫在 `with` 內

### 二、決策摘要

**天氣 DDL 改用與 `create_night_markets_tables.py` 完全相同的形狀。**

| 改動前 | 改動後 |
| --- | --- |
| `src/util/create_weather_related_tables.py` | `src/task/create_weather_tables.py` |
| `create_weather_hist_table(table_name, *, database)` | `create_weather_tables(engine)` |
| 函式內組 DDL 字串 | 模組層 `WEATHER_TABLES` dict 宣告 |
| 自行 `engine.connect()` + `execute()` | `create_tables(engine, WEATHER_TABLES)` |

#### 一併決定的一件事：索引與 UK 名稱不改

固定表名後，索引名可以縮短成 `idx_hw_obt` 這類形式（近似夜市表的 `uk_nm_latlonwkd`）。
**決定不改**，維持與原本內插結果逐字相同的
`idx_fact_hourly_weather_obt` / `_long` / `_lat` 與 `UK_WHH_hash`。

理由是生產環境的資料表可能已以舊名建立，`CREATE TABLE IF NOT EXISTS` 不會重建它。
改名只會讓宣告與實際資料庫綱要出現無謂落差，而索引名不影響任何查詢。
本候選的目的是搬移與樣板化，不是重新命名。

## 候選 3：天氣 API 改走故障分類

- 狀態：**已驗收**
- commit：`4ec33f2`
- 引用：[**ADR-0001**（不使用 AirflowException）](./0001-不使用-airflowexception-一律原樣拋出.md)、
  [**ADR-0003**（不把故障吞成正常但空）](./0003-快取層不再吞噬例外.md)、
  [**ADR-0006**（區分暫時性與永久性故障）](./0006-抓取層區分暫時性與永久性故障.md)
- 併入範圍：[T-C](#t-c-疑似-bug) 第 3 項（`UnboundLocalError`）與第 5 項（失敗率分母）

### 一、病因定義

`src/util/request_weather_api.py` 把**五種** requests 例外全部轉成 `AirflowException`：

```python
except requests.exceptions.Timeout:
    print("response.status_code: ", response.status_code)
    raise AirflowException("Timeout!")
```

#### 病灶 1：轉換型別使故障分類失效

原始例外型別被抹除後，`crawling_utils.is_transient()` 再也認不出 429 與 5xx，
於是 `@retry_on_transient` 完全用不上 —— 一次瞬間的連線中斷，本可在 2 秒後自癒，
卻只能退回 Airflow task 層的重試（間隔 20 分鐘起跳，且整批 50 個地點重跑）。

#### 病灶 2：三個必然觸發的缺陷

| 位置 | 缺陷 |
| --- | --- |
| `except Timeout` / `except ConnectionError` | 區塊內引用 `response`，但這兩種例外發生時 `response` **尚未被賦值** → `UnboundLocalError` 蓋掉真正的網路錯誤（T-C #3） |
| 狀態碼 3xx 時 | 不進 200 分支、不進 429 分支，`raise_for_status()` 對 3xx 也不拋 → 穿過所有分支**隱式回傳 `None`**（ADR-0003） |
| `failed_files / len(data)` | 缺 `hourly` 的元素既不上傳、不計入失敗，**也不留任何紀錄**。`[{}]` 這種回應 → `0/1 = 0` → **「一筆都沒存到」被算成完全成功**，且事後從 log 完全無從察覺（T-C #5） |

#### 病灶 3：位置錯置

OpenMeteo 的 URL、參數名、`timezone=Asia/Taipei` 全是站台專屬。
ADR-0006 的判準是「換一個資料來源仍然成立」才進 `src/util/` ——
這支不成立，該待在 `src/task/e_*.py`，正如 Google Places 的呼叫待在 `e_crawling_nightmarket.py`。

### 二、決策摘要

**刪除 `src/util/request_weather_api.py`，內化為 `_request_weather_api()`；
`e_crawler_weather_gcp_refactor.py` 更名為 `e_crawling_weather.py`。**

本候選經 `/grilling` 走過五個子決策。其中前三個依賴一段查證 ——
**OpenMeteo 的限流是加權計次**，這件事改變了整個決策的前提，記於此。

#### 前提查證：429 是結構性的，不是偶發

##### 已證實的部分

1. **免費層是三個限流窗口**：每分鐘 600、每小時 5,000、每日 10,000
   （[Pricing](https://open-meteo.com/en/pricing)、[Terms](https://open-meteo.com/en/terms)）
2. **呼叫次數是「加權」的，不是一次 HTTP 請求算一次**。成本隨
   時間區間、地點數、變數數、模型數上升，且以小數計。
   最直接的證據是 Open-Meteo 各 API 文件頁**會就當前參數顯示該次請求的呼叫成本** ——
   例如 [Climate API](https://open-meteo.com/en/docs/climate-api) 會顯示單次請求相當於
   `1844.5` 次呼叫，[Seasonal Forecast API](https://open-meteo.com/en/docs/seasonal-forecast-api)
   顯示 `1.3` 次（[Features](https://open-meteo.com/en/features)）

##### 未證實的部分（**本文的推算基於此，使用時請留意**）

具體的加權公式**沒有找到可引用的官方出處**。下式是依「加權存在且隨三個維度上升」
反推的重建，不是官方規則的引文：

```
weight ≈ max(1, 變數/10) × (天數/14) × 地點數
```

套用到本 pipeline 的一批（7 個變數 × 365 天 × 50 個地點）：

```
weight ≈ 1 × 26.07 × 50 ≈ 1,300 次  ← 單一個 HTTP 請求
```

| 窗口 | 推算撐得住幾個批次 |
| --- | --- |
| 每小時 5,000 | 約 4 個 |
| 每日 10,000 | **約 8 個** |

而一年需要 220 個批次（11,000 個獨特座標 ÷ 50），推算免費層跑完一年約需 29 天。

##### 為何仍採信這個量級

推算的**絕對數字未經驗證**，但結論（429 是常態而非邊界情況）有兩個獨立支撐：

- 使用者的實際運行觀察：「確實很容易在一天內觸動 429」
- 加權機制本身已證實存在，而本 pipeline 的請求在三個維度上都遠超基準

決策只依賴「量級」而非精確值 —— 無論單次是 1,300 還是 500 次，
結論都是「日限額每天只夠跑個位數批次」，而兩層重試都等不過那個窗口。

##### 取得權威數字的方法

[Historical Weather API 文件頁](https://open-meteo.com/en/docs/historical-weather-api)
的參數面板可直接填入本 pipeline 的實際參數（50 個座標、整年區間、7 個變數），
頁面會顯示該次請求的實際呼叫成本。**候選 7 執行時應以此核實**，
並回頭修正本節的推算。

Sources：[Features](https://open-meteo.com/en/features)、
[Pricing](https://open-meteo.com/en/pricing)、
[Terms](https://open-meteo.com/en/terms)、
[Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api)、
[Climate API](https://open-meteo.com/en/docs/climate-api)、
[Issue #485](https://github.com/open-meteo/open-meteo/issues/485)

#### 子決策 1：自訂 `_should_retry`，429 不重試

兩層重試的時間尺度都覆蓋不了日限額：

| | 最長能等 |
| --- | --- |
| tenacity（`RETRY_WAIT`，實測） | 3 次嘗試、累計 **6 秒**（2 + 4） |
| Airflow task retry | 4 次嘗試、累計約 **2.3 小時** |
| **日限額需要等** | **最多 24 小時** |

因此 429 交給 tenacity 只會在 log 留下三筆永遠不會成功的紀錄。
**真正的復原機制是 `prep_batch_plan()` 對歷史年份會排除 GCS 上已存在的檔案**
——撞到 429 就讓它失敗，下一次 DAG run 自動從斷點續跑。這是既有設計就支援的，
本候選只是把它確立為正式策略並寫進 docstring。

其餘暫時性故障（Timeout、ConnectionError、5xx）則相反 ——
幾秒退避往往就能自癒，在此重試可省下一輪 Airflow 的 20 分鐘。

與 `e_crawling_nightmarket._should_retry` 同形，但方向相反：那支是**放寬**
（HTTP 200 body 裡的錯誤也要重試），這支是**收緊**（429 不重試）。

#### 子決策 2：失敗率超標拋 `RuntimeError`

與 `c_data_service.py:589`「聚合不出資料代表上游未生效」同形 ——
執行期狀態不對，而非參數問題（那是 `ValueError` 的領域，專案有 8 處）。
ADR-0001 已論證 `AirflowException` 與其他例外的失敗／重試語意完全相同，
因此 Airflow 側行為零變化。

#### 子決策 3：分母改用「請求的地點數」，並加上筆數斷言

```python
if len(records) != len(lat_round_lst):
    raise RuntimeError(...)
```

這個斷言是本候選唯一新增的行為。理由：下方是**按位置**把天氣掛回事故座標
（`lat_round_lst[j]`），舊版有一行註解 `# len(data) == len(lat_round_lst)`
宣告了這個相等關係，卻從未驗證。一旦筆數對不上，天氣會被掛到錯誤的地點 ——
**與 ADR-0010 那個 CSV 欄位錯位是同一類缺陷**：不報錯，只靜靜寫進 MySQL。

不改用回應中的 `latitude`/`longitude`：那是網格中心座標，與事故端的值不同，
改了會讓下游 `t_dataclr_weather_hist` 的 merge 全部落空。位置對應是必要的，
所以只能斷言它。

分母改成請求數後，三種靜默損失都算得進來：缺 `hourly`、寫入失敗、回傳筆數不足。

#### 子決策 4：回傳契約 `list[dict]`，保證非空

OpenMeteo 單一地點回 dict、多地點回 list，那是 API 的特性，
不該讓呼叫端知道（`batch_size=1` 才會踩到的邊界）。正規化與非空判斷都在邊界完成，
呼叫端因此少一層 `if data:` 與 `isinstance` 巢狀。
空回應是故障而非「查無資料」——請求了 50 個地點卻拿回空的，不可吞成正常回傳。

#### 子決策 5：改名 + 全檔 `print` → `logger`

引入 logger 是 ADR-0006 規則 5 的必然結果（要區分 warning 與 error）。
若只改本候選碰到的函式，同一檔案會出現兩種輸出方式並存 ——
比機械性的 diff 更糟。7 處 `print` 全數轉換。

檔名去掉無意義的 `_gcp_refactor` 後綴，與 `e_crawling_traffic_accident.py`、
`e_crawling_nightmarket.py` 一致。

## 候選 4：拆開 E/T/L 糾纏

- 狀態：**已驗收**
- commit：`97c3bab`

  [**ADR-0005**（finally 只負責釋放資源）](./0005-finally-只負責釋放資源.md)、
  [**ADR-0009**（查詢參數走 bind parameter）](./0009-預計算的查詢粒度以批次為單位.md)
- 併入範圍：[T-C](#t-c-疑似-bug) 第 1 項（`Variable.get` 型別）與第 4 項（寫入失敗卻顯示成功）

### 一、病因定義

一個 `l_` 前綴的檔案裝了橫跨三個階段的四個函式：

| 函式 | 實際做的事 | 名稱是否相符 |
| --- | --- | --- |
| `e_get_all_acc_geo` | 查 MySQL 取事故座標 | 相符（但放在 `l_` 檔案裡） |
| `t_dataclr_weather_hist` | DataFrame → DataFrame 清洗 | 相符 |
| `l_summary_report` | 列 GCS 檔案數並印報告 | **不符 —— 什麼都沒 load** |
| `l_transform_and_load_to_mysql` | 116 行，一人做完 E+T+L | **不符 —— 不只是 L** |

#### 病灶 1：連線洩漏

連線在**分批迴圈內**建立，`finally` 卻在迴圈外：

```python
for i in range(0, len(all_files), batch_size):
    ...
    conn = get_pymysql_conn_to_mysql(database)   # ← 每批一條
    cursor = conn.cursor()
    ...
finally:
    cursor.close()      # ← 只關得到最後一批的
    conn.close()
```

跑 N 批就洩漏 N−1 條連線。以候選 7 之後的規模（700 個檔案、每批 50）估算，
一年一次 DAG run 洩漏 13 條。

#### 病灶 2：寫入全數失敗卻顯示成功

```python
except Exception as e:
    print(f"Error on Batch No {...}")
    conn.rollback()          # ← 沒有 raise
else:
    return f"{target_year}_load_done"    # ← 且宣告的是 -> None
finally:
    cursor.close()           # ← 裸 close，前面若在建立連線就失敗會 UnboundLocalError
```

三個 ADR 的違規疊在同一段：`except` 不 raise（ADR-0003）、`else` 內 `return`
與 `finally` 裸 `close()`（ADR-0005）。結果是**寫入全數失敗的 task 在 Airflow UI 顯示綠色成功**（T-C #4）。

#### 病灶 3：手組 UPSERT

20 行的 `INSERT ... ON DUPLICATE KEY UPDATE` 字串組裝，與 `mysql_utils.upsert_to_table()`
內的版本幾乎逐字相同 —— 正是 ADR-0002 要消除的重複。

#### 病灶 4：其餘

- `if not all_files: return None` —— 上游跑完卻零檔案，故障被吞成正常（ADR-0003）
- `batch_size = Variable.get(..., 50)` —— 變數存在時回傳 `str`，`range()` 會 `TypeError`（T-C #1）
- 兩支查詢用 f-string 內插 `target_year`（ADR-0009）
- 缺欄的 Parquet 靜默 `continue`，全年檔案都缺欄時會寫入零列卻顯示成功

### 二、決策摘要

**拆成三支，分批迴圈留在 `l_` 層。** 經 `/grilling` 走過六個子決策。

#### 子決策 1：三支檔案，迴圈放在 `l_fact_hourly_weather`

```

src/task/t_fact_hourly_weather.py    ← 新增，純函式
src/task/l_fact_hourly_weather.py    ← 新增，含分批迴圈
src/task/l_load_to_mysql_gcp.py      ← 刪除
```

分批不能省：候選 7 之後仍有約 700 個觀測點 × 8760 小時 ≈ 610 萬列，
一次讀進記憶體約 500MB。

迴圈放在 `l_` 而非 DAG，因為 `CLAUDE.md` 明訂「改 ETL 邏輯改 `src/task/`，
改排程與相依改 `dags/`」—— 分批是 ETL 邏輯。代價是
`l_fact_hourly_weather(target_year, database, batch_size)` 的簽章與其他
`l_*`（那些接 DataFrame）不同形，此事寫進該函式的 docstring。

#### 子決策 2：兩支 E 函式不合併

`e_get_uniq_acc_geo` 與 `e_get_all_acc_geo` 的**粒度不同**：

| | uniq | all |
| --- | --- | --- |
| 列數 | 約 700（觀測點） | 約 40 萬（每筆事故一列） |
| 用途 | 決定要請求哪些地點 | 與天氣 merge |
| 執行時機 | DAG 最前端 | DAG 最後端 |

讓 uniq 從 all 推導等於為了 700 列從 MySQL 搬 40 萬列，
且違背原註解「只留這二欄，避免造成 Returned value、x-com 過長」的用意。
只把 `e_get_all_acc_geo` 搬到 `e_crawling_weather.py`，兩支 E 函式收在同一檔。

#### 子決策 3：`batch_size` 改函式參數

與既有的 `prep_batch_plan(df, target_year, batch_size=50)` 同形，由 DAG 顯式傳入。
型別確定是 `int`，T-C #1 自然消失；同時拿掉 `from airflow.models import Variable`。

#### 子決策 4：刪除 `l_summary_report`

它名為 `l_` 卻不 load、`upstream` 參數的值從未被使用、回傳值下游也沒用。
唯一產出是一行 log，而 `l_fact_hourly_weather` 本就會列同一批檔案 ——
在開頭 log 出數量即可。DAG 相依改用 `craw_done >> load_done`，同 `d02` 的寫法。

#### 子決策 5：格式錯誤的檔案計入失敗率

這些 Parquet 是抓取階段自己寫的，缺欄代表當時寫壞了 ——
與 ADR-0010「CSV 缺欄是資料來源的正常演進」不同。

採與候選 3 相同的形狀：單一檔案缺欄記 warning 並計數，
迴圈結束後若比例超過 `MAX_FAILURE_RATE`（沿用候選 3 的常數）則 raise。
少量損壞不擋下整年，大量損壞是故障。

空檔案清單與寫入失敗則一律 raise，依 ADR-0003。

#### 子決策 6：T 層的進位維持現狀

`t_fact_hourly_weather` 仍會原地修改傳入的 `df_all_acc_loc`，

## 候選 5：GCS 存取獨立成 seam

- 狀態：**已驗收**
- commit：`d15fd74`
- 引用：[**ADR-0001**（不使用 AirflowException／無 Airflow 環境可匯入）](./0001-不使用-airflowexception-一律原樣拋出.md)、
  [**ADR-0003**（不把故障吞成正常但空）](./0003-快取層不再吞噬例外.md)、
  [**ADR-0004**（連線資源以單例快取）](./0004-mysql-engine-以資料庫名為鍵的單例快取.md)、
  [**ADR-0006**（不疊加重試層）](./0006-抓取層區分暫時性與永久性故障.md)

### 一、病因定義

GCS 是本專案的第三個外部資源（前兩個是 MySQL 與 Redis），但它是唯一沒有存取面的一個。
七個呼叫點各自 `GCSHook(gcp_conn_id="google_cloud_default")`，重複的東西有三類：

| 重複的東西 | 次數 |
| --- | --- |
| `bucket_name = "taiwan_traffic_accidents_weather"` 字面量 | 4 |
| `save_dir = f"weather_cache_final/{target_year}..."` 組法 | 4 |
| `BytesIO` → `to_parquet` → `seek(0)` → `upload` 樣板 | 2 |
| `download` → `BytesIO` → `read_parquet` 樣板 | 2 |
| `list` → 濾 `.endswith(".parquet")` | 3 |

#### 病灶：型別本身綁死 Airflow

`GCSHook` 來自 `airflow.providers.google`，是 Airflow 專屬型別，且吃 Airflow Connection。
只要它出現在 `src/task/`，那支模組就永遠無法在無 Airflow 的環境被匯入 ——
而那正是 `test_util_logger_crtx.py` 兩支護欄測試把關的斷言。

更尖銳的是：`apache-airflow-providers-google` **不在 `pyproject.toml` 也不在
`requirements.txt`**，只是 `apache/airflow` 官方 image 碰巧內建。
換言之這條依賴從未被宣告過，卻是兩支 ETL 模組能否載入的關鍵（見 [T-A](#t-a-依賴宣告與實際不符)）。

### 二、決策摘要

**採方案 B：改用 `google-cloud-storage` 原生 client，並抽出 `src/util/gcs_utils.py`。**

方案 A（包裝 `GCSHook`）被否決的理由是 ADR-0001 的護欄不能為了新資源開白名單 ——
白名單一旦開了，下一個資源沒有理由不比照。完整論證見決策文。

介面：

```python
_CLIENT: storage.Client | None = None
def _get_client() -> storage.Client                                    # ADC，模組層單例

def read_parquet(bucket, object_name) -> pd.DataFrame
def write_parquet(bucket, object_name, df, *, index: bool = False) -> None
def list_parquet(bucket, prefix) -> list[str]
```

本候選經 `/grilling` 走過七個子決策，逐項記錄如下。

#### 子決策 1：seam 切在 DataFrame 層，不切在 bytes 層

`gcs_utils` 擁有 Parquet 序列化。判準是**刪除測試**：若只做 bytes 搬運，
`BytesIO` + `to_parquet` 樣板會原封不動留在 4 個呼叫點 ——
那是把複雜度搬家，不是集中。

先例是 `redis_utils`：它不暴露「存 bytes」，而是 `set_cache` / `get_cache`，
pickle 由模組自己擁有。同一個形狀。

#### 子決策 2：bucket 是顯式參數，不是環境變數

與候選 1 對 `database` 的決定一致：資源內的命名空間由呼叫端指定。
`WEATHER_BUCKET` 常數留在天氣模組，4 個字面量收成 1 個。
效果是 `gcs_utils` 完全不知道 weather 的存在 —— 換一個 bucket 它仍然成立
（ADR-0006 對「什麼該進 `src/util/`」的判準）。環境變數維持 15 個。

#### 子決策 3：ADC + 模組層 Client 單例

`storage.Client()` 不帶參數，走 Application Default Credentials：
VM 上取用附加的 service account（經 GCE metadata server），地端取用
`gcloud auth application-default login` 的憑證。因此 `gcs_utils` 不讀任何 GCP 環境變數。

Client 攜帶憑證與 HTTP session，快取在模組層 `_CLIENT` ——
與 `mysql_utils._ENGINES`（ADR-0004）、`redis_utils._REDIS_POOL` 同形。

否決了「顯式 key file」：需掛載 secrets、新增環境變數、管理輪替，且是 GCP 官方反模式。

#### 子決策 4：不自行重試，依賴函式庫內建

**不再疊第二層。** ADR-0006 明文提醒過疊層會讓重試上限變成 3×3 的隱患。

依賴既有機制的前提是那個機制的範圍要講得精確，否則「以為有重試」與
「以為沒有」同樣危險。以下以**實際安裝的 `google-cloud-storage 3.13.0`
原始碼**核對（`site-packages/google/cloud/storage/retry.py`）：

**承接重試的工具**：`google.cloud.storage.retry.DEFAULT_RETRY`，
底層是 `google.api_core.retry.Retry`，判斷式為同檔的 `_should_retry()`。

**重試範圍**：

| 類別 | 內容 |
| --- | --- |
| HTTP 狀態碼 | **408、429、500、502、503、504 (注意：不是「所有 5xx」，`501` 不重試)** |
| 傳輸層 | `ConnectionError`、`requests.ConnectionError`、`ChunkedEncodingError`、`requests.Timeout` |
| 協定層 | `http.client` 的 `BadStatusLine` / `IncompleteRead` / `ResponseNotReady`；`urllib3` 的 `PoolError` / `ProtocolError` / `SSLError` / `TimeoutError` |

**退避參數**：首次 1 秒、每次 ×2、單次上限 60 秒、總時限 120 秒。

**本模組三支函式所用的 API 皆為無條件 `DEFAULT_RETRY`**，
以 `inspect.signature` 核對實際預設值：

```
Blob.download_as_bytes   retry = Retry(initial=1.0, maximum=60.0, multiplier=2.0, timeout=120.0)
Blob.upload_from_file    retry = Retry(initial=1.0, maximum=60.0, multiplier=2.0, timeout=120.0)
Client.list_blobs        retry = Retry(initial=1.0, maximum=60.0, multiplier=2.0, timeout=120.0)
```

##### 擴充本模組時的陷阱

函式庫另有 `ConditionalRetryPolicy`。對「重試可能造成資料重複或其他副作用」
的操作（例如 `Blob.delete()`、metadata 異動），預設是
`DEFAULT_RETRY_IF_GENERATION_SPECIFIED` ——
**只有在請求帶了 `if_generation_match` / `generation` 時才重試，否則一次都不重試**。

目前三支函式剛好都不屬於這一類，所以本子決策成立。但若日後在 `gcs_utils`
新增刪除或 metadata 異動的函式，不能沿用「反正函式庫會重試」的假設。
此提醒已寫進 `gcs_utils` 的模組 docstring 與各函式的 `Raises` 段。

##### 一併決定：不擴充 `crawling_utils.is_transient()`

GCS 已經有自己的傳輸層與重試機制，不需仰賴與擴充 `crawling_utils.is_transient()`，讓後者保持只依賴 requests、bs4 與 tenacity。

**Sources**：

- [Retry strategy | Cloud Storage](https://cloud.google.com/storage/docs/retry-strategy#client-libraries)
  —— 由 `retry.py` 的模組 docstring 自身引用
- [Configuring Timeouts and Retries | Python client libraries](https://cloud.google.com/python/docs/reference/storage/latest/retry_timeout)
- [Module retry | Python client libraries](https://cloud.google.com/python/docs/reference/storage/latest/google.cloud.storage.retry)
- [Improving the availability of your Cloud Storage: Automatic retries in client libraries](https://cloud.google.com/blog/topics/developers-practitioners/improving-availability-your-cloud-storage-automatic-retries-client-libraries/)
- [feat: retry API calls with exponential backoff · PR #287](https://github.com/googleapis/python-storage/pull/287)

#### 子決策 5：存到 GCS folder `tmp/` 的行為不進介面

`tmp/` 是天氣 pipeline 的路徑慣例，存在理由是 Airflow 的 dynamic task mapping：
`expand()` 只適合傳純量，整年度的經緯度 DataFrame 走 XCom 會過長，
因此以批號為鍵、把 DataFrame 放在 GCS 上交接。

#### 子決策 6：`index` 開參數，預設 `False`

將 parquet 寫入 GCS 下的 folder `tmp/` 用 `index=True`，寫入 `data/` 則用 `index=False`，決策把兩種行為都保留下來，所以寫入 parquet 的函式要開放一個參數 `index`，預設 `False`，`tmp/` 呼叫點顯式傳 `index=True`。

#### 子決策 7：mock 單元測試，不打真 GCS

以假 Client 取代真實 GCS。整合測試被否決：需憑證、會產生費用、
專案無 CI 測試 gate、且會在真 bucket 留下測試物件。

## 候選 7：氣象網格精度

- 狀態：**已驗收**

- 來源：候選 3 的 grilling 過程中浮現，非原始六候選之一
- 性質：**領域建模決策**，非技術債 —— 本輪唯一屬於此類的候選

### 一、病因定義

事故經緯度進位到小數點後兩位（0.01 度，約 1.1 公里），一年得到 11,000 個
相異座標，以 50 個一批共 220 個批次。

OpenMeteo 免費層的呼叫次數是加權計算的 —— 一次請求涵蓋的地點數、天數、
變數數愈多，計入的次數愈多。本 pipeline 一批要 50 個地點、整年逐小時、
7 個變數，很快就用盡每日額度，實務上跑不完一年份。

#### 病灶：0.01 度遠比模式網格細

實測 OpenMeteo archive API（2024 年資料）：

```
請求緯度 24.11  ->  網格中心 (24.147627, 120.605736)  氣溫 15.9
請求緯度 24.13  ->  網格中心 (24.147627, 120.605736)  氣溫 15.9
請求緯度 24.15  ->  網格中心 (24.147627, 120.605736)  氣溫 15.9
```

相鄰網格中心的緯度間距為 **0.0703 度**（約 7.8 公里；2017 年起的資料
來自 ECMWF IFS 9km）。0.01 度遠比它細，多數相鄰座標拿回的是完全相同的資料，
卻各自消耗一份額度。

以 400 個 0.01 度座標實測，只對應 **15 種相異的天氣序列**。

#### 病灶：預設的高程降尺度讓進位失去意義

OpenMeteo 預設以 90 公尺解析度的地形模型查出每個座標的海拔並據此調整氣溫。
於是同一網格內的座標會因海拔不同而拿到不同的氣溫，連帶影響 API 選用的網格 ——
進位後的去重結果因此無法預測。

實測同一批座標：不指定高程時落在 2 個網格，指定固定高程時收斂成 1 個。

### 二、決策摘要

完整論證見 [ADR-0012](./0012-氣象網格精度.md)，此處僅列結果。

| 決策 | 內容 |
| --- | --- |
| 進位精度 | `GRID_STEP = 0.05`，仍比模式網格的 0.0703 度細，不會把兩個原本不同的網格併成一個 |
| 高程 | `FIXED_ELEVATION_M = 10`，車禍多在人口密集的平地市區，主動承擔山區偏高的偏差 |
| 算法位置 | 收成 `round_to_weather_grid()` 單一函式，事故側與天氣側都呼叫它 |
| 文件 | 新增 `CONTEXT.md`（專案第一份領域術語表）與 ADR-0012 |

不選 0.1 度：那已比模式網格粗，一個進位後的座標橫跨約兩個網格，
是系統性地抹掉真實差異，而非邊界效應。
