# ADR-0007：路徑以專案根為基準，而非行程的工作目錄

- 日期：2026-07-31
- 狀態：已採納
- 範圍：新增 `src/util/paths.py`；`src/task/e_crawling_traffic_accident.py`、
  `src/task/e_crawling_nightmarket.py`、`src/task/t_fact_night_markets.py`、
  `dags/d04_analysis_pedestrian_accidents.py`、`docker-compose.yml`、`.gitignore`
- 相關：[ADR-0006 抓取層區分暫時性與永久性故障](./0006-抓取層區分暫時性與永久性故障.md)
- 來源：[ADR-0003 執行摘要](./0003-執行摘要-快取層與日誌職責.md)第五章 A 提出的「候選 8」

## 背景

專案內有五處以 `Path().resolve()` 作為路徑基準，且**每一處的註解都寫著
「取得專案根目錄的絕對路徑」**：

```python
curr_working_dir = Path().resolve()  # 取得專案根目錄的絕對路徑
raw_data_save_dir = curr_working_dir / "test" / "raw_data"
```

`Path().resolve()` 取得的是**行程的工作目錄（CWD）**，不是專案根目錄。
兩者只有在「從專案根執行」時才碰巧相同。

### 1. 落點隨 CWD 漂移

CLAUDE.md 記載「專案根目錄必須是所有指令的執行位置」—— 這是一個**未被強制的約定**。
違反它不會有錯誤訊息，只會讓檔案默默寫到別的地方：

```bash
cd src && poetry run python -m src.task.e_crawling_nightmarket
# → 資料寫到 src/test/raw_data/，下游讀不到
```

### 2. 容器中落在未掛載的位置

`docker-compose.yml` 的掛載設定：

```yaml
volumes:
  - ./dags:/opt/airflow/dags
  - ./logs:/opt/airflow/logs
  - ./src:/opt/airflow/src
  # ./test 沒有掛載
```

Airflow 容器的 WORKDIR 是 `/opt/airflow`（映像預設），因此
`Path().resolve() / "test" / "raw_data"` 解析為 `/opt/airflow/test/raw_data` ——
**那不在任何 volume 裡**。`d02` / `d03` / `d05` 抓回來的原始資料寫進容器的可寫層，
`docker compose up --build` 之後就消失。

這不只是「路徑會漂移」的潛在風險，是每次重建都在發生的資料遺失。

### 3. 兩類路徑混用同一個基準

`dags/d04:45` 用同一個寫法定位 mart 層的 SQL 檔：

```python
find_sql_files(Path().resolve() / "src/task/mart_table_sql")
```

但 SQL 檔與資料落點的性質完全不同：

| | 隨什麼移動 | 正確的基準 |
| --- | --- | --- |
| `mart_table_sql/*.sql` | 跟著**程式碼**走（同一個 commit、同一個映像） | `__file__` |
| `raw_data` / `processed_data` | 是**執行環境**的產物，地端與容器本來就該不同 | 專案根／設定 |

`d04` 這一行**碰巧正確** —— 因為 `./src` 掛在 `/opt/airflow/src` 且 CWD 剛好是
`/opt/airflow`。它靠兩個獨立設定對上，任一改動都會失效。

### 4. `t_fact_night_markets` 的模組層死碼

```python
curr_working_dir = Path().resolve()
raw_data_save_dir = curr_working_dir / "test" / "raw_data"
today = datetime.now().date()
jsonfile_path = raw_data_save_dir / f"Taiwan_night_markets_from_map_api_{today}.json"
```

四行都在模組層執行，而**沒有任何地方用到**（該檔的兩支函式都收路徑參數）。
除了本 ADR 的病因，它還有第二個缺陷：`datetime.now().date()` 在 import 時凍結 ——
DAG parse 在午夜前、task 執行在午夜後的話，日期會對不上。

### 5. 生產資料寫在 `test/` 目錄下

`test/` 同時是單元測試的所在（`test/unit_test/`）。爬回來的原始資料與
處理後的 CSV 寫進 `test/raw_data`、`test/processed_data`，語意混亂；
且 `.gitignore` 沒有對應規則，資料一旦產生就會被 git 追蹤。

---

## 決策

**路徑一律以專案根為基準推導，且「程式碼資產」與「資料落點」分開處理。
`Path().resolve()`（CWD）不再作為任何路徑的基準。**

新增 `src/util/paths.py` 集中推導：

```python
PROJECT_ROOT = Path(__file__).resolve().parents[2]   # src/util/paths.py → 專案根

DATA_DIR = PROJECT_ROOT / "data"
RAW_DATA_DIR = DATA_DIR / "raw"
PROCESSED_DATA_DIR = DATA_DIR / "processed"

MART_SQL_DIR = Path(__file__).resolve().parents[1] / "task" / "mart_table_sql"
```

### 七項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | **程式碼資產用 `__file__` 推導**（`MART_SQL_DIR`） | SQL 檔與程式碼在同一個 commit、同一個映像裡，位置關係是固定的。用 CWD 推導等於讓一個固定的關係依賴一個會變的值 |
| 2 | **資料落點以專案根推導**，不引入環境變數 | 落點需要一個確定的答案，而不是每個部署環境各自猜。環境變數會把「寫到哪裡」變成又一個要同步的設定（屬候選 7），本輪不開這個口 |
| 3 | 新增 `src/util/paths.py` 集中推導 | 病因就是「基準點散在五處且各自算錯」。收成一處，`parents[2]` 這個層數才只需要正確一次 |
| 4 | 目錄由 `test/raw_data`、`test/processed_data` 改為 **`data/raw`、`data/processed`** | 生產資料不該與測試程式碼同住一個目錄。`data/` 也讓 compose 的掛載與 `.gitignore` 規則有明確對象 |
| 5 | `docker-compose.yml` 加掛載 `./data:/opt/airflow/data`；`.gitignore` 加 `data/` | **不加掛載的話，本輪只修好「不漂移」，資料依舊寫進容器可寫層。** 落點錯了，基準對了也沒用 |
| 6 | 刪除 `t_fact_night_markets.py` 的四行模組層死碼 | 零呼叫端，且同時帶著本輪病因與「import 時凍結日期」兩個缺陷 |
| 7 | `paths.py` **只算路徑，不在 import 時 `mkdir`** | Streamlit 容器（`WORKDIR /app`，只 COPY `./src`）載入它時不該憑空建出 `data/`。建目錄留在真正要寫檔的函式裡 |

### 為什麼 `parents[2]` 在三個環境都正確

| 環境 | `paths.py` 的位置 | `parents[2]` |
| --- | --- | --- |
| 地端 | `<repo>/src/util/paths.py` | `<repo>` ✓ |
| Airflow 容器 | `/opt/airflow/src/util/paths.py`（`./src` 掛載） | `/opt/airflow` ✓ |
| Cloud Run | `/app/src/util/paths.py`（`COPY ./src ./src`） | `/app` ✓ |

三者的共同點是 `src/` 直接位於「根」之下，這個關係由 `PYTHONPATH` 設定
（`/opt/airflow/`、`/app`）與 `pyproject.toml` 的 `packages = [{include = "src"}]`
共同保證 —— 也就是說，**`parents[2]` 依賴的是一個本來就必須成立的約定**，
而 CWD 依賴的是一個沒有人保證的約定。

### 為什麼不用 marker 檔驗證專案根

常見做法是從 `__file__` 往上找到含 `pyproject.toml` 的目錄。這裡不適用：
**Airflow 容器內沒有 `pyproject.toml`**（`Dockerfile.airflow` 只 COPY
`requirements.txt`，程式碼靠掛載）。用 marker 驗證會在容器中找不到而失敗，
或往上找到非預期的目錄。

## 後果

- 從任何工作目錄執行 ETL，資料都落在同一個位置。
- **容器重建不再遺失原始資料** —— `data/` 有掛載，且地端與容器共用同一份。
- `mart_table_sql` 的定位不再依賴「`./src` 的掛載點恰好等於 CWD」這個巧合。
- 生產資料與測試程式碼分家；`.gitignore` 擋下爬回來的原始檔。
- 全 repo 零 `Path().resolve()`。

### 誠實的限制

- **`import` 仍然依賴 CWD 或 `PYTHONPATH`**。CLAUDE.md 的「必須在專案根執行」
  這條約定不會因本輪消失 —— `src.xxx` 絕對匯入的解析是另一回事。
  本輪只讓**資料與資產的落點**不再受 CWD 影響。
- **落點寫死為 `<專案根>/data`**。若日後需要把原始資料放到外接儲存或
  另一顆磁碟，就得引入設定（屬候選 7）。子決策 2 是刻意選擇「先確定，再彈性」。
- **`parents[2]` 仍是一個層數硬編碼**。搬動 `paths.py` 的位置會讓它失效 ——
  但它只出現一次，且有測試釘住（對照 `pyproject.toml` 的實際位置）。
- 既有的本機 `test/raw_data` 空目錄不在版控中，本輪不主動清理；
  改用 `data/` 後它會自然被棄置。
