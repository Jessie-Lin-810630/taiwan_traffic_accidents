# ADR-0008：必填設定在「真正要用」的那一刻驗證

- 日期：2026-07-31
- 狀態：已採納
- 範圍：`src/util/mysql_utils.py`、`src/util/redis_utils.py`、
  `src/task/e_crawling_nightmarket.py`
- 相關：[ADR-0004 MySQL Engine 單例快取](./0004-mysql-engine-以資料庫名為鍵的單例快取.md)、
  [ADR-0006 抓取層區分暫時性與永久性故障](./0006-抓取層區分暫時性與永久性故障.md)
- 來源：[ADR-0003 執行摘要](./0003-執行摘要-快取層與日誌職責.md)第五章 A 提出的「候選 7」

## 背景

專案有 9 個由 Python 讀取的環境變數，散在三個模組的模組層：

```python
# mysql_utils.py
host = os.getenv("MYSQL_HOST", "localhost")
port = os.getenv("MYSQL_PORT", 3306)
username = os.getenv("MYSQL_USER")        # 沒有預設值
password = os.getenv("MYSQL_PASSWORD")    # 沒有預設值
```

### 1. 缺設定時，錯誤訊息指向錯的方向

`MYSQL_USER` 未設定時 `os.getenv` 回傳 `None`，程式繼續往下走：

```python
connection_url = f"mysql+pymysql://{username}:{password}@{host}:{port}/{database}?charset=utf8mb4"
# → mysql+pymysql://None:None@10.140.0.2:3306/traffic_accidents?charset=utf8mb4
```

MySQL 收到帳號 `None`、密碼 `None`，回覆的是**認證失敗**。
排查的人看到「Access denied for user 'None'」，第一反應是去檢查資料庫的帳號權限 ——
而真正的原因是 `.env` 少了一行。

同樣的情形發生在 `REDIS_PASSWORD`（Redis 回 `NOAUTH Authentication required`）
與 `GOOGLE_MAP_API_KEY`（Places API 回 `REQUEST_DENIED`，
經 ADR-0006 的分類後訊息會說「金鑰無效」——但實際上是根本沒有金鑰）。

**三者的共同點：真正的原因（設定缺失）被下游的症狀掩蓋。**

### 2. `GOOGLE_MAP_API_KEY` 的檢查只涵蓋一條路徑

`e_crawling_nightmarket()` 函式內有檢查：

```python
if not API_KEY:
    raise ValueError("找不到 API 金鑰，請確認 .env 檔")
```

但 `search_place_id()` 與 `get_place_details()` 直接使用 `API_KEY`，
單獨呼叫它們時沒有任何檢查。檢查的位置與使用的位置不一致。

### 3. `load_dotenv()` 的位置其實是對的

初步盤點時，「三處 `load_dotenv()`」看起來是重複。實際查證後結論相反：

| 模組 | 讀設定嗎 | 需要 `load_dotenv()` 嗎 |
| --- | --- | --- |
| `mysql_utils` | 4 個 | 需要 |
| `redis_utils` | 3 個 | 需要 |
| `e_crawling_nightmarket` | 1 個 | 需要 |
| `crawling_utils` | 不讀 | 不需要 |
| `c_db` | 不讀（經 `mysql_utils`） | 加了也跑不到 |
| `c_data_service` | 不讀（經 `c_db`、`redis_utils`） | 同上 |

在 `c_db` 加 `load_dotenv()` 是**執行不到的**：
`from src.util.mysql_utils import ...` 這一行會先執行 `mysql_utils` 的模組層，
那裡的 `load_dotenv()` 早就跑完了。

同理，把 `load_dotenv()` 集中到 DAG（`d01`～`d06`）也不可行：
DAG 檔在第 15 行左右就 `from src.util.mysql_utils import ...`，
無論 `load_dotenv()` 寫在 import 之後或 `@dag` 函式體內，
`mysql_utils` 的模組層都已經讀完 `os.getenv` 了。
而且 `python -m src.task.xxx`、`streamlit run`、`pytest` 三條入口都沒有 DAG。

**另外，`load_dotenv()` 在容器中本來就是 no-op** ——
`docker-compose.yml` 用 `env_file` + `environment` 注入，
Cloud Run 用 `--set-env-vars`，環境變數在行程啟動時就存在。
它真正有作用的場合只有地端開發，且是冪等的、找不到檔案不報錯。

## 決策

**必填設定在「真正要用它」的那一刻驗證，並在訊息中直接說出設定名稱。**

```python
def _require_credentials() -> None:
    """建立連線前確認必填設定存在（ADR-0008）。"""
    if not username:
        raise ValueError("未設定 MYSQL_USER，請檢查環境變數設置")
    if not password:
        raise ValueError("未設定 MYSQL_PASSWORD，請檢查環境變數設置")
```

### 六項子決策

| # | 決策 | 理由 |
| --- | --- | --- |
| 1 | **`load_dotenv()` 維持現狀**（三處，各自負責自己讀的設定） | 見背景第 3 節 —— 位置已經是對的。搬到 DAG 或 `c_db` 都會因 import 順序而失效 |
| 2 | 必填清單：`MYSQL_USER`、`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`GOOGLE_MAP_API_KEY` | 這四個沒有預設值，缺了必定失敗。`*_HOST` / `*_PORT` 有合理預設（`localhost` / `3306` / `6379`），缺了仍可運作 |
| 3 | **驗證在使用時，不在模組層** | 模組層 `raise` 會讓 import 就炸 —— pytest 的 127 個測試中多數只測 SQL 組裝、不需真連線，會全面陣亡；Airflow 的 DAG parse 也會失敗。「缺設定」不該讓「讀不到設定的程式碼」也無法載入 |
| 4 | `REDIS_PASSWORD` 視為必填 | 本專案的 Redis 一律以 `--requirepass` 啟動（compose 與 VM 皆是），沒密碼必定連不上。雖然 `redis.ConnectionPool(password=None)` 在語法上合法 |
| 5 | 三個 MySQL 連線入口共用一支 `_require_credentials()` | `_create_engine()`、`get_pymysql_conn_to_mysql()`、`get_pymysql_conn_to_mysql_multistatement()` 都會用到同一組帳密，檢查抄三次是 ADR-0005 剛消滅過的樣板 |
| 6 | **不引入設定層**（dataclass / pydantic-settings），不改現有 `os.getenv` 寫法 | 9 個設定、3 個模組的規模撐不起一層抽象。真正痛的是「缺了不講」，不是「散在三處」 |

### 為什麼不做完整的設定層

一度考慮 `@dataclass(frozen=True)` + `get_settings()` 搭配 `lru_cache`：
型別轉換（`port` → `int`）、驗證、lazy 讀取一次到位。否決的理由：

- **規模不相稱** —— 9 個設定分屬三個獨立子系統（MySQL / Redis / Google API），
  彼此沒有交互作用。集中成一個物件後，`redis_utils` 得為了拿一個密碼而
  依賴一個裝著 MySQL 帳密的結構。
- **`import` 時凍結不是本輪的痛點** —— 它確實存在（模組層讀取），
  但實際造成的問題只有「測試換設定需 reload」。而測試目前一律 mock 連線，
  沒有換設定的需求。
- **改動面與收益不成比例** —— 三個模組的模組層全部要改寫，
  而收益是一個目前沒有人抱怨的問題。

若日後設定數量成長、或出現需要在執行期切換設定的需求（例如讀寫分離），
再回頭做設定層。屆時 ADR-0004 的「誠實的限制」已經記下了那個觸發點。

## 後果

- 缺 `MYSQL_USER` 時，第一行錯誤訊息是「未設定 MYSQL_USER，請檢查環境變數設置」，
  而不是「Access denied for user 'None'」。
- `GOOGLE_MAP_API_KEY` 的檢查從「只在 `e_crawling_nightmarket()`」擴大到
  兩支 API 函式，檢查位置與使用位置一致。
- **缺設定不影響 import** —— 不需要真連線的測試照常執行。

### 誠實的限制

- **這輪的價值主要是排查時間**。正式部署由 GitHub Secrets 注入，
  缺設定的情境不常見；受益最大的是地端第一次設定環境的人，
  以及 `.env` 少一行時的排查者。
- **設定仍在模組層讀取（import 時凍結）**。本輪只加驗證，沒有改變讀取時機。
- **`*_HOST` / `*_PORT` 的預設值仍是隱性行為** —— `MYSQL_HOST` 未設定時
  會靜默連往 `localhost`，在 Cloud Run 上這會失敗且訊息不會提到設定。
  這是刻意的取捨：有預設值代表「缺了也能運作」，把它們列入必填會讓
  地端開發變得更囉唆。
- **`port = os.getenv("MYSQL_PORT", 3306)` 的型別仍不一致**（預設是 `int`，
  環境變數來的是 `str`）。後續的 `int(port)` 蓋掉了這個問題，
  但 `_create_engine()` 的 f-string 是直接內插的。本輪不處理。
