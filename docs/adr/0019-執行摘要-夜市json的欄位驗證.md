## 一、病因定義

六支夜市清洗函式讀取欄位的方式一律是 `.get(欄位, 預設值)`，缺欄時填的是說明字串
或 `None`，沒有任何一支會因此失敗。若 Google 改動欄位名稱，整批夜市的地址五欄
會全部變成「無匹配縣市資訊」寫進資料表，pipeline 全綠、沒有一行 log。這正是
ADR-0003 要防的「把故障吞成正常但空」。

`geometry` 更嚴重：緯度加經度加營業星期是 `fact_night_markets` 的唯一鍵，
座標全成 `None` 等於整批資料失去主鍵。

病因的完整論證見
[ADR-0019 背景章節](./0019-夜市-json-的必要欄位在讀取時驗證.md#背景)。

## 二、決策摘要

[ADR-0019 的六項決策](./0019-夜市-json-的必要欄位在讀取時驗證.md#決策)逐條落實：
驗證分兩層（先 `result`，再四個必要欄位）、兩層都在對 `name` 取值過濾「夜市」之前完成、只驗第一層
不驗巢狀結構、缺欄比例以單一夜市為單位計算且分母是 4、未達門檻記 `warning`
且彙總而達門檻記 `error` 後拋 `ValueError`、掃完全部才拋。

## 三、實際改動

### 3.1 `read_googlemap_responsed_json()` 從純讀取變成讀取加驗證

`src/task/t_fact_night_markets.py:50-144`。一個迴圈同時做驗證與過濾地標名稱兩份工作，迴圈跳脫後
彙總驗證結果，並決定要 log level 要記 `warning` 還是記 `error`，後者還會 raise 例外。
目前，改動前後這支對 `data/raw/Taiwan_night_markets_from_map_api_2026-08-01.json` 測試資料的產出完全相同（443 個夜市），顯示這次更改沒有影響 ETL 清洗結果。

| 項目 | 改動前 | 改動後 |
| --- | --- | --- |
| 缺 `result` | `KeyError: 'result'` | 視為四個必要欄位全缺，走門檻判斷 |
| 缺 `name` | `TypeError`（`"夜市" in None`） | 記 warning，該筆在過濾時自然落選 |
| 缺一個必要欄位 | 無聲，填說明字串進資料表 | 記 warning，該筆照常留下 |
| 缺兩個以上 | 無聲 | 記 error 後拋 `ValueError` |

### 3.2 三處對決策文的偏離

**這三項都與 ADR-0019 寫的不同，決策文依慣例不回頭改，記在這裡：**

1. **常數不在模組層，改放函式內。** ADR 決策一寫「兩層都寫成模組層常數」，
   實作時依使用者要求改成 `read_googlemap_responsed_json()` 內的區域變數
   （`required_result_column`、`required_columns`、`missing_ratio_threshold`）。
   代價是測試無法 import 它們來驗證門檻算術，見 [3.4](#34-測試)。
2. **彙總與拋出的邏輯不獨立成函式。** 實作中途曾拆出 `_report_missing_keys()`，
   依使用者要求併回主函式。整支因此變長，但呼叫端只有一個入口。
3. **缺 `name` 的處理方式 ADR 沒寫。** 缺 `name` 只有 25%，未達門檻，但沒有名字
   就無從判斷是不是夜市。實作用 `a_night_market_info.get("name") or ""`
   讓該筆在名稱過濾時自然落選，不額外拋出。程式碼註解與測試 docstring 都標明了。
